<!-- presets -->
The served model on rtx3080ti is IQ3_XXS. Since 2026-10-14, its default tier sets the context window to 206584 and the auto-compact threshold to 150000; an optional tier sets the context window to 156584 and the threshold to 100000. The 206584 context window has been verified on long-context retrieval workloads up to about 151K tokens, matching the speed of the 156584 tier under the same load; longer prompts showed systematic errors in 200K-scale retrieval, and 256584 is not released. For configuration and calls, `config/model-catalog.json` lists only the served model, and its context window is the default tier on this host; because the service does not compact on the caller's behalf, callers must still set the auto-compact threshold of their own harness to the value of the tier in use (150000 for the IQ3_XXS default tier). Meanwhile, `bin/qwen-agent` directly uses the default tier of the served model, which is the first tier in `context_tiers` (see [Parameter comparison with Codex](#parameter-comparison-with-codex)). The remaining preset parameters are: high, thinking budget 8192 / total output limit 24576, temperature 0, top_p 1, top_k 20, presence_penalty 0, CPU assist auto. Here presence_penalty 0 is set explicitly because Strata 0.2.x fills in sampling keys omitted by both the request and the installation configuration with the values from the model card; without an explicit setting, requests with thinking disabled would receive presence_penalty 1.5. These settings serve only as a maintenance starting point, not as a conclusion of full quality acceptance or optimal parameters.

<!-- compact_check -->
Claude Code does not trigger compaction according to `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE`; instead, it compacts only when reaching the blocking limit (context window − 20000 − 3000: 183584 for the 206584 context window, and 133584 for the 156584 context window). You therefore need to set that limit to the threshold of the tier in use via `CLAUDE_CODE_BLOCKING_LIMIT_OVERRIDE` to keep it consistent with Codex. Verification on Claude Code 2.1.303 against a fake server (covering both two-turn conversations and mid-turn tool calls) showed the following: with the 206584/150000 tier, an input of 150.1K triggers compaction while 149.9K does not; with the 156584/100000 tier, an input of 100.1K triggers compaction while 99.9K does not; without this variable under the 206584 context window, compaction waits until 183.7K and does not trigger at 183.5K. In all tests, the session continued normally after compaction. Subsequent re-checks with the compaction probe across multiple versions (Claude Code 2.1.304 on 2026-10-20, 2.1.308 on 2026-10-22, 2.1.309 and 2.1.310 on 2026-10-24, and 2.1.317 on 2026-11-04) ran 3 times each on the 206584/150000 tier and all passed. Because this variable is not in Claude Code's public documentation, re-verify it after upgrading Claude Code.

<!-- approval_cache -->
The engine holds the VRAM prefix cache for a single session, so an approval request evicts the main conversation's cache. To prevent this, this host enables session staging by default (`conversation-cache-mib 8192`, `conversation-cache-slots 4`, `conversation-cache-min-free-mib 5120`), staging the cache to system memory when switching sessions: staging a main conversation of about 17K tokens takes about 0.1 seconds, and restoring it takes about 0.03 seconds; without staging, the entire main conversation must be re-read after every approval (about 16 seconds for 17K tokens). Measured in the same approval scenario, enabling staging reduces the time per run from 69.0 → 46.2 seconds.
