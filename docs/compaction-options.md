# 独立上下文压缩方案研究

核对2026-10-03。当前无需额外下载压缩工具。pi值得借鉴，LLMLingua可以实验，但不能直接替换Codex的compact流程；方案尚未选优。

## 当前流程与实际限制

调用方Codex记录消息/工具事件；当前推荐156584窗口、100000自动阈值及scope total，到阈值安排摘要；摘要由同一本地Qwen生成，桥仅转换协议。config/compact_prompt.txt保留明确约束、精确值/路径/版本、未完成事项、真实失败，以及已成功工具调用/结果/次数。安装项目不替调用方设置压缩。

默认Q2摘要曾丢失ALPHA/BETA，默认IQ2第二次漏禁止下载；自定义提示在自动及手动压缩中保住所选事实。模拟usage199999未触发，200000/200001触发；真实约203K下一轮自动压缩。客户端内部估计与渲染后API usage不同，tokenUsage.total是会话累计用量，不是当前窗口大小。不存在已验证的“精确压到160K”目标。

v0.1.37同一Linux持久线程完成两次200K压缩，实际摘要约118.7、111.5秒，所选事实与一次性回执保留，但第10、19源码批次各重复读取一次，严格工具次数失败。错误摘要在只读fork中产生语义污染；这说明协议成功不保证内容正确。503/504后原历史保留、重启resume可继续；单条超大新输入仍可能400，摘要不能容纳任意单条消息。证据见[验证汇总](validation.md)与[WSL压缩](../reports/v0.1.37/wsl-compaction.json)。

摘要本身要读取长历史，新摘要前缀还可能造成后续重读。比较时计入摘要生成和继续任务成本，不以最终答复正确抹掉重复工具或事实丢失，也不重新提供关键值掩盖丢失。

## 上下文容量计算

2026-10-05用户确定后续上下文比较采用以下公式，K按十进制计算（1K = 1000 token）：

```text
最大上下文容量 = 自动压缩阈值 + 32,000 + 24,576 + 8
```

| 项目 | 含义 |
|---|---|
| 自动压缩阈值 | Codex开始安排自动压缩的当前上下文token阈值；本维度保持64,000、100,000、150,000、200,000四档。它是触发点，不是对请求输入的硬性截断上限 |
| 32,000 | 压缩时上下文超额的最大预算，即从阈值到实际压缩请求输入之间预留的增长空间；覆盖触发前后的生成、工具返回、压缩提示等造成的增加，以及客户端估计与Strata实际分词的差异。不是摘要长度目标，也不是额外输出预算 |
| 24,576 | 当前桥中最高推理强度high的默认总输出预算，包含思考及最终文本。即使本次使用low或medium，也按high预留，允许运行期间临时切换强度而不重新启动引擎；不得再额外叠加思考预算 |
| 8 | Strata v0.1.38容量检查的安全余量（`CTX_SLACK`）；服务要求实际输入token数加请求输出上限加此余量不超过引擎容量 |
| 最大上下文容量 | 本次启动时设置的Strata引擎总容量；隔离Codex的声明窗口同步采用相同值，启动后核对实际生效容量 |

| 自动压缩阈值 | 最大上下文容量（token） |
|---|---:|
| 64K | 120,584 |
| 100K | 156,584 |
| 150K | 206,584 |
| 200K | 256,584 |

在实际压缩输入不超过“阈值 + 32,000”、请求总输出上限不超过24,576时，该公式保留完整输出预算。32,000是容量规划中的最大超额预算，当前实现不会自动把增长限制到这个数；超额超过预算或显式输出上限更大时，严格容量检查仍可能拒绝请求。不据此宣称任意工具返回都能容纳，也不静默截断输入或启用`fit_max_tokens`缩小输出预算。日后改变最高输出预算或Strata安全余量时，需同步重算容量。

四档容量均不超过模型原生支持的262,144 token，无需因本公式超过原生长度而启用RoPE扩展。容量按最高强度预留不代表本测量切换到high；固定测量条件仍采用Q2_0/medium/default。新公式已获用户确认，工程源码及维护部署完成，64K/120584原三次尝试及随后获批单次补跑均已闭合；实际容量120584及严格输出策略已核对，现有三个完整实例和一个未交付实例。完整实例平均诊断分0.546、平均合并耗时51.3分钟，旧失败保留；补跑来源隔离通过但问题及时写入未通过。用户已决定原三档不重测；以后按新公式配置。既有100K/125K、150K/188K、200K/250K结果及64K/80K失败保持原容量，不重标为新公式的样本、不混算均值；本批次具体计划已获用户“agree”批准，仅覆盖64K三个合并实例；其他新批次仍须另报计划并取得开跑同意。

## pi和BetterCompaction

[pi官方压缩说明](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/compaction.md)显示，pi保留近期消息、选择切点、调用LLM生成结构化摘要，再重建上下文。因此安装pi本身不会免去Qwen或另一个模型生成摘要。

[BetterCompaction](https://github.com/NotSoSeriouss/BetterCompaction)是pi扩展，可只使用一个TypeScript文件。它将摘要请求保持为原对话消息并在末尾加指令，尝试利用后端已有的前缀缓存；仍由LLM生成摘要。它有希望缩短本地反复重读约200K历史的时间，但缓存收益取决于切点、消息模板、系统指令和缓存实际保留位置，不能保证完全命中。作者的时长例子没有正式基准，不当作rtx4070tis结果。

其接口是pi的session_before_compact，不是Codex接口。下载后放进Codex目录不会自动生效；本项目继续使用Codex，需要适配摘要请求构造或Codex客户端，再做实测。不要在协议桥内偷偷移动指令、截断原历史或破坏工具调用与返回的配对。

## LLMLingua / LLMLingua-2

[Microsoft官方仓库](https://github.com/microsoft/LLMLingua)提供Python包和小模型驱动的提示压缩。LLMLingua-2以token分类方式保留部分原文，属于抽取式压缩；不是通用的代理状态摘要器。

可能优点：不需要让大Qwen生成整段摘要，保留下来的字词来自原文。问题：删去的标识符、数值、否定词、工具返回或任务状态可能无法恢复；200K输入需要分块，中文/代码及跨块事实要单独验证。包之外还需模型与依赖，CPU耗时和额外RAM也要计入IQ3紧张的资源预算。当前不推荐直接替换Codex的任务历史。

## Codex可以怎样接入

[官方Hooks说明](https://learn.chatgpt.com/docs/hooks)有PreCompact/PostCompact以及压缩后SessionStart事件。PreCompact/PostCompact的当前返回结构没有“替换摘要文本”字段；SessionStart compact可添加上下文。它们可用于保存或重新注入明确事实，不能据此声称能直接运行pi的压缩器替代Codex摘要。

[OpenAI compact API](https://developers.openai.com/api/docs/guides/compaction)返回包含加密压缩项的上下文。该项不能直接交给本项目Qwen/桥解读，现有桥明确拒绝加密输入；不是本地Qwen的可下载压缩程序。

### 冻结输入与独立校验

建立与ARW验收材料分离的代码/文档review临时工程和真实工具任务，预先冻结公开任务及独立期望清单，期望不进入模型提示。任务提供精确中文约束、路径、版本、数值、作废要求的新旧关系、已完成/未完成检查、真实失败及一次性操作回执。分早期、中段和临近压缩三处出现，通过逐步读取不同材料及正常工具调用累积历史，达到当前200K阈值，单次新输入仍须在250K窗口内；不伪造usage或事件来代替真实长上下文测试。

同一线程连续触发至少两次真实自动压缩，压缩前后均保存输入/输出事件、摘要及工具轨迹。随后继续原任务，并用中性问题或后续依赖检查是否保留精确事实；不在问题中重新提供丢失的值，也不回送期望清单。测试结果由程序精确比较可机械校验的字段，语义项由Main按冻结依据逐项裁决，不由模型自评。固定内容中插入网页/工具返回的伪造指令，检查它们有没有被摘要升级成用户授权。

### 必须分别检查的结果

- **事实与约束**：精确值、否定要求、授权范围和作废关系是否正确，是否添加原历史不存在的要求；关键约束丢失、反转或伪造均记失败。
- **工具与任务状态**：检查工具调用与结果配对、成功/失败/未执行状态、完整性及工具次数。预先指定已经完成且无需重读的稳定输入，额外重复读取记失败；明确要求重新验证或文件已经改变时按冻结任务区分，不把合理复核算重复。
- **一次性副作用**：只对临时工程的合成计数器操作，独立观察是否恰好执行一次。工具调用次数和副作用次数分别记录，不能用后者正确掩盖前者重复。
- **继续任务质量**：按独立材料的既定预期检查文档/代码发现、证据及具体干净对照。保留压缩前后原始报告，不能通过追加提示或补跑覆盖失误；这些指标不混入ARW分数。
- **失败与恢复**：分别注入压缩请求503、504、中断以及结束后重启/resume，核对失败未替换原历史、未丢工具结果、未重复副作用，恢复能继续。故意错误摘要只在只读fork做受控反例，与正常运行的自发失败分开统计。

三次完整连续压缩运行分别给出逐项结果，关键约束、工具配对及一次性副作用须全部通过，禁止重复的工具也须满足冻结次数。平均正确率不掩盖某次关键失败；通过只代表覆盖到的工作负载，不宣称任意200K历史无损。

## 基础压缩提示的接入

本工程所有模型任务遵循AGENTS中的基础提示政策。活跃WSL及原版ARW测量入口通过`tools/metrics/prompt_policy.py`组合`config/prompts/compact-prompt.txt`及场景自带的inline/file压缩提示，两者均存在时全部保留；无自定义摘要提示时，保留Codex 0.160.0实际请求中的默认指令作为补充，快照见`tools/resources/codex/0.160.0/compact-prompt.txt`。最终文本及来源SHA存于运行目录的`prompt-policy/`，缺失或空的基础文件使提交失败。普通生成仍由Windows原生服务追加`config/prompts/startup-instructions.txt`；“只输出摘要”仅用于压缩阶段，不影响普通评审任务。其他工程自行管理harness，不自动修改其Codex配置。

历史九个完整上下文实例未接入工程基础压缩提示，只使用原生默认；本次修复后的64K三次采用新组合。原九次不重跑，比较时保留这个固定条件差异。失败终态修复让错误可见，不能自行保证压缩内容正确；每次仍按真实终态、压缩事件及完整会话检查统计。
