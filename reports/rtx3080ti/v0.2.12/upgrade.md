## 核对点

- `MODEL_CARD_SAMPLING`（qwen4exp、qwen35moe、deepseek41 三组）与 v0.2.11 逐字相同，`MODEL_CARD_KEYS` 与 `installation_defaults` 不需改（后者已显式给出 temperature、top_p、top_k、presence_penalty）。
- 新设置 `undeclared_tool_calls`：默认 `text`（行为与旧版一致），配置里没有该键，不需要设；`call` 是可选项，本机不启用。
- 草稿器：本机钉死 MTP；发布说明的调优 DFlash2 对 12 GB 的 UD-IQ4_XS-v31 才由 Auto 启用，对本机 IQ3_XXS + 钉死 MTP 无影响，也不下载 0.34 GB 草稿器。
- 速度口径：发布说明（#5318、#5307、#4006）改了服务报告的速度和时间，短请求的 tok/s 现在把准入时间算进去。下面解码 139 到 149 tok/s 高于 v0.2.11 检查的 86 到 109，**不能直接归为引擎变快**，可能是口径不同（也可能是脚本不同），要在 daily 里同口径复核。
- 与本机相关的修复：#5108（长 CUDA 提示行表越界读，可能崩溃）、#4828 强制 tool_choice、#4832 tool_use_id、#5281 MCP 末段匹配、#5312 Claude Desktop 模型名。未单独验证（本检查走的工具调用路径正常）。

## 实际工作速度对比（2026-11-09，`qwen-strata/speedcheck`）

数据：ARW strataloop 每一步（report / verified）的 `turn.completed` API usage 和 `*.meta.json` 的 ready 到 ended 时间。口径是**任务平均输出** = API 输出 token ÷ 该步墙钟秒数（含输入处理、工具执行），不是引擎解码速度；版本之间只看相对变化。引擎口径见本节后的「引擎口径」小节。

| 组 | 版本 / 配置 | 步数 | 输出 tok/s（总输出 ÷ 总秒） | 每步中位数（范围） |
|---|---|---|---|---|
| A | v0.2.10，ROUTE_PRIOR 关，内存 6600（11-04 到 11-06） | 20 | 66.6 | 65.2（45.9 到 75.0） |
| B | v0.2.11，ROUTE_PRIOR 开，内存 5600（11-08 05:16 到 06:51） | 9 | 77.9 | 78.1（72.4 到 82.6） |
| C | v0.2.12，ROUTE_PRIOR 开，内存 5600（11-09） | 5 | 83.9 | 80.9（75.9 到 88.9） |

- 同配置对比是 B 对 C（只差引擎版本）：83.9 对 77.9，约 +8%，每步最低 75.9，没有退化；差异在噪声上界附近（每步标准差 3.6 到 4.9，批次内容不同），只能说 v0.2.12 没变慢，不能说变快。只算 report 步：C 85.8（3 步）对 B 76.9（5 步）。
- A 到 B 约 +17%，同时变了 ROUTE_PRIOR（开）、内存（6600 到 5600）和版本，不用于归因。
- 同一批次、同一提示的对照（ARW 内容随提交变动，只作参考）：lib-arw-1 report 74.5（11-04，v0.2.10）对 84.8（11-09）；lib-background-agent-1 report 61.1（11-05）对 88.9；lib-arw-common-1 report 64.5（11-04）对 80.6。
- 排除 1 步：11-09 `lib-arw-1/verified`（83 秒、输出 3076 token，无最终消息，`verified.txt` 为空），按失败的核对步处理，与速度无关。
- 局限：API usage 不是引擎日志（测量规则只允许用于对账）；样本少且批次不同；11-09 的内存频率按 11-08 的设置推定为 5600，未重新核对；输入速度（预填充）无法从墙钟分开，未判断。
- 结论（API 口径，相对变化）：同配置的 B 到 C，总输出速度 77.9 到 83.9，约 +8%；每步中位数 78.1 到 80.9，约 +3.6%。批次不同、样本少，幅度不精确，只能说 v0.2.12 没有变慢的迹象。上文 upgrade 一节里冒烟的 139 到 149 tok/s 是短请求，且服务报告口径变了，不与此比较。

### 引擎口径：100K 到 150K 上下文（2026-11-09，`python3 -m tools.metrics.engine_speed`）

速度要在高压力下测，所以只取每个请求总输入（已缓存 + 未缓存）在 100000 到 150000 token 的请求（压缩阈值 150K 以下的高段），不用其他范围顶替。数据取自引擎日志和前端日志（用工具汇总，工具不输出路径和配置）；窗口取自 strataloop 的 `*.meta.json`：

- B（v0.2.11，11-08）：`05:16:48` 到 `06:49:38`，9 步。
- C（v0.2.12，11-09）：`05:33:30` 到 `05:41:52`（lib-arw-common-1 的 report + verified）和 `06:15:20` 到 `06:45:40`（lib-arw-1、lib-background-agent-1 各 report + verified），共 6 步；其中 lib-arw-1/verified 是失败的核对步，引擎请求照常计入。

两边的引擎启动参数指纹相同（同为 `5789852a`，即启动行除时间戳外完全一致）。ROUTE_PRIOR 环境变量不在启动行里，日志无法核对，沿用 speedcheck 的推定（两边都开）；内存 5600 属于启动参数的一部分时已被指纹覆盖，否则仍是推定。

| 组 | 窗口内请求 | 100K 到 150K 请求数 | 引擎输出 tok/s | 未缓存输入 tok/s | 复用比例 |
|---|---|---|---|---|---|
| B v0.2.11 | 483 | 274 | 110.6 | 1387 | 0.979 |
| C v0.2.12 | 35 + 147 = 182 | 13 + 74 = 87 | 116.1 | 944 | 0.990 |

- C 的两个窗口合并按总 token ÷ 总秒数计：输出 91950 token ÷ 791.7 秒，未缓存输入 106005 ÷ 112.3 秒。
- 引擎输出速度 B 到 C 约 +5.0%（110.6 到 116.1）。这里只算了汇总值，没有逐请求的分布，所以不给噪声范围；批次内容不同，幅度只作参考。不分上下文范围的全部请求作旁证：114.2 到 120.6（约 +5.6%），方向一致。
- 未缓存输入速度 B 到 C 下降约 32%（1387 到 944），不能解读为预填充变慢：C 的复用比例更高，每个请求的未缓存输入平均更短（C 约 1.2K，B 约 2.6K），短块的预填充效率本来就低；这个量取决于缓存命中情况，两批工作的不同足以造成。预填充速度的版本对比需要同样缓存状态的专门测量，目前没有。
- 对账：窗口内引擎输出总量与 API 输出总量相差约 1%（B 420965 对 424991；C 182080 对 183833），说明请求与引擎记录的时间对齐可信。引擎日志的 token 记录本身没有时间戳，工具按前端日志里已完成的生成请求顺序给每条记录配时间；两者条数差 2 到 3 条（B 3，C 两窗口合计 2），已在工具输出中如实报告。
- 局限：样本是 loop 实际工作的请求，不是专门的受控测量；C 只有 87 个符合范围的请求；窗口不是同一批工作；ROUTE_PRIOR 未能从日志核对。结论：引擎输出速度在 100K 到 150K 上下文下，v0.2.12 相对 v0.2.11 约 +5%，没有变慢的迹象。
