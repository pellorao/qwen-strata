# 本机 Q2_0：SSD 读取来源与 PLE 读取方式（探索性测量）

2026-10-10，Strata 0.1.40.2。每个条件只加载 1 次模型，先发 1 次冷请求，再测 3 次。这不是规则要求的每条件 3 个独立实例，所以**不作为选优结论**，只用来定位读取来源。完整数据见 [summary.json](summary.json)。

## 结论

- **大量 SSD 读取主要来自模型加载**。每次加载都从 SSD 读 36.2 GB，耗时 16.3–16.9 秒，约 2.2 GB/s，6 次加载结果都一样。加载用的是无缓冲读取。加载后 `strata.exe` 的工作集约 39 GB，64 GB 内存里放不下文件缓存的第二份副本，所以空闲内存帮不上忙。`qwen-agent` 每次运行都会加载一次、结束时停掉，连续运行时读取量就会不断累加，例如 24 次运行约读 870 GB。
- **生成期间的 PLE 读取很小**：
  - 新文本约 44 KB/token：21.6K token 的冷请求读 0.95 GB，4K token 的冷请求读 0.26 GB。
  - 重复出现的文本基本被默认 90 MB 的行缓存吸收，预热后每次请求只读 13–54 MB。
- **三种 PLE 设置预热后没有差别**。耗时都是 16.1–16.9 秒，decode 约 98–101 tok/s，prefill 在两种负载下分别约 2040–2130 tok/s 和 2630–2670 tok/s。
  - mmap 的冷请求代价大：长输入下读了 13.4 GB，耗时 35.5 秒，direct 是 0.95 GB、25.8 秒。
  - 把行缓存加大到 16M 行，工作集多约 1.4 GB，读取量和速度都没有改善。
- 与之前的 [v0.1.40.1 PLE 对比](../../../v0.1.40.1/resource-calibration/ple-io/summary.md)（mmap 工作量多 9.6%，保持 direct）不矛盾。**继续使用 direct 和默认行缓存。**
- 读取不消耗 SSD 的写入寿命；这几组测量中写入量每次请求只有几 MB。

| 4K 输入 / 1500 输出 | direct | 20.6 秒 / 259 MB | 16.9 秒 | 45.7 MB | 2042 | 100.6 | 38.7 GB |
| | mmap | 22.0 秒 / 2768 MB | 16.9 秒 | 42.0 MB | 2037 | 100.2 | 38.9 GB |
| | rowcache 16M | 20.0 秒 / 248 MB | 16.7 秒 | 53.6 MB | 2128 | 100.5 | 40.2 GB |
| 21.6K 输入 / 800 输出 | direct | 25.8 秒 / 954 MB | 16.1 秒 | 17.1 MB | 2670 | 98.4 | 38.8 GB |
| | mmap | 35.5 秒 / 13448 MB | 16.2 秒 | 23.0 MB | 2634 | 100.5 | 39.7 GB |

rowcache 16M 长输入那一行，3 次读取分别是 25、286 和 13 MB。磁盘计数器统计的是整个系统，286 MB 那一次可能包含了系统后台的读取。

## 方法与边界

- 磁盘读取量取自 Windows `PhysicalDisk(_Total)` 累计原始计数器在请求前后的差值。mmap 缺页产生的读取能被统计到，代价是会混入整个系统的读取。
- 每次请求开头都加了不同的 run id，防止 prompt cache 复用前缀。但 3 次测量请求的正文相同，所以"预热后"指的是 PLE 行缓存已经热了，这代表重复文本的情况，不代表全新文本。
- token 和速度取自引擎日志。`--ple-io ram` 需要锁定 28.8 GB 内存，而加载后可用内存只有约 17 GB，所以没有测。
- 运行明细只保存在 `.tmp/validation-2b/s6*`。
