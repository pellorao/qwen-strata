# 206584 档长上下文正确性验证（rtx3080ti / IQ3_XXS，2026-10-24）

## 结论

- 原目的（验证 206584 档 150000 阈值下的正确性）没有达成：150K 基线本身就没通过，所以不写"150K 以上可用"。
- 事先写定的两条判读规则都没有触发：错误不随长度单调增加（100K、160K、175K 每点 3/3 无检索错误，125K、150K、156K 出错），100K 也没有出错。但在 156584 档日常会遇到的长度（≤约 104K）内没有错误，错误只出现在 206584 独有的 125–156K。
- 每个长度是不同的提示（记录数、前缀不同），长度与内容混杂；同一长度的 3 个实例是同一提示的 greedy 重复，接近 1 个独立样本。所以"不随长度单调"只是弱证据，不能读成"与长度无关"。
- 错误几乎集中在一处：9 个检索错误里有 8 个是 cached-update 的同一行。R00583 答成 35（期望 23），用的是同 label 记录 R01583 的 capacity 112、reserve 9，加上 R00583 自己更新后的 used 68。这是字段级拼接，比整条记录认错更隐蔽。这一行在 125K、150K、156K 几乎每个实例都错，在 100K、160K、175K 一次也没错。另一个是 156K r3 的 R01729，同样混成同 label 记录。
- 其余全对：所有长度上，initial-extraction 和 cached-calculation 18/18 实例全对，包括 14 对同 label 记录和 R00999/R01999。kv-resident-long 在 200K 出现的 R00999→R01999 混淆，在 ≤175K 没有出现。
- 性质：greedy 解码下，这是负载里一个对上下文内容敏感、近确定性的混淆点（156K r1 没错，有少量非确定性）；各长度的记录前缀不同，同一行有时触发、有时不触发。混杂因素分不开：成对记录 ID 只差一位（R00583/R01583），label 又相同。
- 适用范围：每点 3 个实例是同一提示的重复，排除系统性断崖的能力也有限；只有这一种合成检索负载，不代表真实 agent 会话；未测超过 175K。
- 对窗口维的含义见「双方意见」。

## 各点判定

判据（事先写定）：每点 3/3 实例无检索错误、无缺行，且算术错行 ≤ max(基线算术错行, 1) = 1。

| 点（首请求提示 token） | 判定 | 检索错误（实例数） | 算术错行 |
|---|---|---|---|
| 100K（100288） | 通过 | 0 | 0 |
| 125K（125314） | 失败 | 3（3/3） | 0 |
| 150K 基线（150254） | 失败 | 3（3/3） | 0 |
| 156K（156284） | 失败 | 3（2/3） | 1 |
| 160K（160317） | 通过 | 0 | 1 |
| 175K（175320） | 通过 | 0 | 0 |

错行明细（全部在 cached-update）：

- R00583，期望 23、答 35，同 label：125K r1–r3、150K r1–r3、156K r2、r3。
- R01729，期望 84、答 49，同 label：156K r3。
- 算术错：156K r3 的 R01437（期望 95、答 94）；160K r1 的 R01729（期望 84、答 75，任何同 label 记录都解释不了）。

- 内部段为 4 的实例：cached-update 用满 8192 推理预算后引擎续生成一次，最后都以 stop 结束，没有出现"更新未生效"。

## 负载修正（`benchmarks/resource-calibration-v1/workload.py` 新增 `build(n, version=2)`，v1 逐字节不变）

1. 同名记录对：28 个 ID 改为 14 对同 label 记录（i 与 i+1000；第 0 对是 R00999/R01999）；每对 capacity 必然不同，答案能区分。每个用例带上同 label 记录会给出的行，cached-update 另带"更新未生效"的行。
2. 不再截断：cached-update 和 cached-calculation 的 available 不再截到 0，截断会掩盖检索错误。
3. 工具：`tools/tuning/resource_calibration.py` 新增逐行分类（ok／missing／same-label／stale-update／other），备选行 SHA 绑进计划；租约被占时轮询等待，不抢占。

## 与 kv-resident-long 的差异

Strata 0.2.2（引擎 0.1.47，旧为 0.1.42）；各点都用窗口 206584（旧为按长度取最小档）；负载 v2。请求参数和提示 SHA 相同。结果与旧报告不可比。

## 偏离

1. 计划写"基线失败就停、不补点"；实际照跑了已冻结的 156K/160K/175K，判据不变。
2. 100K/125K 是看到基线失败后，按窗口维第二次独立审查的意见加的；判读规则在运行前写进运行计划：混淆随长度增多，另列部署决定；100K 同样出错，维持 206584。

## 双方意见

1. **Main**：倾向维持 206584 并登记为最终决定，理由是错误不随长度单调、集中在同一行。
2. **独立审查（Opus high，只读）**：先维持 206584，但暂不登记为最终决定，先补测。
   - 不建议降阈值：要避开 125K 的失败点，阈值得降到约 100K，就和 156584 一样了。
   - 补测：负载加 version 3，引入内容种子（打乱记录顺序、改变成对偏移和 ID 差位），让每个种子是不同的提示；100K、150K 各 6 个种子，每个 1 个实例，另加 190K 2 个种子，覆盖日常 160–190K 的空白区。约 1 小时 GPU。
   - 事先写定停止条件：100K 出现任何同 label 错误，维持 206584 并登记；100K 0/6 而 150K ≥3/6，算与长度有关，另列部署决定（倾向改回 156584）；介于两者之间，按 206584 登记并注明残留风险；190K 系统性出错，单列为部署隐患。
   - 其他风险：比较两档时要把"检索混淆"和 156584 多压缩造成的"B 类记录丢失"放在同一张账上；部分实例出现 sw_thermal，长跑时留意降速。
3. **Main 采纳审查意见**，并按它改了本报告的措辞（原目的未达成、判读规则未触发、同一提示的重复不是独立样本、"近确定性"、字段级拼接）。补测改了测量设计，按硬约束 1 先列状态页 `decide` 由用户定。

## 未验证
