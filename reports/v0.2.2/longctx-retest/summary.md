# 206584 档长上下文记忆重测（负载 v3，rtx3080ti / IQ3_XXS，2026-10-24）

## 结论

- 分数拉开了：各长度得分 64.6–74.6，互不相同，没有挤在顶端（上一轮 v2 几乎全对）。
- 未见断崖，但 175K 以上的 latest 错和 other 错偏多（other 错题：100K 7、125K 4、175K 15、190K 11；latest 按题汇总，100K/125K 对 53.5%、≥150K 对 46.2%，差约 7 个百分点、约 1.8 倍标准误）。不能读成"与长度无关"。各长度区间大幅重叠，排名不单调（190K 高于 175K），对长度的线性斜率为每 +10K −0.55 分（95% 区间 ±1.18）。种子之间的差别（100K 三个种子 61.3–83.8）大于长度之间的差别，其中一部分来自题型配比：各实例的 latest 题数在 26–51 之间，100K r2 得 83.8 分，只有 29 道 latest。下一次应固定每实例的题型数，或主表改用按题型分层的分数。
- latest 只对约一半是模型层面的弱点，与窗口档无关：100K 也只对约 52%，而 156584 档的日常请求上限就在约 104K。在 agent 会话里，这对应多次修改过的文件或配置，模型容易报旧值。
- 难度几乎全来自"多次更新后答最新值"（latest）：这类题只对 49.2%，错题里 82% 是答成了较早的更新值（stale）；其余六种题型合计约 92%。去掉 latest 后各长度在 89.5–95.2 之间，有弱的下降趋势（100K/125K 约 94–95，175K 约 89.5），同样不显著。
- 对窗口维：没有给出"150K 以上更差"的证据，也不能排除轻度退化；当前样本只能排除断崖。决定见「双方意见」。
- 适用范围：只用窗口 206584，没有 156584 档对照；每长度 3 个种子；一种合成记忆负载；Strata 0.2.2（引擎 0.1.47）。
- 设计：[benchmarks/resource-calibration-v1/iq3_xxs-longctx-retest-2026-10-24/](../../../benchmarks/resource-calibration-v1/iq3_xxs-longctx-retest-2026-10-24/)；逐题数据在同目录 [summary.json](summary.json)（含题型、位置、是否涉及孪生记录、错题类别）。

## 用户要求与实际做法

用户（2026-10-24 04:5x–05:2x）的要求：分数粒度细、各长度尽量拉开；主要考上下文记忆，允许简单组合；题型和格式多样，体现泛化能力；增加题目数。

- 已做到：分数拉开；题型 7 种、记录格式 5 种、更新写法 5 种；每个请求一批 8 题，一次答完。
- 没做到：每份上下文的题目数要求约为旧负载的 30 倍，实际每实例 80 题，和旧负载（每实例 84 行）差不多。原因是 Main 给 worker 定的规则是"总时长 5 小时以内，时间不够就减题、不减种子"，按实测耗时（每批 8 题约 75 秒）反推只能放 80 题。
- 难度分布偏斜：除 latest 外的题型接近满分，"题型多样"主要体现在按题型拆分的报告里，对总分的贡献小。

## 负载 v3（`benchmarks/resource-calibration-v1/workload.py`，v1/v2 逐字节不变）

- 由内容种子生成，不同种子是不同的提示。
- 记录格式：JSON、表格单元格、key=value、散文句、日志行；字段名随格式变。
- 更新写法：JSON、`UPDATE` 行、`Correction:` 句、日志 `set`，以及按 label+region 指代记录的更新。
- 孪生记录：label 相同、ID 只差一位数字，region 和数值不同。
- 题型：retrieve（原样取回）、latest（多次更新后的最新值）、join（两处拼接）、jump（按 link 字段跳到另一条记录）、compare（两值比较）、arith（只有加减，占少数）、find（按 label+region 找记录）。
- 请求：同一前缀 + 一批 8 题，各自独立对话，前缀不变、问答不累积；会话缓存命中正常（每实例 reused 1.9M–3.6M token）。
- 答案为 JSON 数组，一律字符串；数字有没有引号视为相同（这是格式，不是记忆）。
- 单测含一个独立求解器：解析全部记录和更新格式，按题面求答案，与负载期望逐题比对。全量 738 项通过。
