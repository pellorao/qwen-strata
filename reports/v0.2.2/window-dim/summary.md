# 窗口维：206584 对 156584（本机 / IQ3_XXS，2026-10-24）

## 结论

- 这套负载测不出两档在模型侧的差别。依赖模型的部分在两档、两个 harness 下全部答对：原文题共 133 道，压缩后要问的 K、U 类事实也全对，每个压缩摘要都保留了全部 16 个 K 值和待问 U 的最新值。所以不能写成"判定等效"，只能说负载对模型侧不敏感、区分不了两档。
- 按用户定的平手规则看总工作时间（含压缩），206584 更短：Codex 503 秒对 697 秒，Claude Code 261 秒对 451 秒。每档 n=1，但两个 harness 方向一致，差距可以由压缩次数解释（Codex 2 次对 4 次，Claude Code 1 次对 3 次；每次压缩都要全量 prefill，再生成摘要）。M（机械的原文保留比例）同样偏向 206584，单列在下面，不作依据。
- 窗口维以试跑收尾，暂时维持 206584。这一决定经两次独立审查、由 Main 采纳，待用户复核。最终决定要等「206584 档 150K 以上长上下文验证」的 100K、125K 对照结果出来，届时再把"维持 206584"登记到 README。
- 适用范围：
  - Codex 0.164.0，另跑了 Claude Code 2.1.309。
  - 负载 window-v2-seed1，每档、每个 harness 各 1 个实例。
  - 最大请求约 156K。
  - 不覆盖同 label 混淆，也不覆盖日常可能出现的 160–190K 请求。
- 设计见 [benchmarks/window-load-v1/design.md](../../../benchmarks/window-load-v1/design.md)。

## 分类工具修正（2a5d510）

- **问题**：Codex 压缩时，会把最老的那条保留用户消息从中间截短，只留首尾，所以批次标签还在。206584 rollout 的第 17 批和第 34 批都被截到约 2.1–2.2K 字符。旧工具按整条消息判断"原文仍在"，把 Q34（HM-1269）误记成了原文题，它也就是 C1 唯一的那道错题。
- **修正**：改为按记录判断。在提问前那个请求实际携带的原文里，要能找到该记录及其当前值所在的行（整词匹配；K 类找 `= 值`，其他类找 `字段=值`）。Codex 侧按 `replacement_history` 重建文本，Claude Code 侧按 `compact_boundary` 之后剩下的原文判断。
- **重算后**：4 个实例的 C1 全对，Q34 改归 C2-B。E 不变，因为分类不影响分数。

- 所有错题都是被压缩掉的 B 类，所以 E = M + 压缩后 K/U 题的占比。两档 E 的差异全部来自机械成分：B 记录被压缩后丢失，这是工程压缩提示 "Omit bulk repetitive rows" 预期的结果。
- 两档的工作时间差由压缩次数结构性决定，压缩请求的全量 prefill 成本已计入工作时间。

## 越线记录（决定 A：超过已验证的 151K 只记录，不作废）

- Codex 206584：越线请求 4 个，即 2 个 ACK 和 2 个压缩请求，最大 156,029；问答请求都不超过 149.4K。越线只能通过压缩摘要影响 C2，而压缩后 K/U 全对。
- Claude 206584：只有 1 个压缩请求越线（151,547，pre_tokens 152,948）。
- 156584 的两个实例都没有越线。
- 原因：Codex 0.164.0 在回合结束后按真实 usage 判断是否压缩，所以最大请求约等于阈值加一个回合的增量。设计里"206584 约在 122K 压缩"的前提，来自旧版 Codex 的本地估算，已经不成立。
- 部署侧的隐患单独登记：日常用 206584 时请求可达 160–190K，而 200K 已知有系统性检索错误。这一点由长上下文验证覆盖。

## 双方意见

1. **151K 越线（02:3x，独立审查 Opus high）**
   - Main 原先建议先补测 156–160K 的长上下文验证，再测窗口维（B）。
   - 审查选 A：请求长度是处理条件造成的结果，按它作废实例，等于以处理之后的变量为条件；越线的请求都不是问答。B 不改变窗口维的任何分数，改为单独的待办。
   - 另外补充 4 项：按实测压缩点复核检查点；做零成本的摘要保留诊断；"C2 饱和"只按 K、U 判断；压缩成本计入 C3。
   - Main 采纳。
2. **试跑结论（03:2x，独立审查 Opus high）**
   - Main 原先建议补测（Codex 每档再跑 2 个）。
   - 审查选 ②，以试跑收尾。理由：greedy 加冻结负载，重复实例几乎是确定性的，SE 会小得不真实。
   - 审查还纠正了 C1 那道错题实为工具误分，要求结论不写"判定等效"、写明适用范围，并要求长上下文验证加 100K、125K 两个对照点，各 3 个实例。判读：混淆随长度增多，才算对 206584 不利的证据，那时另列部署决定；100K 同样出错，就维持 206584。
   - Main 采纳。
- 两次决定都是用户 30 分钟内没有答复后按 AGENTS.md 硬约束 1 做出的，待用户复核。
