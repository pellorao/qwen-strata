# Code Spec v2 测量报告（原定样本：Opus medium ×3、IQ3_XXS ×5；加测至 10 次；本机，Strata v0.1.42，Codex 0.162.0）

## 结论

**v2 已冻结**：
- 经过两轮"全新 Opus-high 盲答 + 两阶段审计"，第 2 轮无阻断、无主要问题。冻结提交 6f60c8c，code-spec-reviewer 修订号 12。
- 改了三处：
  - 访问窗口的结束边界改为半开区间；
  - spec:42 写明取消状态的要求；
  - 答案键补了 4 个直接证据关联点。
- 详见 `benchmarks/reviewer-suite-v1/code-spec-v2.md`。

**场景对两个模型没有区分度**：
- 21 个问题用例全部被检出：Opus 3/3，Q3 5/5（加测后 10/10）。双方都没有 0 命中的用例。
- 原定样本均值 Q3 0.815，Opus 0.799，Q3 略高。相对口径 Q3 / Opus = **1.02**。
- 分差全部来自两处，与发现能力无关：
  - 证据定位精度：每个用例只拿到 0.8–0.9；
  - 格式和证据诊断带来的 ×0.9 罚分。

**按 Spec v3 的四条"一切正常"判据**：

| 判据 | 结果 | 依据 |
|---|---|---|
| 1. Opus 明显高于 Q3 | **不成立** | Q3 0.815 ≥ Opus 0.799 |
| 2. 双方 0 命中的用例都有效 | 成立 | 没有这样的用例 |
| 3. Q3 会话有效 | 成立 | 10 个会话全部有效 |
| 4. 评分可复现 | 成立 | 盲裁 A1 与全量独立复裁 A2 一致 265/265；`score-completed` 重跑结果逐字节一致 |

**调参判据**（两种口径的 SD 都 ≤ 0.068）按数字成立，但不建议据此用于调参：

| 样本 | 扣罚后 SD | 扣罚前 SD |
|---|---|---|

| 10 次 | 0.048 | 0.040 |

不建议的原因：检出率已经饱和，组内波动主要来自格式罚分和证据精度。用这个场景调参，调到的是"不要把时刻写进反引号"这类格式行为，而不是审查能力。

**建议（worker 意见，用途待独立意见后定）**：
- Code Spec v2 可以作为"基础对照规范"能力的通过性检查，Q3 在这一项上与 Opus 持平。
- 它不能作为能力区分或调参用的场景。
- 要提高区分度，需要另做更难的版本，例如跨文件或隐含要求的缺陷。这超出本次"修到无问题"的范围。

## 偏离清单（相对"修到无问题"目标与 ARW 原版）

1. **区分度饱和**（最重要）：所有用例都是单文件内 spec 原句与实现的直接对照，Opus medium 和 Q3 都能全部检出，分数只反映证据精度和格式。这不是答案键错误，审计已确认键准确，但它让 Code Spec 失去了能力区分作用。
2. **v2 残余次要项**（未改，记在变更说明的"残余"一节）：
   - spec:56 拆成两个用例：合成一条报告时原子性约 0.667，本次 P20/P21 实测约 0.65。
   - spec:6 的 "after normalization" 没有定义规范化方式。
   - spec:5 没说查找房间时是否用 trim 后的 roomId。
   - 改写后的 spec:42 后半句有一定提示性。
   - "进入不查 confirmed"用例的关联点只有 `access-policy.mjs:7` 与 `reservation-service.mjs:79`。
3. **ARW 格式修正关口不接受只涉及短路径的修复**：
   - 本工程的 format-normalized-scoring 补丁只认解析诊断。只修了简写证据路径的报告会被拒，报 "Original report has no verified representation error"。
   - 这类报告改按原报告评分，结果与 ARW 原版相同。
   - 本次只影响 Opus 第 1 次：它仍记 evidence-invalid 并 ×0.9。
4. **`repair_reviewer_report` 工具缺陷**：
   - 根目录文件 `governing-spec.md` 的短名与自身相同，触发断言 "locator change is not a directory prefix"。
   - 本次测量用包装脚本绕过：只把路径含 `/` 的来源交给修复。
   - 工具已在 3bf0afa 修复（根目录来源的定位视为已完整），测量后提交，不影响本次分数。
5. **反引号里的时刻被 ARW 当作证据定位**：
   - Q3 的 evidence-invalid 全部来自这一点。
   - 按 ARW 原版规则照罚，没有修复，因为它不在修复工具能修的三类错误之内。
   - 已登记为 ARW 上游问题第 4 条（`docs/arw-upstream-issues.md`）。
6. **规则冲突**（各 Code Spec 实例共有）：
   - `reviewer.md` 的 Communication 一节要求 send_message 和运行标识；
   - Role Inputs 要求治理副本的 SHA-256，而交接不提供。
   - 测量说明已写明不需要运行标识，双方报告都没有因此失分。
7. **Opus 参照的局限**：
   - Opus 用的是 medium，在 Claude Code 中按真实交接盲答，未接入本工程提示。
   - `reviewer.md` 的 Independent runtime 一节说 Claude Code 原生 Reviewer 的执行已暂停。
