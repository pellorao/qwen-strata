# 本机 IQ3_XXS 长上下文 KV 驻留：20480 / 32768 × 64K/100K/150K/200K

**结论**（自主模式第 3 项，2026-10-12，Main 与独立复核一致）：

- **kv-resident 各档都保持 20480**，不按档位绑定。配置中的这个值不改。
- **206584 / 150000 发布为可选档位**，默认档仍为 156584。验证边界：提示约 151K token 以内。200K 的提示也能放进这个窗口，但在 200K 长度上出现了系统性错误。
- **256584 不发布**。引擎在该窗口下运行稳定，但 6 个实例都在同一条记录上答错。

**适用范围**：本机、IQ3_XXS、Strata v0.1.42、`--kv int8`，合成的三请求长上下文检索负载。不代表 ARW 等真实会话在长上下文下的质量。

## 条件

**固定条件**：当晚的默认部署，参数如下：

- 不传 `--pcie-frac`
- `--ple-io direct`
- `--vram-reserve-mib 512`
- `--spec 4`、`--spec-min-p 0.9`
- 采样 0/1/20，请求自带 temperature 0 / top_p 1 / top_k 20
- CPU 辅助 auto
- `STRATA_ADAPT_LAG 2`

**变量**：

- 条件只改 `--kv-resident`。
- 窗口经 `--max-context` 传入，取该长度所属的最小档位：64K 和 100K 用 156584，150K 用 206584，200K 用 256584。

**负载**：合成记录表，记录数分别为 1529 / 2400 / 3609 / 4818。每个实例发 3 个逻辑请求：

1. initial-extraction
2. cached-calculation
3. cached-update

每个请求期望 28 行。三个请求合计的未缓存输入分别为 94354、104707、157186、209656 token。

**执行**：

- 每个长度内顺序为 A B B A A B（A = 20480），每个实例冷启动。
- 运行时间 2026-10-12 04:00–05:19。
- 冻结计划：[kv-long/](../../../../benchmarks/resource-calibration-v1/iq3_xxs-night-2026-10-12/kv-long/)。
- 开跑前重绑了两项，见提交 70dff0c：
  - `measurement_host.py` 的 SHA。52cb873 只增加了服务日志读取，接口不变。
  - 专家档案 SHA。已核对，与安装目录一致。

**生效核对**：24 个实例的实际引擎参数和引擎 KV 信息都是条件值（`KV streaming: <kv-resident> of <max-context> cells`）。

## 分析

**kv-resident 两个值没有可用的差别**：

- 64K、100K、200K 三个长度上，两个条件的引擎输出差都在单实例波动之内。例如 64K 单实例的范围是 116.5–119.9。
- 150K 有可分辨的差：20480 为 115.3，32768 为 113.6，两组单实例值基本不重叠。机制上说得通：20480 多出 68 个专家槽位（2213 对 2145）。
- 32768 在任何长度上都不更快，却稳定少约 68 个专家槽位，所以没有理由按档位绑定。
- 上游对 64K 以上推荐 32768，但在本机和本量化上没有观察到收益。

**150K（206584）运行稳定**：

- 9 个请求组中只有 1 行错值：kv32768-150k-r1 的 cached-update，R00703 的 available 期望 90，实际得 43。
- 这一行是算术失误（125−33−2），不是检索错误。
- 输出是严格 JSON，结果完整，以 stop 结束。

**200K（256584）是长程检索精度问题**：

- 6 个实例在两个条件下的 initial-extraction 都把 R00999 答成了 R01999 的值：capacity 105、used 0、reserve 2，正确值是 92、50、1。
- 两条记录的 label 都是 parcel-969（label 每 1000 条循环一次）。
- 两个条件给出的错误值逐字相同。
- 100K 和 150K 的负载里同样有 R01999，R00999 没有答错。
- 基础设施可以排除：全部以 stop 结束，每次都返回 28 行，输入在窗口之内，没有 OOM。
- 不能单独归咎于模型权重：全部实例都使用 `--kv int8`，没有做非 int8 KV 的对照，模型原生上下文长度也没有核实。

## 双方意见

**Main（worker）**：

- 各档维持 20480，不做档位绑定。
- 206584 可以作为可选档位。
- 256584 引擎可用，但精度下降，建议暂不发布。

**独立复核**（Opus，effort high，只给事实文件和原始明细）：

- 按行计分，两个条件都在 0.08 以内，于是按引擎输出比较。只有 150K 可分辨，并且偏向 20480，所以维持 20480、不绑定。
- 206584 可以发布，但要注明"已验证约 151K 以内"。
- 256584 不发布。R00999→R01999 的一致性错误是长程检索精度问题，基础设施已排除。但所有实例都用 int8 KV，要区分原因需要另做对照。

**采纳**：上述三项双方一致，已执行。

## 复核提出的疑点（记录，未影响结论）

- **cached-update 在 200K 掩盖了错误**：
  - R00999 的 used 被更新为 111 之后，正确值和错误值算出的结果都截到 0。
  - 所以该请求"通过"不能证明检索正确，负载设计在长长度上会漏检。
- **kv20480-200k-r3 打满了 8192 推理预算**：
  - 引擎记录了第 4 个内部阶段（续生成），R00888 的更新没有生效：期望 0，得到 82，即更新前的值。
  - 这属于预算或续生成问题，不是检索问题。
- **缓存复用按 16384 粒度向下取整**：
  - 64K 后续请求只复用了 49152 个缓存 token，每次约有 15K 需要重新 prefill。其他长度只损失 2–4K。
  - 各长度每次的复用量分别是 49152、98304、147456、196608，都是 16384 的整数倍。
  - 这会拉低 64K 的任务速率，已记入 [Strata 上游问题](../../../../docs/strata-upstream-issues.md) 待查。
- **工作秒差异主要来自输出长度**：例如 64K 的 122.9 对 135.6 秒，对应输出 10089 对 11619 token，不是条件差异。
- **greedy 下输出长度仍有浮动**：同条件的输出 token 在 8.7K–15.1K 之间变化，说明各实例并非逐 token 确定。
