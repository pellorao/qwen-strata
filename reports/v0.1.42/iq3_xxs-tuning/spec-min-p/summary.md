# rtx3080ti IQ3_XXS 第 8 维：spec-min-p（0.3 / 0.5 / 0.7 / 0.9）

结论：**采用 0.9**（原默认 0.50）。spec-min-p 是不影响输出的参数，按引擎输出 tok/s 选择，分数只作异常检测（用户 2026-10-12，[测量规则 · 评分口径](../../../../.claude/rules/measurement.md#评分口径)）。依据：Strata DETAILS.md，它只决定草稿层多有把握才继续猜；greedy 下草稿只在与模型所选 token 一致时保留，输出逐字节相同。0.9 引擎解码最快（104.0 tok/s，0.5 为 102.5，+1.5%，0.3 为 100.3）。现行分数 0.705 / 0.809 / 0.800 / 0.837（顶层 `[a,b]` 按 ARW 定义是两行；0.3 低分来自一个实例的报告写法，不是程序错误），不参与选择。Main 与独立复核意见一致，用户 2026-10-11 确认保持 0.9；已于 2026-10-11 写入 rtx3080ti 的 `model_overrides.IQ3_XXS`（`"spec-min-p": 0.9`）并部署。

**口径变更**：本维初次按旧口径（格式失误照常计分）评分，0.3 得分 0.705，因第 1 次 0.472 出组。口径变更后该次在独立副本上把 45 处 `[a,b]` 读作区间，重评为 0.815，0.3 回到比较组；胜者不变。**边界**：该报告裸 `[a,b]` 占区间写法的比例为 0.82（45 对 10 处嵌套区间），紧贴 0.8 阈值；阈值若取 0.85，这次就不会归一，0.3 会再次出组，但胜者仍为 0.9。

速度优势很小，逐次范围互相重叠（0.9：105.4 / 103.6 / 102.9；0.7：102.2 / 104.3 / 103.2；0.5：102.3 / 102.2 / 103.0），每值只有 3 次，0.9 对 0.7 在统计上不显著。采用依据是**单调趋势加机制**，不是显著性：阈值从 0.3 升到 0.9，草稿接受率 72.6% → 92.4%，每个输出 token 提议的草稿数 0.963 → 0.700，被拒废稿减少，解码速度 100.3 → 104.0 单调上升。

**证据定位口径（2026-10-12）**：用户确定证据写法只按冻结 ARW 定义解释（`commit-audit-reviewer.md`：`lines` 元素为正整数或 `[起,止]`，顶层 `[a,b]` 是两行），调参和 benchmark 相同，取消上段的"裸区间对读作区间"修复。0.3 第 1 次按原件重评：候选与原裁决逐字相同（88 个，无新增或变化），扣罚前分 0.472，0.3 均值 0.705，出组；胜者仍为 0.9，结论不变。上段的 0.815 / 0.819 已失效，只作历史记录。

**评分口径复核（2026-10-12）**：按用户确定的调参口径（[测量规则 · 评分口径](../../../../.claude/rules/measurement.md#评分口径)），调参取 ARW 扣罚前分。本维每个实例的分数都等于由 problemDetectionRate、cleanAcceptanceRate 按 ARW F2 公式算出的扣罚前分（逐实例核对，差 <0.0006），即格式归一后没有残留报告诊断、没有 ×0.9 罚分，分数和结论都不变。

适用范围与回退：仅 rtx3080ti、IQ3_XXS、Strata v0.1.42、Codex high、ARW Commit Audit 一种场景。0.95 / 1.0 未测，更高阈值对长输出或代码生成的影响也未验证。后续同类运行解码稳定低于约 102 tok/s，或出现与投机解码相关的输出异常，就退回 0.5。
