# Spec Readiness v4 测量报告

## 测量条件

- **场景版本**：v4 夹具（修订号 43，冻结提交 61287ee）+ v4.1 答案键（8510561）。共 21 个问题用例、43 个 clean 用例。
- **样本**：原定 Opus medium ×3、IQ3_XXS ×5，另外空闲时加测到 Q3 ×10。
- **软件**：主机 rtx3080ti，Strata v0.1.42，Codex 0.162.0。
- **主机**：BIOS 1.C0（微码 0x137），内存 XMP 6600，CPU 功耗档 Intel Default Settings。
- **完整数据**：[summary.json](summary.json)。
- **评分规则**：本报告的分数是升级前规则（证据定位 F3）的值，**没有重算**。2026-10-14 评分规则升级为证据定位 F2（计分补丁 `benchmarks/reviewer-suite-v1/arw-patches/scoring-f2.patch`），2026-10-15 又加入两类计分（A 类判断题按对错 ±1，与其余用例的 F2 加权合成），改变总分的合成方式。这批运行的原始明细（运行目录、报告、裁决）已经删除，summary.json 只保存逐用例的合成分（0.4 结果 + 0.4 证据 + 0.2 原子性），从中分离不出证据的覆盖率和精确率，也没有逐条发现的记录，新规则下的分数无法唯一推出，所以不做估算。本报告的分数只能与升级前的结果比较。v4.1 在新规则下的基线由 v0.1.44.1 重测提供。

## 结论

- **改了什么**：
  - v4 修改了 v3 两个双 0 用例的夹具，即 INTERFACES#5 和 SEAMS#1，并入 v3.1 的答案键。经过一轮两阶段审计，没有阻断项，也没有主要问题。见 [v4 变更说明](../../../benchmarks/reviewer-suite-v1/spec-readiness-v4.md)。
  - v4.1 只改答案键：删除 MD-SEAMS-ADAPTERS#1，因为它的答案不成立，见下文。删除后仍满足 ARW 的最低要求：问题用例和 clean 用例各至少 20 个（`MINIMUM_CASE_COUNT = 20`）。所以没有补充用例。
- **四条"一切正常"判据（原定样本，v4.1 键）全部成立**：
  1. **Opus 明显高于 Q3**：Opus 0.774，Q3 0.593，差 0.181，约为 Q3 组内 SD 0.036 的 5 倍。
  2. **没有审计认为可疑的双 0 用例**：剩下唯一的双 0 用例是 MD-RATIONALE#3。缺陷确实存在，漏检是智力原因，按用户规则不改。
  3. **会话全部有效**：Q3 原定 5 次、加测 5 次，共 20 个会话。
  4. **评分可复现**：原定样本由两名裁决者独立盲裁，147/147 一致。加测采用增量盲裁，12 个锚点全部一致。每批带裁决评分两次，输出逐字节一致。
- **相对口径**：
  - 原定样本 Q3 / Opus = **0.766**；Q3 ×10 时为 0.780。
  - 用 v4 原答案键算是 0.569 / 0.744 = 0.765。删除用例后两边的召回率同幅上升，比值基本不变。
- **INTERFACES#5 修好了**：v3 时两边都是 0 命中。v4 中 Opus 命中 1/3，Q3 ×10 命中 2/10。
- **不用于调参**：调参要求 10 次的组内 SD 在扣罚后和扣罚前都 ≤ 0.068。
  - Q3 ×10 实测：扣罚后 SD **0.073**，超过标准；扣罚前 0.062，在标准内。
  - 原定 5 次的 SD 只有 0.036，但加测 5 次的波动很大（0.507～0.739，SD 0.102）。
  - 所以 v4 只用于 ARW 能力验证和 benchmark。
- **速度不能和 v3 直接比较**：
  - v4 的 Q3 引擎输出 86.8～92.0 tok/s，v3 是 98.0～102.3 tok/s，低约 12%。
  - GPU 利用率、SM 频率和 strata.exe 的 CPU 占用都和 v3 相当。下降来自 CPU 频率：刷 BIOS 后功耗档是 Intel Default Settings，长期功耗上限 PL1 为 65 W。运行期间实测全核平均约 3.3 GHz，而 Strata 有一部分计算由 CPU 完成。
  - 用户决定在重启观察期内保持这一档。

## 双 0 用例的处理

按用户规则处理：先确认答案键里的缺陷是否成立；成立了，再分析为什么没有命中，只修非智力原因。

### MD-SEAMS-ADAPTERS#1：答案不成立，v4.1 删除

- **v4 改动已生效但仍无人命中**：`prec:59` 现在已经写明失败形状是 Seam 的返回值，但 8 份 AP 回答里，没有一条 finding 提到"成功时的 recoveryState 形状"。
- **答案为什么不成立**：`prec:57` 写明 Module 用输入的 priorTrackedState 和原始 failure code 形成成功结果。成功时 Module 用不到 recoveryState 的字段，所以"成功语义已经足够"是站得住的读法。
- **审计佐证**：v4 审计阶段 1 由全新的 Opus-high 执行，要求穷尽查找缺陷。它的原文是："prec:57 成功语义无精确形状——判'语义已足够，不报'"。
- **决定**：用户 2026-10-13 决定删除这个用例，保持 20/20 下限。删除后不需要补充用例，所以也不存在补用例带来的选择偏差，不需要敏感性数字。
- **核查过的另一条线索**：Q3 曾报过"`restore` 要求报告 baselineStatus 但输入不带 baseline"。核查后不是缺陷：失败时这个值由 Seam 返回，成功时是常量 "removed"。

### MD-RATIONALE#3：缺陷有效，属于智力因素

候选说的都是"边界缺少替代方案"，那属于 MR#1，所以判 not-matched。v4 审计阶段 1 也没有列出这一项。不再修改。

## 裁决与可复现

- **原定样本**：
  - 共 147 个候选：Opus 58、批 A 54、批 B 35。

    - INTERFACES#6：4 条只说出 source 那一半，按 brief 判 matched。
