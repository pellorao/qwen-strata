# Code Spec 阅读量 rv3 测量报告（IQ3_XXS ×3+2；Opus-high ×1；rtx3080ti，Strata v0.1.44.1，Codex 0.162.0）

## 结论

**150K 档成立：Opus-high 在公式时限内命中 20/20，核心 31 个 clean 用例 0 失败（判据只用 Opus）。**

**Q3 的总命中没有下降，但原样题的命中下降了。**
- Q3 平均每次命中 14.8 题，v4.7 原定 5 次也是 14.8。ARW 均分 0.655（原定 3 次）和 0.632（全部 5 次）；v4.7 是 0.652（5 次）和 0.639（10 次），差别在一个 SD 以内。
- 能归因到"阅读量条件"的是原样 8 题。Q3 在这部分的命中率从 v4.7 的 88%（35/40）降到 73%（29/40）。
  - 下降集中在 4 题：durationUnits 0/5、snapEnd 3/5、accessUntilLarge 4/5、amenityDup 2/5。
  - 另外 4 题都是 5/5，和 v4.7 一样。
- 搬家 12 题的命中率从 65% 升到 75%。
  - 原因是 v4.7 里 Q3 几乎不中的 trimBoth（正则 g）和 buildingFromRoom，这次分别中了 5/5 和 4/5。
  - 这两题的位置、周围代码和 spec 写法都换了，所以只作参考，不和 v4.7 直接比较。
  - 两边相抵，总命中就持平了。
- 两道依赖 platform 的跨目录搬家题，holdUnits 和 confirmedAtKept，Q3 在 5 次里全部漏掉；Opus 两题都命中。

**Q3/Opus = 0.786（原定 3 次），全部 5 次为 0.758**；v4.7 是 0.744 和 0.729。比值升高不是因为 Q3 变好：这次 Opus 只跑了 1 次，又因为证据格式被罚 ×0.9，得分 0.834。按罚前 0.927 算，比值是 0.707 和 0.682。

**适用范围**：只适用于 rtx3080ti + IQ3_XXS + Strata v0.1.44.1 + Codex 0.162.0，推理强度 high，默认档 206584/150000。冻结版本为 code-spec-reviewer 修订号 34（3a2ad7c），设计说明见 `benchmarks/reviewer-suite-v1/code-spec-rv.md`。Opus 的结果可能利用了"每模块一个缺陷"的结构，见"会话分析"中的局限。

## 会话分析

只用动作序列、写入时刻和答案键的对应关系，不分析推理内容。

- **Opus**：
  - 先读 spec 全文，再读 platform 和 reservations，写下核心 7 条。
  - 之后每条命令都是"追加上一模块 1 条，再读下一模块"，按字母序读完 11 个干草堆模块。
  - 没有搜索，没有执行代码，也没有复查。
  - **每个干草堆模块恰好报 1 条**，全部命中。
- **Q3**：
  - 5 次都没有搜索，都是整模块 `git show` 读入，每次读一个或两个模块。
  - 只有 q3-4 用 node 执行代码，验证了 3 处行为。
  - 首批写入有早有晚，q3-3 和 q3-4 读完约一半模块就开始写。
- **Q3 稳定漏掉的题**：两道跨目录搬家题 holdUnits 和 confirmedAtKept，5/5 全漏；durationUnits 5/5 漏；activeDefault 4/5 漏。
- **会话检查**：5 个 Q3 会话都找到了 handoff，每个实例只有 1 个会话，0 次压缩。没有越界读取，也没有接触答案。被标记的项目：
  - q3-1 写错一次嵌套工作目录，命令失败后自己改正；
  - q3-4 尝试写 `/tmp`，被沙箱拒绝，没有重试；
  - 其余是误报：源码里本来就有 denied/permission 字样。

**局限：Opus 的结果可能利用了场景结构。**
- rv3 里每个干草堆模块恰好有 1 个缺陷。Opus 每个模块恰好报 1 条就转去下一个模块，这个节奏与结构完全吻合，可能是从"每模块一个缺陷"推断出了停止条件。
- 这样它不需要逐条核对全部条款，用时也会偏短。因此 20/20 可能高估了 Opus 在缺陷数未知时的表现，150K 档成立的结论带有这一保留。
- 对策已经定下：正式场景的缺陷全部打散（用户 2026-10-14），每个模块的缺陷数不再固定为 1。

## 混杂清单

与 v4.7 相比，下面几项同时变化，报告不把变化单独归给其中任何一项：
- (a) 时限：v4.7 没有时限，rv3 按公式给出时限。实际上没有实例被时限中断。
- (b) 交接模板：测量说明要求每找到一条发现就追加写入结果文件。
- (c) 核心缺陷数从 20 个降到 8 个。搬走的 12 题在核心原位改回了正确写法，原样题周围的局部上下文也随之变化。
- (d) 孪生写法已修复：干草堆里不再有与核心同形的写法，例如 `hasAmenities` 改为 `offersAll`，history 追加已删。
- (e) 版本：Strata 0.1.43.1 → 0.1.44.1，视为可比。
- (f) 跨模块结构：新增共用目录 `src/platform/`，7 个搬家缺陷的关键定义放在这里；干草堆 spec 的 50 条条款移入 5 个跨模块主题节。核心 12 节和 Conventions 与 v4.7 逐字相同。

## 偏离

- **T_Opus 取 2728 s**：用新测的 β 2.2447 加上冻结前登记的 G 51.8 tok/s。原因是子 agent 会话记录的流式 usage 只有占位值（`output_tokens: 8`），G 测不出。Opus 实际用时 4.1 分钟，远低于时限，所以这一取值不影响结论。
- **速度探针整批只测一次**：运行计划写的是每实例一次。改为整批测一次、5 次共用 T_Q3 = 879 s，是为了保证实例之间可比；β 测得 3.6590，与冻结值 3.6591 一致。
- **Opus 只跑 1 次**：按判据，命中 ≥19/20 即达标，不需要补到 ×3。

## 运行过程

- Q3 每个实例冷加载。开跑前核对了启动提示 1cae169a、角色绑定 5f9efc02，防循环段关闭；运行脚本逐实例核对安装版本 0.1.44.1。
- q3-1..3 在 16:10–16:36 运行，q3-4..5 在 16:36–16:57 运行；全部 rc=0，结束后租约 free。
- 盲裁分 3 批，每批用一个全新的 Opus-high agent，在只含候选池和说明的隔离目录中进行：opus 33 个候选、q3a 61 个、q3b 47 个。每批混入 v4.7 的同一组 12 个锚点，判定 36/36 一致。共判 matched 118、not-matched 23（含锚点）。

## 付费模型用量

- Opus-high 参考运行 1 次，速度探针 3 次。
- 盲裁 3 次。
- 冻结前独立意见 1 次、diff 审查 1 次、结构改造审查 2 次。

## 未完成或未验证

- Opus 只跑了 1 次，逐题命中没有方差估计；结果还可能利用了"每模块一个缺陷"的结构，见会话分析中的局限。
- Q3 只有 5 次。原样题的下降（88% → 73%）样本小，durationUnits、snapEnd 这类题每题只差几次命中。
- 预先登记的协变量（缺陷宿主文件首次读入时的上下文 token、阅读顺序、首次写入时间）只在会话分析中做了定性整理，没有逐题量化。
