# 防循环提醒真实试跑（3 次）

2026-10-11。rtx3080ti、Strata v0.1.41、Q2_0 / high、Codex 0.162.0。场景是冻结 ARW 760007c 的完整 Commit Audit，加上工程的 Codex 0.162 兼容补丁，3 个重复。服务端提醒（`src/loop_reminder.py`，机械规则 r6）默认开启。完整数据见 [summary.json](summary.json)。

## 结论

- **提醒能送达，判断可复现**：3 次运行共触发 7 次（3 / 3 / 1），都进入了转发给模型的 Responses 请求。用原生会话逐个前缀重放，时刻和措辞与线上完全一致。
- **7 次里 3 次部分有依据，4 次误报**：
  - **同一步内部（3 次）**：三次运行各有一步一次性做完整个需求审计，推理写到 32k–35k 字符，被推理预算截断（"I have thought about this long enough"）。这几步里确实反复回到少数几条需求，但主体是正常推进的审计。3 次同一步提醒都落在这种被截断的步骤上，规律是系统性的。
  - **写报告（2 次）**：根据上一步已有的判断编写报告记录，属于交付。
  - **路径相似（1 次）**：读取两个不同 issue 文件的命令被配成余弦 0.94。原因是工具参数里的 `workdir` 是同一条很长的场景路径，词项占了大半；文件名里的数字又不参与比较。
  - **真实修复（1 次）**：报告生成脚本的证据格式修正被配到前面的补丁。相似度同样主要来自路径。
- **没有确认的跨步循环**。只有上面 3 处同一步内部的反复斟酌。
- **提醒效果无法判断**：每次同一步提醒之后，模型都转入写报告，但被截断时它本来就准备收尾。没有提醒关闭的对照组，不能把后续行为归因于提醒。
- **耗时 7.0–7.8 分钟是本条件下的正常值**：3 次分别为 7.8、7.0、7.4 分钟，得分 0.798、0.586、0.713，批次 0.699，落在历史同场景的 0.67–0.82 之内。历史的 24–50 分钟是另一台主机、更早的版本和 medium 强度，不可直接比较。据此看，作废的第 1 次（8.2 分钟、0.472）的耗时并不异常，低分可能是运行间波动。是否恢复它的有效性由用户决定，本报告仍按作废处理。

## ARW 兼容补丁

Codex 0.162 把工作区根目录从每个 `turn_context.workspace_roots` 移到会话开头的 `session_meta.runtime_workspace_roots`。ARW 760007c 只读旧字段，原生事实核验因此判为 incomplete。

补丁只改一行：旧字段缺失时回退到新字段（[补丁](../../../benchmarks/reviewer-suite-v1/arw-patches/codex-0.162-workspace-roots.patch)）。冻结包和逐文件 SHA 不变，补丁登记在 manifest 的 `patches` 里，展开时打上，并校验打完后的 SHA。

解析器读取的其他字段在 0.162 中都还在。本批 3 次运行的 `unknownReasons` 均为空，完成状态都是 `ready`。ARW 状态库快照里的 `recoveryIncomplete` 为 true，与原生事实核验无关，未进一步排查。

## 会话检查

3 个原生会话的全部工具调用都在各自的场景根目录内。没有读取隐藏预期、准备记录或其他实例。实例 1 中出现的 `expected` 是模型自己核对需求覆盖时打印的变量名。实例 2 尝试写 `/tmp/build_review.py`，被沙箱拒绝（Read-only file system），随后改写到报告目录，沙箱行为符合预期。3 次都没有触发自动接续。
