# 上游推理重复检测在本工程语料上的覆盖（离线发现，无模型）

2026-10-10。上游 v0.1.41 内置一个可选的推理重复检测，本次把它原样用在本工程已完成标注的全集语料上，看它能发现多少已确认的循环、会在多少正常推理上触发。这次只做发现性统计，不按评分合同计算 F1，也没有运行或请求模型。完整数据见 [summary.json](summary.json)。

## 结论

- **上游检测只能覆盖本工程循环中很小的一部分，代替不了我们自己的防循环检测**：
  - 单次响应内部的推理循环共 81 组，触发 5 组（6%）。其中 70 组的推理长度达到了它的最低门槛（2,000 词），所以多数漏检不是因为文本太短。
  - 跨调用的推理循环共 54 组，一组也没有触发。它只看当前这一次回复内部的推理，看不到跨调用的重复。
  - 原因：本工程的循环大多是**换了措辞的反复重判**，而它要求同一段 12 词原文至少出现 3 次。上游 [#1753](https://github.com/Niko1221/Strata/issues/1753) 也报告了它漏检的另一种形态。
- **误触发**：2,074 条正常推理里有 3 条触发，都是模型在逐条起草 JSON 证据列表（反复出现 `"filepath": "src/dispatch/…"` 这种结构），并不是循环。
- **触发时机**：5 组中有 4 组到触发时，所标注的第三次重复已经写完，在生成过程中干预算偏晚。按本工程的评分口径，单响应循环只在一个检测点判断，时机不影响是否计为 TP，所以这一点只作参考。
- **对现有决定的影响**：
  - 日常配置不必开启 `reasoning_loop_recovery`。它默认关闭，我们也没有开。
  - 防循环检测的三条路线和 F1 = 1 门槛不变。
  - 上游的单 token 重复停止（`repeat_stop_tokens` 256）默认开启，本次没有评估，因为语料里没有保存 token id。

## 上游机制

| 项 | 值 |
|---|---|
| 来源 | v0.1.41 `serve/server.py` 的 `reasoning_repeat_coverage`，对应 [#728](https://github.com/Niko1221/Strata/issues/728) 和 #869，提交 `fb58e0d` |
| 开关 | `reasoning_loop_recovery`：`stop` 直接结束回复，`recover` 改用低强度指令继续。默认关闭 |
| 判定 | 最近 2,000 个词里，至少 25% 落在"最近 30,000 词内出现过至少 3 次的 12 词片段"中 |
| 检查频率 | 推理阶段每生成 512 个 token 检查一次 |

## 方法与边界

- **语料**：`benchmarks/loop-detection-v2` 的 `behavior.jsonl.gz` 和 `main-annotations.json`（标注第 2 版），SHA 记在 JSON 里。共 2,265 条推理记录，标注为 156 组循环。
- **喂入方式**：把每条推理记录当作一次逐渐变长的回复，每 2,048 个字符检查一次。这是对"每 512 token"的近似，因为当前环境没有分词器。函数逐字复制自上游。
- **标签的用法**：只在跑完后用来统计命中，检测过程中不读标签，不跳过，也不干预。
- **不适用于本次统计的循环**：单次响应内部的可见规划循环（1 组），以及没有推理文本的跨调用工具或输出循环。
- **不能推广的部分**：这些结论只针对本工程的历史会话（Q2_0 / IQ3_XXS，temperature 0）。上游 [#1622](https://github.com/Niko1221/Strata/issues/1622) 反映的 v0.1.41 循环，在我们的语料里无法验证，因为语料全部来自 0.1.40.x 及更早版本。
