# 前缀缓存尾部检查点：重复 prefill 离线统计

2026-10-24，离线统计（Sonnet worker），不加载模型。背景见 [0.2.x 核查](../v02x-review.md) 与 [上游问题 #2](../../../docs/strata-upstream-issues.md)。

## 结论和判据

- 判据（统计前定下）：重复 prefill 耗时占全部推理时间 ≥3% 才建议测 `--prompt-cache-tail` 的 A/B。分母是引擎侧 prefill 加 decode 的总时间。
- 结论：**全部数据合计远低于 3%，不建议专门做 A/B。**
  - 合计重复 prefill 耗时占比是 0.60%（下限）到 1.21%（上限）。
  - 最宽的敏感性上界也只有 1.30%。这个上界把新会话和压缩造成的差异也全算进重复。
- 例外：长上下文专项（首请求 ≥100K）的上限是 6.98%，已超过判据。
  - 这类数据主要来自 2026-10-24 的 longctx 测量，是合成长上下文负载，不是日常 agent 会话。
  - 这类负载下的 prefill 以 16384 对齐复用为主。
  - 如果以后要把 Strata 作为 100K+ 长会话后端并看重这类延迟，可以做一次小规模 A/B（见局限）。
  - 日常 agent 工作不必为此测。
- 需要说明：日志里没有请求内容，重复量是估算，不是精确值。下面区间两端是不同的估算口径。

## 数据来源

- 主数据：安装目录 `logs/iq3_xxs-prebuilt-engine.log`（2026-10-11 02:53 至 10-24 22:23，771 次引擎启动、21,828 条请求行、2 条被取消的已排除）。
- 用到的字段：
  - 每个请求的一行 `strata serve: prompt P tokens = R reused + D read in ms (tok/s), G generated in gms ms ..., N checkpoints`，即 prompt 总长度 P、命中前缀 R、实际 prefill 数 D、prefill 耗时、decode 耗时和生成数。
  - 复用来源行 `conversation cache: restored N tokens (checkpoint|live)` 和 `borrowed N tokens`。
  - `engine started` 行的启动时刻和命令行。
- 其他来源的核对结果：
  - 前端日志 `frontend.log` 只有请求行，没有 token 数和时间戳。
  - pool-workers、outcap-verify 运行目录里的 `engine-request-log.txt` 是同一份引擎日志的截取。这两项是 32K 合成负载，每块靠标记头强制缓存不命中，不代表真实重复，所以没有单独统计。
  - sampling-dim 等 agent 运行目录不保存逐请求请求体，也没有 cache 字段。
  - Q2_0 引擎日志按项目约定不计入。
- 四项数据中前三项是直接记录：命中长度 R、prefill 数 D、prompt 总长 P。第四项「与上一请求的公共前缀长度」日志里没有，只能估算：
  - 下限：`min(P, 上一请求的 P)`。
  - 上限：`min(P, 上一请求的 P + G)`。
  - 重复量 =（估算的公共前缀 − R），按 D 封顶。
  - 只计 R>0 且差值在 8 到 16384 之间的请求。理由是 16384 是检查点间隔，同会话分叉的损失不超过这个值；差值更大的是新会话或压缩后内容全新，不算重复。
- 耗时折算：用该请求自己的 prefill 速度（D / prefill 耗时），D<512 的小请求按每秒 2000 token 的回退值。

## 局限与未覆盖的部分

1. **分 harness 没做到。** 引擎日志不记录 harness 和会话 id。
   - 只能用「首请求 prompt 长度」当代理：首请求约 17.9K 的段已核对对应 10-24 sampling-dim 的 Codex 运行，其余长度带的归属没有核对。
   - 上面的分组只是工作负载特征分组，不能当作 Codex 和 Claude Code 的分布。
   - 要得到准确的分 harness、分场景数据，需要在前端或运行驱动层给每个请求记 `{harness, scenario, session id, 时间戳}`。
2. **公共前缀是估算，不是真值。** 日志里没有请求内容或 token 序列。
   - 估算按「同段内相邻请求」处理，多会话交错时会把别的会话算成上一请求，造成高估，也可能漏掉真实的跨会话重复。
   - 要精确得到公共前缀，需要在前端层保存每个请求的 token 序列哈希或前缀块哈希（例如每 1024 token 一个块哈希）。
   - 打开 `STRATA_CACHE_MESSAGE_BOUNDARY` 或 `--prompt-cache-tail` 后引擎日志会多出什么，没有验证。
3. **检查点的实际网格不明。** 日志里 restored 的 token 数有 361、604、12089、13570 这类非 16384 倍数，说明还有 prompt 末尾之类的检查点。上限口径里的 16384 封顶是按设计推断的，没有从引擎源码核实。
4. **时间分母只有引擎侧时间。** 没有包含工具执行、harness 开销和排队等待；改用端到端墙钟时间，占比会更小。
5. **长上下文和合成负载在样本里占比偏高。** 日常 agent 的真实分布可能比上面的合计更偏向低值。
6. **没有覆盖的内容。** Q2_0 引擎日志没有计入；`--prompt-cache-tail` 和 `STRATA_CACHE_MESSAGE_BOUNDARY` 本身没有测，771 次引擎启动的命令行都不含 `prompt-cache`。

统计脚本是一次性的，已删除；要复现，按上文口径从引擎日志重算。
