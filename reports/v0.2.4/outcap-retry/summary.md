# 输出上限重试改进：真实模型验证（本机 / IQ3_XXS，Strata 0.2.4，2026-10-24）

设计见同目录 [design.md](design.md)。worker（Opus high）报告，Main 整理存档。

## 结论

- 新代码三项判据全部通过，已正式部署到 本机。同一个撞上限的请求跑了 3 次，每次都满足：
  - 以 `response.completed` 结束；
  - 工具调用完整，`bash -n` 通过；
  - `frontend.log` 有 `retrying with the notice and max_output_tokens 16384 (limit set by the frontend)`。
- **偏离：旧代码对照组没有复现"重试后仍撞上限"。**
  - 试了 4 种直连请求，其中 3 种第一次都撞到 8192，思考都正好停在 2065，和 low-a9 一样。
  - 但旧代码只加通知重试后，这 3 种全部完成：模型把内容缩短，或者只写分步的第一步。
  - low-a9 的失败可能和 Codex 的上下文有关，用直连请求复现不了。
- **核心假设"上限加倍后模型能一次写完"没有证实。**
  - 新代码重试时有约 14300 token 的回答空间，模型只用了 3500–5100，仍然照通知分步或缩短。
  - 在这个负载上，新代码不比旧代码差，但也没看到收益。
- 回归：不撞上限的请求两组都正常完成，速度没有可见变化。逐字节不一致来自引擎本身的不确定性：旧代码自己两遍就不同，冷加载之间也会交替出两种结果。
- Main 的判断：新代码不比旧代码差，部署前已过独立审查，所以保留部署。收益要等 Codex 端到端场景再看。

## 方法

- 直接对前端 `/strata/v1/responses` 发流式请求，部署默认参数（greedy）。每组都冷加载、先预热，加载后核对启动提示 SHA。
- 撞上限请求 C4：low 强度，不给上限（前端补 2048/8192）。要求用一次 `exec_command` 把 330 条记录转成 JSON。显式给上限时的自然长度是 13836 token。

## 未验证

- Codex 端到端：low-a9 那类情况，以及长时间重试会不会让 Codex 断流。
- 加倍后的上限被窗口剩余空间裁小、guardian 1024 加倍、调用方给上限时只加通知，这几条路径都没有用真实模型测。
