# 窗口维负载 v2：206584 与 156584 的比较设计

用途：在 rtx3080ti / IQ3_XXS 上比较对外上下文窗口 206584（压缩阈值 150K，现默认）与 156584（阈值 100K），决定哪档更好。本文是长期设计文档，取代 `benchmarks/tuning-workloads-v1` 里的 v1 窗口负载（L130/L180，从未运行，已删除）。

来源：负载设计草案第 2 版 §2（W2）及用户决定（2026-10-22，记在 `docs/plan.md`「采样与窗口重新测量」）。本文完整记下 §2 和这些决定，不依赖 `.tmp`。

## 用户决定（2026-10-22）

- 先做窗口维（206584 对 156584），按 v2 §2 设计。
- 打分统一：5 个检查点等权。
- 平手（分阶段判定判等效）时按总工作时间选，总工作时间含压缩。
- 其余 U 项按 v2 推荐：
  - U9：E 按检查点等权；C1/C2 由模型实测；"原文与否"按实测压缩位置判定；K 带标记与不带各半。
  - U10：试跑时限 3600 秒；正式时限取试跑最慢实例 × 1.3–1.5，不超过 2700 秒。
  - U11：判定只用 Codex；Claude Code 只核对机制。
  - U13：每轮内同条件连跑，轮间反转顺序。

## 1. 对话结构

- 一段约 300K token 的纯对话，经原生 Codex 0.164.0 运行，推理强度 high。
- 开场写入关键事实；之后是记录批次，每批约 6K token，用安装目录 IQ3_XXS 分词器精确计数。每批模型只回 `ACK nn`。
- 5 个检查点，在"从不压缩时的累计上下文"约 120K、165K、210K、255K、300K 处。
  - 不设 70K 检查点：两档在 70K 都还没压缩，只增加噪声、稀释差值。
  - 按 Codex 实测偏低的触发点重算：156584 约在 95K、170K、245K 压缩 3 次；206584 约在 122K、230K 压缩 2 次。各检查点因此落在两档压缩周期的不同位置。
- 事实分三类：
  - **K 关键事实**：16 条。8 条带标记"later steps depend on this value: keep it"，8 条不带。其中 5 条在第一次压缩之后的批次里更新（`K_UPDATE_AT` 约 140K，第 21 批）。
  - **B 批量记录**：沿用 v1 格式：编号、owner、site、qty、status、tag，值互不相同；批次里另有对早先记录的更新行。
  - **U 更新链**：同一记录改两次。
- 每条事实全程只问一次。
  - 题目按年龄段和检查点预先分配：每个检查点 12 题（K 3、B 7、U 2），共 60 题。
  - 被问过的事实，在之后的批次里不再出现、不再更新。
  - 题面会点名"哪条记录、哪个字段"，可能让后续摘要保留它们。这个影响小，报告里写明。
- 分类按实例实测。每题在提问时其来源是否仍在原文里、之后经过了几次压缩，都由该实例实测的压缩位置机械推出：
  - Codex：rollout 的 `compacted` 事件，以及 `replacement_history` 里保留的原文用户消息。
  - Claude Code：`compact_boundary`。Claude Code 压缩后不保留原文，只留摘要。
  - "U 链是否跨压缩"同样按实测判定。

冻结负载：`window-v2-seed1.json`。

| 项 | 值 |
|---|---|
| 生成 | `python3 -m tools.tuning.window_bank build --seed 1`，分词器计数 |
| SHA256 | `560a1c6489643432c92772453ac92771a106d6f9a87bfa67d161bef56ac3c63f` |
| 批次 | 46 批，每批 5,729–5,910 token；K 更新在第 21 批 |

## 2. 判定量（U9）

只用依赖模型的成分：

- **C1 原文检索准确率**：来源仍在原文里的题，按提问时那个请求实际携带的上下文分段：< 100K、100–150K、≥ 150K。核心问题是 206584 在 100–150K 是否退化；0.2.2 在长提示上出现过一次一致的错答。
- **C2 摘要保持率**：来源已被压缩掉的题，按类别（K 带标记、K 不带、U、B）分开统计。另按经过的压缩次数细分（`C2_by_compactions`）。
- **C3 工作时间**：总工作时间，含压缩。取各回合 `codex exec resume` 的墙钟之和。

机械成分 **M**：各档在各检查点、各年龄段的原文保留比例，按实测压缩位置直接算出。B 记录被压缩后预期接近 0，因为工程压缩提示写明 "Omit bulk repetitive rows"。

**实例分 E** = Σ_检查点 w ×（该检查点各题所在格的准确率的平均）。题在原文里时取 C1(长度段)，否则取 C2(类别)，两者都是该实例的分格准确率。

- 权重 w 每个检查点等权（用户决定）。等权时 E 恰好等于原始总正确率：每格对总分的贡献是"格内答对数 / 60"。所以 E 的方差与原始正确率相同。C1/C2/M 的拆分用于解释差异来自哪里，不改变分数。
- 压缩后的 B 题按类别 B 进 C2，与 K、U 一样。设计草稿的 C2 定义只写了 K 与 U；这里按 E 公式"原文中 ? C1 : C2(类别)"的字面含义处理，B 也有自己的类别格。
- E 在 0–1 刻度上，按测量规则做分阶段判定：两候选，第 3/5/7/9/11 轮，c = 2.25·√(5/轮)，等效阈值 δ = 0.05。
- 平手（判等效）时按 C3 总工作时间选，时间短者胜。

报告同时给出：原始总正确率、C1、C2、M、C3，以及由两档 M 的差能算出的上限效应。

## 3. 时长、时限、生效核对

- **时长估计**：约 50 个 ACK 回合 × 6–10 秒，加 3 次压缩 × 60–90 秒，加 5 个问答回合，约 20–30 分钟。
- **时限**（U10）：
  - 试跑硬时限 3600 秒。
  - 正式时限取试跑最慢实例 × 1.3–1.5，不超过 2700 秒。
  - 到时不再发后续回合，未答的题记 0 分。
- **生效核对**，每个实例都做：
  - 引擎回读 `--max-context` 与档位一致。
  - 启动提示 SHA 和压缩提示 SHA 与工程源一致（绑定写进实例记录）。
  - 156584 压缩 ≥ 2 次，206584 ≥ 1 次；记录每次压缩前的批次。
  - 206584 的最大请求输入不超过已验证的 151,000 token（`verified_prompt_tokens`，取引擎日志）。
  - 出现任何工具调用，实例即无效。
- ACK 不合规（回复不恰为 `ACK nn`）只记录，不使实例无效。

## 4. harness（U11）

- 判定只用 Codex。
- Claude Code（2.1.309）只在试跑阶段每档跑 1 次，只核对机制：压缩位置、ACK 是否合规、问答能否解析、压缩请求是否带工程压缩提示。不声称两个 harness 的结论一致。
- 两边的窗口与压缩点已由 `qwen-agent` 设成同一档位。剩余差异：
  - 基础开销不同。
  - 触发计数口径不同：Codex 用本地估算，偏低；Claude Code 在阈值 ±100 内触发。
- harness 版本取自 `tools/reviewer/harness_pins.py`，整个工作期间固定。

## 5. 排程与预热（U13）

- 每轮内同条件连跑，一个条件一次加载，轮间反转顺序：
  - 第 1 轮：a a a b b b
  - 第 2 轮：b b a a
  - 第 3 轮：a a b b
  - 以此类推，`codex_workload.next_round(grouped=True)`。
- 试跑：每条件 1 个实例，206584 在前。
- 块运行：
  1. 领一次租约，冷加载该档位。
  2. 做一次不计分的预热对话：开场 + 4 批，独立线程，时限 900 秒。
  3. 依次跑该块的实例，每个实例一条全新会话。
  4. 停模型并截取引擎日志；按实例的字节窗口切分 token 和四种速度。
  5. 归还租约。
- 预热的形态是本工程按测量规则「加载后预热」的选择，设计草稿没有指定：用同一负载的开头，不计分。

## 8. 试跑与停止（§2.6）

- **试跑**：Codex 每档 1 次，加 Claude Code 每档 1 次，后者只核对机制。约 4 × 25–30 分钟，加上加载，约 2 小时。
  - `python3 -m tools.tuning.codex_workload run --plan benchmarks/window-load-v1/pilot-plan.json --out <dir>`
  - `python3 -m tools.tuning.codex_workload claude-window --plan … --out <dir> --condition window-206584`
- **改设计的条件**，满足任一即停下、改设计：
  - 实例超过 3600 秒；
  - ACK 回合普遍出现工具调用或长思考；
  - C1 或 C2 在两档都饱和（全对或全错）。
- **正式**：每档 3 次开始，约 2.5–3 小时。greedy 下回忆输出波动小，预计第 1–2 轮可以判定，约 3–4.5 小时；最坏 22 次，约 9–10 小时。

## 9. 风险

- 窗口的取舍依赖使用场景，E 的权重就是在选场景。
- 回忆记录表不等于真实 agent 工作。用工具读文件的变体测不到保持能力，所以不采用。
- ACK 回合在 high 强度下仍会思考，拉长时长。不降低强度，以免回合之间设置不一致。
- 206584 若在 150K 阈值附近才压缩，一个请求可能携带约 150K 加一批 6K，超过已验证的 151K。试跑会显示是否发生；发生时按生效核对失败处理，停下给出选项。
