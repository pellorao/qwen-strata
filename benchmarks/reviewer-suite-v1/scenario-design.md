# Reviewer 场景设计规则

设计或改版 reviewer 场景（Commit Audit、Code Spec、Code Standards、Spec Readiness）时读。评分与流程见[ARW Reviewer 测量规则](../../.claude/rules/reviewer-suite.md)；相对路径链接以本文件所在目录为准。

- 场景时长（设计规则，用户 2026-10-13）：Strata（rtx3080ti 当前默认部署）跑一个 reviewer 场景实例（含该实例全部子线程，如 Spec 的 RM+AP），工作时间每次不得超过 30 分钟，平均最好在 20 分钟以内。这是场景设计与验收的约束：设计新版本时控制 Input 规模和用例数，冻结后若 Q3 有实例超过 30 分钟或均值明显超过 20 分钟，先缩减场景再定版。不改 ARW 原版的时限提醒与中断，也不在运行中途强杀。加难度应靠推理深度（跨文件对照、隐含缺陷）。
- 阅读量维度（Code Spec、Code Standards 等代码题，用户 2026-10-14）：从大量代码中找出问题是 reviewer 的真实工作，大阅读量是正确的出题方式；真实审查可能面对约 300K 材料，审查中压缩不加限制。阅读量作为独立难度维度，与推理难度分开测，不在同一版本里同时改。目标阅读量 100K–150K，工作时长 20 分钟以内：到时限停止答题（用 ARW 原版的时限与中断实现，不强杀），只按截至时刻已写出的结果计分；时限和"每确认一个问题就追加写入结果文件"都写进 handoff 提示。时限公式（用户 2026-10-14）：T 秒 = B ×（1/P + k/G）/ β，B 为输入规则和代码总字节，β 为该模型在该输入上的字节/token（B ÷ 引擎报告的输入 token），P、G 为该机器加该模型的读入、生成速度（每批测量前用短探针测一次，不按单次运行取值），k 为每个输入 token 允许的生成 token；k 按"rtx3080ti 上 Q3 时限 = B/10K 分钟"反推（估计约 2），β 首次实测后校正一次再固定。Opus 用同一公式和它自己的 P、G、β。Opus 若在自己的时限内也找不到大部分缺陷，先调大 k，不把被时限压低的比值当结论。干草堆用真实相关的代码，缺陷不能靠 spec 关键词搜索直接定位（防搜索捷径），也不能有局部线索。Opus 参考窗口更大、压缩更少，接受这一差异（测整体后端表现），报告注明。
- 难度设计（用户 2026-10-13）：推理步骤数是智力难度的关键。加难度时提高每个缺陷从 spec 到判定所需的推理步数；调整按二分法（AGENTS.md）：试跑显示太容易，平均步数至少 +2 步（上界未知时大步探界）；发现太难就取与上一个"太容易"点的中点（用户 2026-10-14）。步骤类型同样决定难度：推算具体值（单位、边界、时间点）或依赖语言语义（类型转换、展开覆盖顺序、引用共享、异步时序）的步骤，比对照 spec 逐行比对的步骤难得多；加难度时步数和步骤类型两边同时加（用户 2026-10-14）。步数指规则网络中的推理步数（从事实到判定违规需要经过的规则应用、优先级或覆盖判断、条件分支的个数），不是代码执行或引用追踪的步数：后者能被执行代码直接压平，一万步和一步没有区别；规则网络的推理要用代码复现就得先完成很强的数据建模，答题者真有这个能力，用代码做也可以（用户 2026-10-14）。步数按"有效步数"计：从 spec 到判定的最短推理路径，不是设计者写下的链长。不得留捷径，缺陷所在行和它附近不能有局部线索（可疑写法、命名、注释、与 spec 字面直接对照），否则答题者跳过中间步骤就能判定（用户 2026-10-14）。"局部线索"指缺陷附近能提示问题的东西；缺陷行本身写得自然、只有懂语言语义或把数据流追到最终结果才能判错的，不算捷径（例：先展开原对象再展开 `delete` 过字段的新对象，被删字段的原值保留）。一套题不能只有一种题型或一种难度：以这类长链、无线索的缺陷为主，同时保留一部分推理步数少但问题隐晦的缺陷（例：`save` 前少写 `await`），以及少量保底题（用户 2026-10-14）。design.md 为每个用例写明为什么每一步都不可跳过。能执行代码的答题者会用运行代码压平静态推理链（因素探针 2026-10-14：约 20 步的容易链与 4 步链检出相同），所以难度要放在执行代码绕不过去的推理上；首选做法是参考 Spec Readiness，把 spec 写成有优先级、覆盖、条件分支和例外的规则网络，判定违规需要在网络中正向或反向探索，优先级和覆盖关系必须在 spec 中写明以保证答案唯一（用户 2026-10-14）。因素探针（分开测量步数、步骤类型等难度因素的小组题）不是 ARW 场景，不受 ARW 用例数等合同限制，可按测量需要拆分；每组 Q3 跑多次。Opus 只在 Q3 结果还不能下结论的组上跑：Q3 在某组已经全部检出（该因素对 Q3 无效），这组就不需要 Opus（用户 2026-10-14）。答案键为每个问题用例写明推理链和步数，审计核对步数与唯一性。草稿难度用 Q3 单次试跑校准，不必跑满：第一次得分就很高说明难度一定不够，直接回到设计继续加难；试跑得分低不能直接定版（可能只是单次波动），只有试跑得分已明显下降，才进入审计、冻结和正式测量（正式测量仍按原定次数）。难度目标是 Opus 稳定找到大部分缺陷，同时 Q3 明显下滑；审计阶段的 Opus-high 盲答找不到的缺陷，先查歧义或过偏，不当作难度合适。
- 场景分工（用户 2026-10-14）：各场景的难度来源要不同，避免考察内容重合。Code Standards 中难度来自规则网络的题最多占一半，其余守住代码质量与设计标准（复用与归属、同形异质、`writing.md` 结构问题、语言语义）。发现重复或高度相似代码并合并是重点能力，这类题约占 1/3 或更多；负面例子（看起来相似、实际不应合并的代码，作 clean 孪生）与正面例子 1:1，每道重复题配一个，design.md 写明不该合并的理由（反例输入或归属、演化理由）。不出逐字或几乎逐字相同的重复：机械比对就能找到，检验不了智能；只出写法不同但行为等价、参数化后可合并、同一规则不同表达的重复，并用去空白、去标识符后的文本比对自检，能直接匹配的要改写。design.md 用配比表写明每题的难度来源。
