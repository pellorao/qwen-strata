# 裁决先例

评分、盲裁和实例有效性的争议，先在这里查先例。有先例就照先例处理，不重新争论；没有先例，或者先例的前提已经不成立，就按 AGENTS.md 硬约束 1 处理（口径问题由用户定），定下来后补进本表。

状态分三种：**用户定**，是用户的决定；**暂行**，是用户未答复时按独立意见执行、等用户复核的；**规则**，是现行规则的应用，写在这里只为方便查找。暂行条目经用户复核后改成"用户定"，用户推翻的直接改写。

## 场景文本与评分

- **场景原文有歧义（用户定，2026-10-20）**：Main 先用可执行检查复核有争议的 unsupported 项。文本确实两可的，在报告里列为已知歧义，并给出两种读法下的分数。决定库只存一种主读法。benchmark 结束后修改题目，消除歧义。
- **CS v5 `governing-spec.md:160`，空白的目录 locale 键是否归为 `en`（用户定，2026-10-20；属于上一条）**：原文是 "Catalog locale keys and a member's `locale` are trimmed and lowercased, a missing or blank locale being `en`."。主读法是不归，相关 finding 判 unsupported。依据：后半句的单数 locale 对应成员的 locale，目录键在全句都用复数 keys；"missing" 只能用在成员身上；brief 规定判断不了时选 unsupported。报告同时给出判为 supported 时的分数。这条歧义 10-14 试点时就已出现（OpenAI finding-14），10-21 的第一批盲裁中又出现了 13 条。
- **CA 只说"实现违背 / 未满足"、不讲机制的 finding（用户定，2026-10-21，先暂行、经独立审查后用户确认）**：判 unsupported。例如 "The staged implementation directly fails the stated behavior."：挂载行给出了要求，证据给出了代码行，但没说那段代码错在哪（什么输入、得到什么错误结果）。依据：R3b 给出的四种去向里只剩这一种；冻结的 workflow:30 要求写出可采取行动的问题说明；Role:44 规定重复的通用问题不能替代语义判断。判 supported 会留下捷径：模型在每条问题行写一句"违背"，就不会受罚。这类 finding 没写出机制，不属于下下条"挂在别的位置的真缺陷"。
- **finding 挂在已满足的要求行上，内容讲的却是相邻行的缺陷（规则 r8.1）**：判为所挂那一行的误报（`false-positive:clean-N`，取该项可选值里的 N），不得改挂到别的行。r8.3 也不允许跨行给分。
- **答案键里的缺陷挂在了别的位置（用户定，2026-10-21；推翻同日为 CA 定的"判 unsupported"）**：finding 讲的缺陷属实、写出了机制，在答案键里，但不在所挂位置（SR 的检查、CA 的要求行）的 `problemOptions` 里，判 `supported`（不得分也不扣分）。所有场景通用。依据：r7 的 `unsupported` 指无依据；r8.3 把可选项收窄到同一位置后，"答案键外"按"不对应列出的问题用例"读，即 CA brief:21、SR brief:21/30 原文；缺陷在正确位置漏报已按漏报扣过，重复报的按上游原文"不再接受第二项干净用例惩罚"，再记失败干净用例就是同一错误扣两次。例外照旧：挂在已满足行上按 r8.1 判误报；只说"违背"的按上上条、模板句按下一条判 unsupported；原文照贴的副本按下下条判。CS、CStd 只有一个范围、一个检查，答案键内的缺陷总在 `problemOptions` 里，不会出现这种情形。经独立审查确认（10-21）。
- **finding 的机制写对了，但结论或例子与代码相反（用户定，2026-10-22）**：检验办法是只照 finding 写的结论或复现去修，能不能修掉真缺陷。(1) 主结论或复现例子与代码的实际行为相反，判 `unsupported`。例如 CA authorizeRouteBatch 的真缺陷是"第 0 个路线失败时整批仍被接受"，finding 却写"后面的路线失败才被接受"；或者把合法输入 `'02'` 当作反例。照着修会改动正确的分支，真缺陷还在。(2) 主结论和复现都成立，只是个别措辞写反，判 `supported`（例：第一阶段 ds-ca-4-149）。(3) 机制说明自相矛盾，但复现的情形实测属实，判 `supported`，不对应该问题用例（缺陷存在，所以不算误报；所述原因与答案键要求的点相反，所以不算命中；例：p2-ca-15-042、15-067）。(4) finding 指出的问题属实，但把答案键缺陷背后的错误意图当成正确要求，判 `supported`，不对应该问题用例（用户定，2026-10-22；例：p2-sr-claude-2-044。答案键缺陷是 Readiness 与 Promotion 重复负责验证，finding 却要求接口传入 request，让 Promotion 的再次验证能做成；照它修会坐实重复，说明它没有找到问题）。出处：第二阶段 CA/CS 复核 N-a、N-b，SR 复核。
- **模板式的通用 finding 原样贴在多行上（用户定，2026-10-21）**：例子是"…contract does not establish the needed callback, unknown-address, or measurement-unit semantics"。即使碰巧说中某一行的答案，也判为没有对上（association 判 not-matched，finding 判 unsupported）。依据：Role:44 规定重复的通用问题不能替代实际的语义判断；否则模型把一句宽泛的话贴满所有行就能得分。
- **一条 finding 讲了两个缺陷，原样贴在几行上（用户定，2026-10-21）**：例如 "The admin check ignores active claims, and suspended actors can still receive active claim scopes."。它不属于模板式通用 finding，因为写出了具体机制。哪一行的缺陷在文中被讲到，那一行就判对上；文中没讲到的行仍按上一条（判 unsupported）或 r8.1 处理，不适用"挂在别的位置"那条。这不算跨行给分：每行得分靠的都是本行自己的缺陷。
- **新代码照搬仓库里已有多份的重复实现（用户定，2026-10-21）**：例如 CStd 的 catering 手写第 4 份状态表推进，或又一份 store 写队列和 requestKey 扫描。这算本次变更的问题，finding 判 `supported`。依据是 Role 的两条要求：检查"当前变更是否重复实现了仓库其他位置已有的相同逻辑"；通用功能放入公共模块，"不以已有多个调用方为前提"。违背了就是违背了，与仓库以前怎么写无关。brief 中性规则排除的"只存在于未改动文件的既有问题"，只指重复完全在未改动文件里的情形。修法与某个干净用例相反的，仍按该条处理。

## 盲裁流程

- **盲裁隐藏不了答题人来源（用户定，2026-10-20）**：接受版式泄露，靠分族的锚点和合成项监控偏差；身份泄露也可以接受。提示词里写明要公平判定。
- **跨池一致性（规则，2026-10-21）**：同一文本在不同池判法不一时，以有冻结文本依据的判法为准，经独立复核后用 `blind_pool override` 统一改判，并保留历史。

## 格式错误与有效性

- **能机械恢复的错误一律按格式错误计（用户定，2026-10-20）**：修复后证据有效，计入 r。具体做法见 [reviewer-suite 规则 · 评分](../../.claude/rules/reviewer-suite.md#评分)。
  - 证据引用了落盘文件的行号：只取会话中被工具引用过的落盘文件，按 hunk 换算，换算结果必须唯一，且逐行内容相符。
  - CA 要求行号整体错位：finding 引用的要求原文和所讲缺陷都属于另一行，标的行号却是本行（用户定，2026-10-21，例 OpenAI luna-low-a7 行号整体偏一行）。用引用的要求原文能唯一定位到正确的行时，改挂到那一行计分，并按格式错误计入 p；定位不唯一就不修，按标的行号判。不分关、不分场景（用户定，2026-10-22："能机械修复的错误都修复，算格式扣分，没有第一关修其他不修的道理，用到所有场景"）：CA 第 2 关（spec 行）同样修，其他场景凡报告引用的原文能唯一定位到另一行的，同样改挂并计入 r。范围按行号的作用划分，不按条数（用户定，2026-10-22）：**标识用行号**（只指明在判哪一条要求，报告同时给出该要求原文，如 CA 的 `source.line`）按原文唯一对应改挂，一行也修；**证据定位行号**（行号本身是被计分的定位，如 CS/CStd/SR 的证据定位、CA finding 的 `lines`）即使附了引文也不改挂，按所写行号判，以免由计分端替模型完成定位。
  - B 类：报告已写完，但最终状态消息不合规，且之后没有接续修正。实例有效，计 1 处格式错误。
- **Strata Codex 臂在前端重试 1 次后仍撞输出上限、没写出报告（用户定，2026-10-22；先由 Main 依独立意见暂行）**：实例有效，登记为模型失误、按 r8.4 记 0，不作废补跑。依据：输出上限和前端重试 1 次（10-20 部署）都是固定条件，按设计生效，不是工具故障；Codex 收到 response.incomplete 结束回合，与 F4 的模型侧错误同类。10-20 部署前因 incomplete 作废的 4 个实例，作废原因是固定条件不同，不构成先例。例：strata-codex CStd low-a9。
- **提醒和中断打断生成（用户定，2026-10-20；判据 2026-10-23 用户改定）**：这是高优先级消息的预期行为，不算 relay 错误，实例有效。判据只有一条：提醒或中断送达（status accepted）时正在进行的请求（started_at < attempted_at ≤ ended_at），它的错误行不算 relay 错误，其他错误照常。原来的 7 条判据（Main 2026-10-20 定，未经用户复核）多出的旁证条件误排除了 CStd luna-max-a4、a6：relay 要到下次写数据才发现客户端断开，记下的结束时刻比重发晚 1.8–3.7 s。机械做法见 [benchmark 计划 §14 M2](../multi-model-v1/plan.md)。
- **上游断流、harness 自动重试（用户定，2026-10-21）**：断流是服务端的问题，重试只是重新连接，和做题无关，只要模型看到的输入没有变，实例就有效。须同时满足以下条件：
  - 断开前已返回 200；
  - 断开的流没有任何输出写进会话（rollout）；
  - harness 在几秒内重发同一请求，并以 200 completed 结束；
  - 其他检查都通过。
  
  不满足的实例照旧判无效，例如断开前的部分输出被带进了重发请求（DeepSeek SR codex-low-a1）。断开的那次请求，从开始到重发之间的时间和它的 token 都不计入，费用按已完成请求逐个计价。因误判引发的补跑算重跑，不算额外样本。
- **还没拿到 HTTP 状态就断开的传输错误（用户定，2026-10-21；按上一条的理由推广）**：例如 BrokenPipe、连接被重置，harness 在几秒内重发同一请求并以 200 completed 结束，rollout 里没有任何写入。判有效，理由同上一条：模型看到的输入没有变，只是重连了一次。断开那次请求的时间不计入。不适用的情形：
  - 请求挂起占掉了可观的做题时间，例如 DeepSeek SR codex-low-a5 的 URLError 挂起 900 s，占了硬时限的四分之一；
  - 有部分输出写进了 rollout。

  这些仍判无效，按常规补跑。不另列敏感性行：这是网络问题，与模型表现无关（用户 2026-10-21）。
- **Claude Code 实例到硬时限被强杀，没有 result 事件（规则，2026-10-21）**：plan 规定到硬时限停止的实例有效。如果 stream 里没有 `server_tool_use`，网络请求按 0 次计，实例判有效，费用按 relay 或余额差补记，token 记为未知。由这类误判引出的补跑算重跑，不算额外样本：没有合并的格，主统计取按开始时刻排序的前 5 个有效实例（2026-10-23 用户改定：多跑的有效实例只要不是按分数加跑，全部计入，见测量规则「失败与重跑」；第三阶段起适用）。
