- Badge event key lookup is limited to the event's own building, but the governing spec requires a key match in any building. `src/badges/badge-service.mjs:5-7,15-17` lists events with `store.list(event)`, which filters by `buildingId` (`src/platform/append-log.mjs:6-8`). Governing spec `governing-spec.md:167`: "if an event recorded in any building has the key, recording returns it and does no further work." Impact: a retried event whose key was first recorded in another building is stored again instead of returning the existing event, so duplicate badge events and duplicate anomaly notices can be created. Fix: look up the key across all recorded events (for example, `store.list()` without a building filter, or a dedicated key lookup) before the repeated-swipe check.

- The audit query window limit compares minutes with milliseconds, so the 10080-minute maximum is never enforced. `src/audit/audit-query.mjs:9` checks `windowSpan(query) > AUDIT_LIMITS.maxQueryWindow`, where `src/audit/retention.mjs:13` returns minutes (`/ MINUTE`) and `src/audit/retention.mjs:5` defines `maxQueryWindow: minutes(10_080)`, which is 604800000 ms. Governing spec `governing-spec.md:97`: an audit query must have "`until` later than `from` by at most 10080 minutes". Failing scenario: `prepareQuery({from: 0, until: minutes(20160)})` passes because 20160 is not greater than 604800000, so an over-long window is accepted. Fix: compare the window in the same unit, for example `(query.until - query.from) > AUDIT_LIMITS.maxQueryWindow` with the constant in milliseconds, or make `windowSpan` and the constant share one unit.

- The actor summary applies the query `limit`, but the spec says it must ignore `limit`. `src/audit/audit-query.mjs:49-51` builds the counts from `selectEntries(entries, query, at)`, and `src/audit/audit-query.mjs:41` applies `pageOf(...).slice(0, query.limit)`. Governing spec `governing-spec.md:146`: the summary "counts every entry it matches, ignoring `limit`". Failing scenario: with `limit: 1` and three matching entries from two actors, the summary reports one entry for one actor instead of the full counts. `src/audit/audit-service.mjs:47-50` passes the prepared query straight through, so the error reaches the caller. Fix: count from the filtered entries before applying the limit, for example by filtering with `matches` without calling `pageOf`.

- Applying a reservation transition mutates the caller's reservation history. The spec requires that operations not modify a received reservation and return new records. `src/reservations/transitions.mjs:16-17` copies the record with a shallow spread and then calls `next.history.push({state: rule.to, at})`, which appends to the same `history` array as the input record. Governing spec `governing-spec.md:8`: "Operations never modify a reservation object they receive; they return new records." Failing scenario: `confirmReservation` (`src/reservations/reservation-service.mjs:34-40`) or `cancelReservation` (`src/reservations/reservation-service.mjs:43-51`) called on a held reservation leaves the caller's object with two history entries, so a retry or a caller holding the original record sees a state change that did not occur. Fix: build a new history array, for example `history: [...record.history, {state: rule.to, at}]`, and do not call `push` on the received array.

- A rescheduled window is not checked against the duration limit. The spec requires the snapped window to satisfy the duration limit and be available. `src/reservations/reservation-service.mjs:53-57` checks only `endAt > startAt` and room availability, and never calls `exceedsMaxDuration`, which `createReservation` applies at `src/reservations/reservation-service.mjs:13-14`. Governing spec `governing-spec.md:197`: "The new window must have an `endAt` value later than its `startAt` value. It is then snapped, and the snapped window must satisfy the duration limit and be available." Failing scenario: a held reservation rescheduled to a 300-minute window is saved with `endAt - startAt` of 300 minutes, above the 240-minute limit in `governing-spec.md:21`. Fix: after snapping, `if (exceedsMaxDuration(window)) throw new Error('reservation is too long');` before the availability check.

- An expired waitlist offer can be accepted. The spec allows only a nonexpired `offered` entry to be accepted. `src/waitlist/waitlist-service.mjs:58-63` calls `moveEntry(entry, 'accept', at)`, which returns an entry with `state: 'accepted'`, then tests `isLapsing(next, at)`. `isLapsing` (`src/waitlist/queue.mjs:13`) requires `entry.state === 'offered'`, so the check on the already-accepted record is always false. Governing spec `governing-spec.md:50` ("Only a nonexpired `offered` entry may be accepted") and `governing-spec.md:182` (an offer is expired when `now()` is equal to or later than `expiresAt`). Failing scenario: an offer with `expiresAt` 1 minute in the past is accepted and saved as `accepted` with `acceptedAt`, instead of being rejected. Fix: test the expiry on the stored entry before the transition, for example `if (isLapsing(entry, at)) throw new Error('offer has expired');`, or use `isExpired(entry, at)` on `entry`.

- The 60-minute withdrawal cutoff also applies to `waiting` entries. The spec says only an offered entry is subject to it: `governing-spec.md:183` reads "Withdrawing an `offered` waitlist entry is rejected when its `startAt` is less than 60 minutes after `now()`. A `waiting` entry has no such limit." `src/waitlist/entry-states.mjs:9` defines one withdraw rule for `['waiting', 'offered']` with `cutoff: WITHDRAW_CUTOFF_MINUTES`, and `src/waitlist/entry-states.mjs:22` applies that cutoff to every matched state. Failing scenario: a `waiting` entry whose `startAt` is 30 minutes after `now()` is rejected with "too late to withdraw", which the spec does not allow. Fix: split the rule into a `waiting` rule without `cutoff` and an `offered` rule with `cutoff`.

- A room with duplicate amenity names cannot be booked even when no amenity is requested. The spec requires a room to contain every requested amenity, and it does not forbid duplicate room amenities. `src/reservations/catalog.mjs:16` returns `new Set([...room.amenities, ...amenities]).size === room.amenities.length`. For room amenities `['pool', 'pool']` and no request, the set size is 1 while the length is 2, so the function returns false. Governing spec `governing-spec.md:77`: "a room must contain every requested amenity". Failing scenario: `createReservation` and `listEligibleRooms` (`src/reservations/reservation-service.mjs:18,31`) reject or omit the room with an empty amenity request. Fix: compare membership, for example `amenities.every((amenity) => room.amenities.includes(amenity))`, as `offersAll` already does in `src/utilization/room-directory.mjs:20-23`.

- A desk closure is treated as ended at a sub-minute boundary, which contradicts the closure rules. `src/schedules/closures.mjs:26` defines `hasEnded` as `minutesBetween(at, closure.endAt) <= 0`, and `minutesBetween` truncates to whole minutes (`src/platform/time.mjs:9`). Governing spec `governing-spec.md:184`: "A closure whose `endAt` is not later than `now()` is rejected." and `governing-spec.md:189`: upcoming closures are those "whose `endAt` is later than `now()`". Failing scenario: with `now()` at 1000000 ms and `endAt` at 1030000 ms (30 seconds later), `hasEnded` returns true, so `addClosure` (`src/schedules/front-desk-service.mjs:31`) rejects a closure that ends in the future, and `upcomingClosures` (`src/schedules/front-desk-service.mjs:56`) omits it. Fix: compare the instants directly, for example `const hasEnded = (closure, at) => closure.endAt <= at;`.

- A confirmed reservation that starts exactly at the start of the usage month is not counted in the member's used minutes. Governing spec `governing-spec.md:154` counts confirmed reservations "whose `startAt` is within the month", and `governing-spec.md:180` defines a usage month as half-open. `src/members/allowance.mjs:12` uses `overlaps(instant(reservation.startAt), period)`, and `overlaps` (`src/platform/periods.mjs:5`) requires `period.startAt < instant.endAt`, so an instant equal to `period.startAt` is excluded. Failing scenario: a confirmed reservation with `startAt` equal to the month's `Date.UTC(year, month - 1, 1)` is omitted from `used`, `remaining` and `reservationIds`. Fix: test `period.startAt <= reservation.startAt && reservation.startAt < period.endAt` directly.

- A non-quiet message is sent before its save has been applied. Governing spec `governing-spec.md:207`: a message outside quiet hours "is saved as `sent` with `sentAt` from `now()` before `send` receives `{messageId, memberId, body}`." `src/messaging/messaging-service.mjs:54-55` calls `const saved = store.save(sent);` without `await`, then immediately calls `await send(sentNotice(sent))`. The store write is only queued (`src/messaging/outbox-store.mjs:13-18`), so `send` runs before the record is written. Failing scenario: `send` observes a message whose `state` is not yet persisted, and if the queued write later fails, the message has been delivered without a stored `sent` record. Fix: `const saved = await store.save(sent);` before `await send(sentNotice(sent));`.

- The quiet-hours release time is one minute late, and it can equal `now()`. Governing spec `governing-spec.md:206`: `releaseAt` is "at the first minute boundary after `now()` whose local minute is `endMinute`". `src/messaging/quiet-hours.mjs:33-35` computes `wait` from the local minute of `at`, but adds it to `minuteStart(at + MINUTE - 1)`, which is the boundary after `at`, not the minute of `at`. Failing scenario with `utcOffsetMinutes` 0 and `endMinute` 600: for `now()` at 09:58:10 the code returns 10:01, but the first boundary after `now()` whose local minute is 600 is 10:00. For `now()` at exactly 10:00:00, `wait` is 0 and `releaseAt` equals `now()` rather than the next day's 10:00. Fix: take `base = minuteStart(at) + MINUTE` (first boundary strictly after `at`), then `wait = (endMinute - localMinuteOfDay(base, offset) + DAY_MINUTES) % DAY_MINUTES` and return `base + minutes(wait)`.

- The CSV writer doubles only the first double quote in a field. Governing spec `governing-spec.md:241`: a field containing a double quote is wrapped in double quotes "with inner double quotes doubled". `src/exports/csv-format.mjs:7` calls `text.replace(/"/, '""')`, which has no `g` flag and replaces only the first occurrence. Failing scenario: a text value `a"b"c` (for example a reservation `note`) is written as `"a""b"c"`, which a CSV reader parses as `a"b` followed by malformed text, not `a"b"c`. Fix: use `text.replace(/"/g, '""')`.

- List items in CSV exports are prefixed with an apostrophe when they start with a formula character, but the spec says list items are written as stored. Governing spec `governing-spec.md:242`: the apostrophe prefix applies to a `text` value. `governing-spec.md:243`: "a `list` of strings is joined with `;`, its items written as stored." `src/exports/value-format.mjs:29` maps each list item through `formatText`, which adds `'` for items starting with `=`, `+`, `-` or `@` (`src/exports/value-format.mjs:9`). Failing scenario: a room with amenity `-pool` is exported in `ROOM_COLUMNS` (`src/exports/reservation-columns.mjs:29`) as `'-pool`, not `-pool`. Fix: join the items without calling `formatText`, after the type check.

- The credit reason on an invoice request is trimmed, but the spec says it is stored exactly as supplied. Governing spec `governing-spec.md:135`: "its `reason` must not be blank after trimming; the reason is stored exactly as supplied." `src/billing/invoice-request.mjs:12` returns `reason: credit.reason.trim()`, which stores a trimmed value and changes it. Failing scenario: a credit with reason `"  goodwill  "` is stored and returned as `"goodwill"`. Fix: keep `reason: credit.reason` after the blank check, and only use the trimmed value in the blank test on line 11.
