## 1. 目的

推理难度不变，只把阅读量从 v4.7 的 17.9K 提高到约 150K，回答两个问题：
- 判据：Opus 在按同一公式给出的时限内，能否仍找到大部分缺陷。
- 报告（不作判据）：Q3 在大阅读量下的得分。

报告分两部分：
- 原样缺陷（8 个）的命中变化归因到"阅读量条件"。
- 搬家缺陷（12 个）的命中变化只作参考。

"阅读量条件"是一个整体，不只是字节数。与 v4.7 相比同时变了以下几项，报告不把变化单独归给其中任何一项：
- (a) 时限：v4.7 没有时限，本档按公式给出时限。
- (b) 交接模板：测量说明要求每找到一条发现就追加写入结果文件。
- (c) 核心缺陷数：核心里只剩 8 个，v4.7 是 20 个；核心的缺陷密度下降。搬走的 12 题在核心原位改回了正确写法，所以原样题周围的局部上下文也变了，例如 accessUntilLarge 旁边的 accessFromInstant 已是正确写法。
- (d) 孪生写法：已修复（用户 2026-10-14 要求冻结前修复）。
  - 干草堆 7 个有状态记录的模块（maintenance、waitlist、billing、visitors、payments、members、messaging）不再保留 `history`，状态变化只记时间戳，spec 同步删去相应条款。这样干草堆里没有与核心 `transitions.mjs` 同形的 history 追加。
  - amenityDup 的逐字孪生 `hasAmenities` 已改写为 `offersAll`（Set 成员判断）。
  - selfConflict（修订 33）：`maintenance/ticket-policy.mjs` 的 `conflictingTicket` 原来和核心 `isRoomAvailable` 一样按 id 排除自身。现在 spec 写为"Planning a ticket that already has a planned window is rejected."（修订 34：只描述拒绝，不把清除与再计划连在一起，避免在 spec 层面指向 P15），`planWork` 拒绝已有 `plannedWork` 的工单，`conflictingTicket` 不再比较 id；对应的 maintenance clean 用例改写为 `c_maint_replanRejected`。P15 confirmedAtKept 的期望句补上新后果：清除之后再也不能计划。`members/member-service.mjs` 的 `updateContact` 原来按 `memberId` 排除自身，改为比较 email（库内 email 唯一且已规范化，语义等价）。
  - historyShared 的弱孪生（修订 33）：maintenance 的 `escalations` 和 payments 的 `refunds` 原是 `[...arr, {…, at}]` 不可变追加，改为只记最近一条（`lastEscalation`、`lastRefund`），spec 与测试同步改。干草堆 src 里已没有数组追加写法。
  - 其余 5 个原样题逐一核对过，干草堆里没有同形写法，理由见 `rv/v3/design.md`。
- (e) 版本：Strata 0.1.43.1 → 0.1.44.1（见第 2 节）。
- (f) 跨模块结构：干草堆新增共用目录 `src/platform/`（time、periods、site-settings、invoice-terms、records、append-log、listing），7 个搬家缺陷的关键定义放在这里，判错必须跨目录追踪。干草堆 spec 的 50 条条款移入 5 个跨模块主题节，不再是一个模块对应一节。核心 12 节和 Conventions 与 v4.7 逐字相同。这一项主要影响搬家题；对原样题只是间接影响，比如读入顺序和注意力分配。

结论用于决定代码题的阅读量档位和压缩阈值方向。适用范围只限 Strata v0.1.44.1、rtx3080ti、IQ3_XXS。

## 2. 主机与模型

- rtx3080ti，IQ3_XXS，Strata 0.1.44.1，Codex 0.162.0，effort high。
- 参考模型：Opus-high（Claude agent，与 Q3 相同的渲染交接盲答），不占 GPU。
- 与 v4.7（0.1.43.1）的逐题比较是跨版本的。冻结前复核时，用户确认视为版本间可比（2026-10-14）。依据有两条，报告里都写明：
  - 0.1.44.1 发布说明称默认 pack 的答案逐字节相同。
  - 两版的引擎速度不同：v4.7 正式批引擎输出均值 88.5 tok/s；0.1.44.1 升级短检查 96.0 tok/s，速度探针 91.95–96.30 tok/s，差异主要来自功耗档。时限按每批开跑前的速度探针计算，所以速度差反映在 T 里，不会挤占答题时间。

## 3. 固定条件

基础条件：
- 安装默认值、启动提示与压缩提示的接入、native CLI、按 ARW 原版罚分，均与 v4.7 冻结版相同。开跑前在 0.1.44.1 安装上核对实际加载的 SHA，并保存绑定。

缺陷与用例：
- **原样缺陷 8 个**：selfConflict、durationUnits、lateFeeState、snapEnd、accessUntilLarge、amenityDup、historyShared、rescheduleDuration。
  - 按类别分层随机选出，种子 20261014：长链 4、规则交互 1、短而隐晦 2、保底 1。
  - 注入代码和答案键（期望句、证据标记、spec 依据句、收窄词组）与 v4.7 逐字相同。
  - 行号随夹具重新定位：spec 穿插、搬走的缺陷改回正确写法，都会让行号变化。
- **搬家缺陷 12 个**：其余 v4.7 缺陷各搬到一个新模块，每个新模块一个。
  - v4.7 原位改回正确写法。
  - 新缺陷与原题的题型、有效步数、"为什么不能跳步 / 局部可见性"对等。
  - 答案键为每题写明对应 v4.7 的哪一题，以及逐步对应关系。
- **clean 用例**：
  - v4.7 的 30 个 core clean 用例原样保留。
  - 每个新模块另加 2 个（同类诱饵的正确写法）。
  - 最后一项是 `noOtherSupportedFinding`。

阅读材料：
- 核心 `src/reservations`，加上 12 个新子系统和共用目录 `src/platform/`。修订 34 的 B = 152,846 字节（spec + 候选代码，全部注入版），冻结补丁 `arw-patches/code-spec-rv.patch`（sha256 50087dd75cf064722090152597bed5478f89f26d87277bc4821c9722cb35e98e，即 `rv/v3/rv3f.patch`），冻结 manifest `source-snapshots/current/manifest-code-spec-rv.json`（`code-spec-v3.patch` 之后叠加 rv 补丁，替代 `code-spec-v4.patch`；v4.7 的 `manifest.json` 不变），冻结计划 `code-spec-rv-iq3_xxs-2026-10-14/plan.json`。修订 33 为 152,877 字节（`rv3e.patch`，e2838d7b…），修订 32 为 152,773 字节（`rv3d.patch`，0903484b…）。
- spec 除标题和 Conventions 外，按 `##` 节以固定种子随机穿插。干草堆部分是模块节加 5 个跨模块主题节。

测量说明与时限：
- 测量说明模板：`benchmarks/reviewer-suite-v1/measurement-note-time-limit.txt`（SHA 4c7558c8…），由 `arw_dimension prepare --time-limit-seconds T` 渲染。
- 时限公式：T 秒 = B ×（1/P + k/G）/ β。
  - P、G、β 由开跑前在本批材料上的速度探针测得（`tools.metrics.speed_probe`，引擎日志取值）。
  - k 在 0.1.44.1 的首批探针上按"Q3 时限 = B/10K 分钟"重新反推一次：k = G ×（0.006β − 1/P），之后固定。两个模型用同一个 k。
  - 0.1.43.1 上测得的 k = 2.1653 作废。
  - 0.1.44.1 上的取值：k = 2.0755（13:47 首批探针反推，固定）。β 在修订 32 材料上实测为 3.6591 字节/token，定为冻结值；v2 材料测得 3.6600，差 0.03%。
  - 冻结前的探针（修订 32 材料）：P 2497.3、G 91.95。按修订 34 的 B 算，T_Q3 = 960 秒（16.0 分钟）；Opus 用 β 2.446、G 51.8，T_Opus = 2504 秒（41.7 分钟）。正式批开跑前重测 P、G，按测得值重算 T。
- Q3 的时限执行：ARW 原版提醒与中断（`ReviewDeadline`）。被中断的实例按截至时刻已写出的结果计分。
- Opus 的时限执行：
  - 用同一公式，取 1/P = 0。G、β 用 Opus 探针 agent 的用量差估计。这两个估计偏宽：Read 带行号前缀，G 含首 token 延迟。
  - 正式批的 T_Opus 用开跑前新做的 Opus 探针重算（β、G 取该探针的值）。
  - 到 T − 5 分钟发提醒，到 T 停止该 agent。被停止时按截至时刻已写出的结果文件计分。
  - 被时限中断时按第 8 节的分支处理（调大 k）；按 Q3 口径重估 β、G 只放进敏感性分析，不据此改 T 或重跑。

## 4. 维度与取值

- 维度：阅读量 B，本计划只有 150K 一档。
- 新子系统：同一预订系统里新增的 12 个子系统。
  - 不从 `src/reservations` 导入。共用的时间单位、区间、设置、记录辅助等从 `src/platform/` 导入（rv3）。
  - spec 新节只写直接规则，不覆盖原有条款，也不给原有条款开例外。
  - 不用开源代码。
- 防搜索：spec 关键词（hold、confirmed、canceled、expiresAt、partySize、buildingId、fee、history、now() 等）在新代码里按各子系统自身的含义多处出现。

## 5. 规模

- 速度探针 1 次（1 次加载）。
- 结构确认：Q3 初筛 ×1，只用于确认阅读顺序与找到缺陷的时间点确实分散，不计入。
  - 判定线。两条都满足才算分散：
    - (i) 首个缺陷写入结果文件之前，已读过至少 3 个非核心模块的 src 文件。（在看结果之前写定。）
    - (ii) 非核心模块里的命中数 ≥3。
  - (ii) 原来是"结果文件的前 8 条发现里，至少 3 条位于非核心模块"。用户在看过 trial-1 结果后把它改成现在的写法（2026-10-14）。理由：原来的 (ii) 量到的是一次批量写入里的排序，量不到阅读顺序。trial-1 按原条件是 2/8，不通过；按新条件，非核心命中 8 个，通过。
  - 不满足：回到结构设计，汇报后再定。
  - 结果：trial-1（rv2，修订 28）Q3 命中 15/20，按新 (ii) 通过；但会话分析表明干草堆没有增加难度，于是改为 rv3。trial-2（rv3，修订 31）Q3 命中 13/20：原样 6/8，搬家 7/12，跨目录 4/7。少命中的两题，trial-1 是靠已修掉的捷径命中的。漏题集中在第一批结果写出之后才读的模块。
  - 初筛结果只用来判结构，不用来调整缺陷内容。
- 正式：Q3 ×3（每次全新 ARW 准备、冷加载）+ Opus ×1；Opus 落在 17–18/20 时补到 ×3。
- 空闲加测：GPU 空闲时 Q3 加测到 5 次。目标事先定为 5，不按中途结果决定；报告同时给前 3 次和全部结果。

## 6. 预计耗时

- 构造：
  - 2 个 Opus 子 agent 并行搬家缺陷，约 1–2 小时。
  - 组装、verify、conformance 约 20 分钟。
  - 多轮 Opus 审查，每轮约 30–40 分钟。
- 正式运行：
  - 探针加结构确认约 30 分钟。
  - Q3 ×3 约 55 分钟。
  - Opus ×1 约 25 分钟，与 Q3 并行。
- 评估：机械计分、盲裁、会话检查与协变量提取约 40 分钟。

## 7. 前置条件

- 工具：`ReviewDeadline` 接受 selection 时限、速度探针、`arw_dimension` 模板渲染与 `--time-limit-seconds`，单元测试全过。
- 构造检查：
  - 每条新 spec 条款至少有一个可执行测试，且全部通过。
  - `rv/v3/verify.sh`：正确版全过；每个缺陷单独注入只破坏自己的检查（已记录的重叠：durationUnits → rescheduleDuration，与 v4.7 相同）；全部注入时恰好缺陷检查失败。
  - conformance 通过；导入白名单、禁用 API、无注释的机械检查通过。
- 多轮 Opus 独立审查：
  - 审查新内容，去掉真问题；每轮修正后重跑上述检查。
  - 专门核对每个搬家缺陷与原题的对等。
  - 几轮后成本过高时停止，交由 Q3 在正常评审中顺带发现，不提示它检查新内容。
- 中性规则，冻结前写定：
  - 冻结后，正式运行在新代码上报出的发现，如果核实为真缺陷，就修正代码进入下一版；在本版计分中按中性处理，既不算 `noOtherSupportedFinding` 失败，也不计分。
  - 核实由一个独立裁决 agent（Opus，effort 不低于 Main）完成，盲化：它只看合并去重后的发现文本、代码和 spec，不知道发现来自哪个模型、哪次重复。
  - Main 再用可执行检查复核；结论和依据写入报告。
- 冻结：独立 agent（不低于 Main）给意见后冻结，记入 `docs/plan.md`。冻结版用独立 manifest（`code-spec-v4.patch` 换为 rv 补丁），v4.7 现行 manifest 不变。
- 每实例：经前端领租约、冷加载，结束后停模型并归还租约；有其他持有者时等待，不抢占。升级 worker 完成前不领租约。

## 8. 判据、停止条件与报告

判据（只用 Opus 的结果）：
- 命中按 ARW 关联计，20 个问题用例合计。
- ≥19/20：命中达标。
- 17 或 18/20：Opus 补到 ×3，按 3 次均值判，均值 ≥17 为达标，否则不达标。
- ≤16/20：不达标。
- clean 误报（口径由用户 2026-10-14 确定）：只算核心 31 个 clean 用例的失败（ARW 判定），以 v4.7 Opus ×3 为基准（每次 0 条）。每次比 v4.7 多出 ≥2 条算明显增加；补到 ×3 时按均值判。无依据的发现和新模块 24 个 clean 用例的失败单列报告，不作判据。

两个分支：
- 命中达标，且误报没有明显增加：150K 档成立。完成加测与报告后停止。
- 命中不达标，或误报明显增加：
  - 先看 Opus 是否被时限中断（按用户 2026-10-14 的二分规则）：
    - 被中断：调大 k，按新 k 重算两个模型的 T，同档重跑。
    - 没被中断：降到 125K 档。
  - β、G 不重估；按 Q3 口径重估的 T 只用于敏感性分析。
  - 调大 k 重跑后仍不达标，或需要降到 125K 时，先停下交用户决定：缺陷已分布到全部模块，降档时去掉模块会同时去掉缺陷，所以降档构造方式需要重新设计。

计分口径：
- 命中：与 v4.7 相同的盲裁流程。各次运行的发现合并、分组、打乱后交裁决 agent；锚点和 v4.7 已有裁决（P7、P2、P16）沿用。
- 误报分两类，分开报告：
  - clean 用例失败（ARW 判定）。
  - 无依据的发现：既不关联任何问题用例，裁决也认为不成立。按中性规则核实为真缺陷的项不计入。
- 可与 v4.7 直接比较的误报数，只取核心 31 个 clean 用例（30 个 core clean 加 `noOtherSupportedFinding`），单列。新模块的 24 个 clean 用例另列。
- 裁决 agent 与 Main 的可执行检查不一致时：
  - "是否真缺陷"以可执行检查为准，能复现即为真。
  - "是否命中某题"以盲裁为准。
  - 每条分歧都写入报告，附双方依据。

预先登记的协变量（报告，不作判据）：
- 每个缺陷宿主文件第一次被读到时的上下文 token 数（取自会话日志）。
- 阅读顺序：目录和文件的首次读取次序。
- 各缺陷首次写入结果文件的时间点。
- 孪生文件：修订 33 已去掉全部孪生写法，不再登记（见 design.md）。
- 压缩：次数，以及每次发生时的上下文位置。
- 中断：是否被时限中断；中断时已写出的发现数。

原样缺陷的合计（预先登记）：
- v4.7 Q3 在这 8 题上的基线：68/80 = 0.85（每题满分 10：selfConflict 10、durationUnits 2、lateFeeState 10、snapEnd 9、accessUntilLarge 10、amenityDup 7、historyShared 10、rescheduleDuration 10）。v4.7 Opus 是 24/24。
- 本档报告 Q3 合计命中率与 0.85 的差，并给出单题方向。
- 分辨率有限：本档 n = 3–5，v4.7 n = 10。单题差 1 次就是 20–33 个百分点，所以不对单题下结论。durationUnits 的 Q3 基线已在地板附近。

Opus 敏感性分析（报告，不作判据）：用各缺陷的首次写入时刻，计算在同口径时限（Opus 的 β、G 按 Q3 口径重估后的 T）之内的命中数。
