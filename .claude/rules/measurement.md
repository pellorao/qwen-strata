# 测量规则

## 设计
- 调参和条件对比每个条件跑 3 次，取算术平均；影响输出的调参参数按「调参选择」的分阶段判定逐步增加样本，最多 11 次。按重要度逐个维度比较，其余条件固定；不组合成矩阵。reviewer 场景的次数见 [reviewer-suite · 场景流程](reviewer-suite.md#场景流程)。
- 不同量化的结果分开计算，不混合均值。基础条件和候选必须在同一安装内对照。
- 记录版本、全部参数、执行顺序、缓存冷暖、加载耗时；复用旧结果必须满足冻结输入、评分和固定条件完全相同。
- **harness 版本**（用户 2026-10-23）：Codex、Claude Code 等 harness 不长期钉在旧版。每项工作（一次 benchmark、一项测量、一次工具验证）开始时换成当时的最新版，开始后到结束固定不变，版本和 SHA 写进绑定；换版后先重跑该 harness 的零模型 mock 门，Claude Code 另跑 `tools.ops.claude_compact_probe`。已结束工作的结果照旧按当时版本记录，不追溯。版本、SHA 和 benchmark 副本路径只在 `tools/strata/harness_pins.py` 一处配置，工具默认就用它，版本或 SHA 不符即拒绝运行；副本按旧 benchmark 计划第 3 节的做法安装（计划已删，见 tag `reviewer-bench-v1` 里的 `benchmarks/multi-model-v1/plan.md`）（只读、不在 PATH 上、核对官方 checksum 或 registry integrity）。冻结计划（`arw-dimension-v1` 等）用它自己记的 Codex 版本的副本，所以旧副本在它的结果可能重新 prepare（如重新计分）期间保留。
- **新版沿用上一版**（用户 2026-10-24）：benchmark 或测量出新版时，运行设计、计分规则和设置默认沿用上一版。只有理由充分才改，例如新版改了规则 A，而规则 A 影响规则 B，所以 B 也要改。每处改动都写明理由。
- **模型地位相同**（用户 2026-10-24）：多模型 benchmark 里 Strata 与其他参与模型地位相同；计划和报告不写成「Strata 与其他模型对照」。
- **多模型 benchmark 不做组间比较**（用户 2026-10-25）：不出比较族、检验、组间差值、高于 / 低于结论和排名；条件完全相同的组（同一场景、模型、harness、强度）的组内统计照旧，另给逐实例的详细结果。比较由外部页面的使用者自己做。
- **空闲时加测**（用户 2026-10-13）：GPU 空闲（租约空闲、无其他排队测量）时，可以给测量提前加测，把有效实例数提高到 10 次或更多，以降低评分随机性。加测不得拖慢其他工作：后续步骤（评估、判定、下一项工作）按原定次数照常进行，加测与之并行，结果出来后再补进报告。目标次数在看到加测结果之前定好并写进计划，不按中途结果决定停不停；报告同时给出原定次数和全部次数的结果。加测优先级最低（用户 2026-10-21）：不占 Anthropic agent 名额，由运行脚本自己跑，Main 的定时检查看状态，不为它单开或保留监督 agent；真实工作需要 GPU 或名额时，加测在当前实例结束后让出。
- Claude Code 测试隔离（用户 2026-10-14）：在测试里用 `qwen-agent` 启动 Claude Code（升级短检查、冒烟检查、测量）时，必须在隔离环境运行，不让它接触额外的规则或配置。具体做法：`CLAUDE_CONFIG_DIR` 指向全新的临时目录，只放测试需要的设置；工作目录放在工程目录外；不加载用户 `~/.claude` 下的 CLAUDE.md、settings、hooks、skills 和 memory。只换 `CLAUDE_CONFIG_DIR` 不够：工作目录在 `/home/pello` 之下时，Claude Code 会把祖先目录的 `/home/pello/.claude/CLAUDE.md` 当项目说明加载，所以要同时加 `--setting-sources user`（user 即全新的 `CLAUDE_CONFIG_DIR`），或把工作目录放在 `/home/pello` 之外（v0.1.45 升级时用假服务器证实，2026-10-18）。`qwen-agent` 自己带的设置（审批、压缩提示 hook）照常传入。从 agent 会话里启动时，用 `env -i` 只给最小环境（PATH、HOME、LANG、`CLAUDE_CONFIG_DIR` 等测试需要的变量），不把父会话的变量和用户的第三方 key 传下去；`qwen-agent` 自身也会去掉父会话的 `CLAUDE*` 变量。剩余途径：同用户进程能读祖先进程的 `/proc/<pid>/environ`，环境变量层面清不掉，只能靠沙箱（2026-10-19）。用真实配置目录运行的 Anthropic 模型 headless（Opus、Haiku 的参考运行和盲答）不适用 `user`：那样会加载真实的 `~/.claude/settings.json`，包括 hook 和权限，所以改用 `--setting-sources ""`，不加载任何设置源（与 v2 相同，2026-10-18）。日常使用不隔离。
- 跨 harness 比较时，各 harness 的设置尽量一致（窗口、压缩点、强度对应、输出上限、提示接入等）；“各用原生设置”不是目标。只有理由充分时才保留差异（比如某个 harness 更适合某个配置），理由写进计划，开跑前用零模型方式核对两边实际生效的值（用户 2026-10-22）。
- 主板 BIOS 升级（7E13v1C）和 CPU 功耗档 Intel Default Settings 前后的速度不直接比较。

## 原则
- 评分或场景有缺陷就修正并出新版本，接受与旧结果不可比；旧结果留作历史基线和噪声估计（用户 2026-10-15）。提选项时先问哪种做法让分数更准确，不把"保持可比、少做工作"当默认推荐；评分审计的目的同样是效度。
- 定口径只论逻辑与效度：该用例应归哪类、算对还是算错、该不该罚；分数怎么变、某版本能否达标不作论据（用户 2026-10-15）。重算分数只检查实现是否正确，并写进报告作参考，不作选口径的理由。口径变化交用户定。

## 计量
- token 只从引擎内部日志计算，逐个实际执行段累加 `read`（未缓存输入）、`reused`（已缓存输入）、`generated`（输出），包括续生成、压缩和 guardian 请求。用 `tools/metrics/strata_tokens.py` 计算。API usage 只用于对账。
- 缺失的计数记为未知，不填零，也不用 API 数值补。有依据时可以给出上下界范围，并说明假设。
- 每次模型运行后统计四项速度（token/s），工作时间用 `tools/metrics/review_work_time.py` 计算：
  - 引擎输入 = read / 输入处理秒数
  - 引擎输出 = generated / 解码秒数
  - 任务平均输入 = 累计 read / 工作秒数
  - 任务平均输出 = 累计 generated / 工作秒数
- 多个实例的速度按总 token ÷ 总耗时汇总，不取各实例速度的算术平均（用户 2026-10-22）。
- 工作时间包括推理、工具执行与等待、任务内自动恢复；不包括停机，以及回合结束后等待下一条指令的空闲。
- 耗时一律从模型开始正式工作（首个请求进入引擎）算到任务完成，不含部署、模型加载与预热、批次准备（用户 2026-10-13）。
- 报告固定保留逐实例表（用户 2026-10-13）：耗时、三类 token（read / reused / generated）、两种口径的输入输出速度——模型直接速度（上面的引擎输入、引擎输出）和用户感知速度（上面的任务平均输入、任务平均输出）。原始明细删除后仍要能据此比较速度，所以写进 `summary.md`/`summary.json`，不只留在 `.tmp/`。
- Opus 等 API 参照：token 按 API usage 记录并注明来源；用户感知速度同样从开始工作算到完成。模型直接速度只要求尽量准确，数据来源不固定（用户 2026-10-14）。子 agent 会话记录的流式 usage 只有占位值（`output_tokens` 8），不能用来算速度；探针做法见[测量附注](../../docs/measurement-notes.md#opus-参照速度探针)。
- 等效费用（美元，3 位小数，只用于用户指定的报告）=(未缓存 × 0.15 + 已缓存 × 0.016 + 输出 × 0.47) / 1e6。三类 token 任一未知，费用即未知。

## 评分口径
调参和 benchmark 用不同的评分口径，按场景选择，不混用（用户 2026-10-12）。ARW reviewer 场景的口径（证据 F2、k 分档计分、罚分、修复）见 [reviewer-suite · 评分](reviewer-suite.md#评分)。

- 有歧义的题（用户 2026-10-25）：场景用例两种解读都说得通、又分不出优劣的，删掉或换成没有歧义的题，不在裁决说明里硬选一种。答案键外的 finding 删不掉，这时歧义若出在场景文本，就改场景文本消除（如 multi-model-v2 的 SR v4.4、v4.5）；裁决说明只写有明确依据、能判出优劣的读法，依据要写出来。
- 同一次测量的全部场景和实例用同一套评分规则；规则在测量中途变化时，全部跑完后按最新规则统一重评一次（不涉及模型），不逐批混用（用户 2026-10-12）。
- 调参选择（用户 2026-10-12）：调参前先判断参数在理论上是否影响模型输出，依据写进报告。
  - 不影响输出的参数（只影响放置、调度、投机猜测，如 adapt-*、kv-resident、pool、pcie、prefill、显存预留、CPU 辅助、spec、spec-min-p；greedy 下草稿只在与模型所选 token 一致时保留）：按引擎输出 tok/s 选择。分数只用来发现异常（如某条件全部实例明显失常、可能是程序错误），不参与选择。
    - 排程与汇总（用户 2026-10-12，参照 Strata `tools/agent_turns_bench.py`）：条件按块交替排程（如 AA BB BB AA，多条件时按轮次反转顺序），抵消主机状态随时间的漂移（温度、后台任务、内存碎片等，重新加载清不掉）；每次换条件都部署、加载并预热。按同一负载的逐回合（逐请求）速度比取中位数，不用整段均值。只用于今后的调参，不追溯已有结论。
  - 影响输出的参数（采样、窗口与压缩等）：分数为主，用分阶段判定（用户 2026-10-12）：
    - 样本数依次为 3、5、7、9、11，每轮给仍未判定的条件各加 2 个实例（同样预热后运行、同一冻结输入），每轮后判定。增加的实例算有效样本，保留全部实例，不按得分挑选。
    - 标准误按该次测量的实例分计算：`SE = sqrt(s1²/n1 + s2²/n2)`，d 为两条件均值差。离群实例计入计算，同时单列说明原因。
    - 分出高下（O'Brien–Fleming 边界）：|d| > c·SE，c 依样本数为 5.0 / 3.6 / 2.9 / 2.5 / 2.25（= 2.25·sqrt(5/轮次)）。前几轮门槛高，挡住小样本标准差估计不准带来的早期误判。已判定落后的条件退出。
    - 多候选（3–6 个，用户 2026-10-12；采样维为 3 个）：每轮把仍在采样的候选各与当前领先者（均值最高）比较。落后超过 c·SE 的出局；|d| + 2·SE < δ 的记为并列，不再加样本，最后与领先者一起按速度选；其余继续，领先者和它们下一轮各加 2 个实例（镜像排程 a b c c b a，逐轮反向）。c = c_final(k)·sqrt(5/轮次)，k 按开始时的候选数固定，不因出局放宽：c_final 为 2 个 2.25、3 个 2.6、4 个 3.0、5 个 3.3、6 个 3.4。理由：与"观测到的领先者"比较是挑最大值后的比较，Bonferroni 不够；上表按模拟标定，使全部候选真实相同时误淘汰任一候选的概率仍约 6%（模拟依据见[测量附注](../../docs/measurement-notes.md#分阶段判定的模拟依据)）。
    - 等效停止：|d| + 2·SE < δ 时判定等效，停止增加，按引擎输出 tok/s 选择。δ = 0.05（分数为 0–1 刻度；用户 2026-10-12：分差小于 0.05 对实际使用无影响，模拟依据同上）。
    - 到 11 个实例仍未判定：停下，分析原因（波动来源、离群、负载是否合适），交用户决定。
    - 报告写明每轮的样本数、d、SE、边界和判定。
  - 负载（用户 2026-10-12）：调参默认用答案可机械判定、单实例含多题以压低波动的专用负载（ARW 评分不确定性高，Spec Readiness 组内标准差可达 0.12–0.16）；ARW 场景用于 reviewer 能力验证和 benchmark，只有 10 次组内 SD ≤ 0.068 的场景才考虑用于调参（[场景流程](reviewer-suite.md#评分)，用户 2026-10-13）。
    - 单实例时长（暂行，用户 2026-10-12）：普通调参场景每个 Strata 实例运行不超过 10 分钟（不含部署与加载）；需要压缩的场景（窗口负载）可适当放宽。若发现它让调参整体变慢，再放宽。为达到上限可减题或把难度减为 3 档。
    - 预热与连跑（用户 2026-10-12）：每次加载模型后先用同一负载做一段不计分的预热（采样负载完整做一遍题），让前缀缓存和自适应参数进入稳态，使缓存均匀影响所有实例，也更接近常驻服务的真实工作点。分数类参数同一条件的实例排在一起连跑，实例之间只用全新会话隔开、不重新加载，换条件时部署、加载并预热；速度类参数见上文按块交替。报告检查同一条件内实例分和速度是否随运行顺序有趋势，并看引擎日志已缓存输入（reused）比例是否各实例一致；有趋势或缓存容量不足导致命中不均时，加长预热或调整后重跑受影响部分。
    - 分段清空上下文（用户 2026-10-12）：若"做几题后清空上下文再继续"能节省总时间，大多数调参场景都这样运行（每段一个全新会话，全部段合起来计一个实例分）；测长上下文和压缩本身的负载除外。
    - 硬时限（用户 2026-10-12）：做题负载都设硬时限，到时强制停止模型（杀掉会话的整个进程组，断开连接使 Strata 取消生成，并确认引擎空闲后才继续），按已写出的结果评分，未写入的题记 0 分；超时本身不使实例无效，报告写明超时会话数和已答题数。提示必须写明有硬时限、每题做完立即写入指定文件。采样负载按组设硬时限：组时限 = 组内各题档之和 × `group_seconds_per_tier`（暂定 30 秒，按试跑实测调整）；每组一个新会话，慢组不挤占其他组。窗口实例 1800 秒覆盖整段对话。Opus 标定同样按截止时刻的工作区快照评分。
    - 按组运行（用户 2026-10-12，试跑和正式实例都用）：混组（用户 2026-10-12）——题按（方向，档）排序后蛇形轮流发到 ceil(N/`group_size`) 组（1→G 再 G→1，各方向各档题数相同时各组档和相同），同组混入不同方向和难度，组顺序固定、不随机（实现 `sampling_bank`、`codex_workload.run_sampling` 已于 2026-10-24 删除（用户关闭 v5 题库），可从 git 历史恢复，提交 585e693）。每组一个全新 Codex 会话，工作区只放本组题，模型可逐题做也可一起做。组耗时和组 token 精确（token 按组的引擎日志区间切分）；每题耗时只按结果文件写入间隔近似。按题计分；同组题共享会话、不独立，报告另给以组为聚类的标准误和设计效应。会话发生压缩则该组无效，在新会话中重跑一次，仍压缩则实例效果检查失败。
    - 固定套题（用户 2026-10-12）：正式实例全部使用同一套固定题目和顺序，不随机抽题（随机抽题使实例间分数不可比）。选题从试跑数据挑出（目标题数、试跑正确率区间、耗时），可以只剩约 20 题。
    - 隔离：每个会话一个临时工作目录，题面从原位置复制进去；工具命令只能读该目录（Codex 原生权限 profile，见 `tools.tuning.codex_workload.isolation`），提供方 key 不进命令环境。开跑前 `codex_workload check` 用本地模拟模型跑 `tools.tuning.sandbox_probe`，答案库、工程、CODEX_HOME、`/tmp`、`/mnt/c` 必须读不到；越界调用检查保留为兜底：被标记的调用不自动判实例无效，按结果在会话检查中逐条判定，只有确实看到工作区外内容（可能影响评分）才判无效，被沙箱拦下的只记录（用户 2026-10-12 环境查询按结果判定的同一口径）。
  - 工作时间（ARW 等场景）不确定性大，不作强选择依据（用户 2026-10-11）。

## 会话分析（用户 2026-10-14）
- 会话分析是优化模型参数和测试场景的必要手段，能做就做。试跑、初筛、正式测量和调参实例都要分析 Strata 的实际会话：它按什么顺序、以多大块读入材料；每道题或每个问题是怎么解出或找到的，靠对照、执行代码还是搜索；每个失败卡在哪一步；参数改变时，行为上有什么变化。判断场景是否达到设计目的、下一步改题或调参，都以这个分析为依据，不凭猜测模型的想法。结论写进进度记录和报告。
- 控制 token 消耗，做法和安全检查一样：先用脚本过滤掉无用数据，再让 agent 分析过滤后的内容。脚本负责提取动作序列（命令、读取范围、写入时刻和内容）、可见消息，以及与答案键的对应关系；不分析模型的推理内容（用户 2026-10-14：结论靠动作序列已足够，提取推理会触发 Anthropic 安全过滤）。重复的文件内容、完整工具输出和元数据不进入分析。只有过滤后的内容不足以下结论时，才按事件号调取对应的动作或消息原文。过滤脚本放进 `tools/`，复用已有的 `inspect_session`（已归档在 tag `reviewer-bench-v1`），能扩展就不新建。

## 失败与重跑
- 先评估错误影响范围再决定重跑：影响该场景全部重复，修复后重跑全部；只影响当前一次，只重跑这一次；不影响结果，只修复不重跑。
- 保留原始失败、恢复过程和额外消耗。不按得分挑选重跑。
- 多跑的实例（补跑、因误判引出的重跑、并行调度多出的尝试）只要有效、且不是因为已有分数差才加跑，就和预登记的实例效力相同，全部进最终实例集合，不截取前 n 个（用户 2026-10-23）。加跑如果由分数触发，加跑的实例不进主统计，并在报告中说明。
- 有效性判据只用因果上必需的条件；每多加一条旁证条件，都会额外排除一些实例，而且被排除的往往和结果相关（例如跑得久的实例才会遇到时限提醒），造成选择偏差（用户 2026-10-23）。
- 压缩前后的请求超过压缩阈值（压缩前最后一个请求 = 阈值 + 一回合增量，压缩请求本身也在阈值附近）是正常现象，不作为实例无效的理由，只记录最大请求输入（用户 2026-10-24，确认窗口维决定 A）。

## 存放
- `.tmp/`：运行副本、完整会话、请求响应、日志、逐项裁决、进行中的进展。
- 每个实例跑完就清理残留（用户 2026-10-20，防止磁盘撑爆）：删掉场景仓库副本、prep、工作目录、`/tmp` 下属于本实例的条目，以及沙箱留下的占位目录。保留答案（报告），以及与临时目录无关的记录：会话历史（stream、rollout、machine.jsonl）、instance.json、日志、检查结果。删除前先确认会话检查、unexpected_changes 这类比对需要的内容已经产出。
- `reports/`：只放**已结束**测量的摘要（`summary.md`）和可重算的完整精度数据（`summary.json`）。不放原始明细，测量未结束不发布。新报告写入 `reports/<版本或主题>/`；已有报告保留原路径。
- （v1 benchmark 的工具链已归档在 tag `reviewer-bench-v1`，这一条只作历史口径。）多模型 benchmark 的 `summary.json` 和公开结果文件（`benchmark-results.json`）只经工具链生成：`bench_records` → `bench_score` → `benchmark_summary` → `benchmark_export`，补测、加测也一样，不用临时脚本代写（用户 2026-10-23：第三阶段补充曾由临时脚本写出，耗时只到 0.1 分钟、没有引擎速度）。工具不支持新配置或新阶段时先改工具，再生成。
- `benchmarks/`：场景、规则、冻结输入的源文件。
- 长期文档和报告不得依赖 `.tmp/` 才能理解或重算。删除明细后无法重放的部分，要写明边界。
- 展示格式：已有表格的单位和精度不批量修改；任何舍入都不能把非零值显示成零。
- 耗时单位（用户 2026-10-13）：reviewer 场景，以及任何平均耗时达到 100 秒的场景，耗时以分钟显示、保留一位小数（如 22.3 分钟），沿用 profile 报告的分钟格式；速度（tok/s）不受影响。
