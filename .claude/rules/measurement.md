# 测量规则

## 设计
- 每个条件跑 3 次，取算术平均；影响输出的调参参数按「评分口径」的分阶段判定逐步增加样本，最多 11 次。按重要度逐个维度比较，其余条件固定；不组合成矩阵。Spec Readiness 的 medium/high × 100K/150K 是已批准的例外。
- 不同主机、不同量化的结果分开计算，不混合均值。基础条件和候选必须在同一主机内对照。
- 记录版本、全部参数、执行顺序、缓存冷暖、加载耗时；复用旧结果必须满足冻结输入、评分和固定条件完全相同。

## 计量
- token 只从引擎内部日志计算，逐个实际执行段累加 `read`（未缓存输入）、`reused`（已缓存输入）、`generated`（输出），包括续生成、压缩和 guardian 请求。用 `tools/metrics/strata_tokens.py` 计算。API usage 只用于对账。
- 缺失的计数记为未知，不填零，也不用 API 数值补。有依据时可以给出上下界范围，并说明假设。
- 每次模型运行后统计四项速度（token/s），工作时间用 `tools/metrics/review_work_time.py` 计算：
  - 引擎输入 = read / 输入处理秒数
  - 引擎输出 = generated / 解码秒数
  - 任务平均输入 = 累计 read / 工作秒数
  - 任务平均输出 = 累计 generated / 工作秒数
- 工作时间包括推理、工具执行与等待、任务内自动恢复；不包括停机，以及回合结束后等待下一条指令的空闲。
- 等效费用（美元，3 位小数，只用于用户指定的报告）=(未缓存 × 0.15 + 已缓存 × 0.016 + 输出 × 0.47) / 1e6。三类 token 任一未知，费用即未知。

## 评分口径
调参和 benchmark 用不同的评分规则，按场景选择，不混用（用户 2026-10-12）。

| | 调参（参数维度、资源校准等条件对比） | benchmark、reviewer 能力验证 |
|---|---|---|
| 目的 | 比较条件，分数只反映主要体现模型能力的因素 | 与 ARW 自己的结果直接对比 |
| 罚分 | 排除 ARW 一切"有报告诊断就整体 ×0.9"类罚分，取扣罚前分（`scoreBeforePenalty`） | 完全按 ARW 原版，罚分照算 |
| 格式错误 | 不计入分数，只记录并标在分数旁 | 计入，按 ARW 规则影响分数 |
| 可机械修复的错误 | 修复成可评分副本，只为让报告能被评分 | 修复成可评分副本，记录"做过格式修复"，再按 ARW 规则 ×0.9 |
| 无法机械修复的错误 | 按 ARW 原版判定，只影响其本身的得分项，不再整体罚分 | 按 ARW 原版处理 |

- 理由（用户 2026-10-11）：低频、随机的格式和报告诊断样本太少，不能说明能力差异，在调参中只是噪声；benchmark 需要保持 ARW 原版口径。
- 证据定位的含义只有一个，以冻结 ARW 的定义为准，调参和 benchmark 相同，修复不得改变含义（用户 2026-10-12）：
  - Commit Audit（角色文档 `commit-audit-reviewer.md`）：`lines` 是数组，元素为正整数（单行）或 `[起,止]`（闭区间）。所以 `"lines":[12,20]` 表示第 12 行和第 20 行两行，`[[12,20]]` 才是区间。
  - Code Review markdown（`reviewer-capability-scenarios.md#locator-matching`）：`完整路径:行,起-止`；同一对反引号内仅含行号的片段归属最近的文件路径；新文件必须写出完整路径。
  - Spec Readiness（`spec-readiness-reviewer/findings.md`）：以 Input 完整 `filePath` 开头，后接行号或范围。
- 可机械修复（在上述定义下有唯一含义、只是写法不合规）：`lines` 写成数组外的单个整数（补成 `[n]`）；markdown 报告第一个编号或 `- ` 条目之前的标题和说明段；正文中省略目录、能唯一对应冻结源中一个文件且行号在文件范围内的简写证据引用。只纠正写法，不改判断、finding 或证据指向；修复在绑定原实例的独立副本中进行，往返断言确认只改了这些位置，原报告不改。符合 ARW 定义的写法（如顶层 `[a,b]`）按定义解释，不做修复，即使模型可能本意是区间。
- 无法机械修复：行号越界、证据写成非定位内容（如时间比较）、简写对应多个文件。
- 修复不改变样本数，每个实例无论得分高低都用同一套规则。
- 同一次测量的全部场景和实例用同一套评分规则；规则在测量中途变化时，全部跑完后按最新规则统一重评一次（不涉及模型），不逐批混用（用户 2026-10-12）。
- 调参选择（用户 2026-10-12）：调参前先判断参数在理论上是否影响模型输出，依据写进报告。
  - 不影响输出的参数（只影响放置、调度、投机猜测，如 adapt-*、kv-resident、pool、pcie、prefill、显存预留、CPU 辅助、spec、spec-min-p；greedy 下草稿只在与模型所选 token 一致时保留）：按引擎输出 tok/s 选择。分数只用来发现异常（如某条件全部实例明显失常、可能是程序错误），不参与选择。
    - 排程与汇总（用户 2026-10-12，参照 Strata `tools/agent_turns_bench.py`）：条件按块交替排程（如 AA BB BB AA，多条件时按轮次反转顺序），抵消主机状态随时间的漂移（温度、后台任务、内存碎片等，重新加载清不掉）；每次换条件都部署、加载并预热。按同一负载的逐回合（逐请求）速度比取中位数，不用整段均值。只用于今后的调参，不追溯已有结论。
  - 影响输出的参数（采样、窗口与压缩等）：分数为主，用分阶段判定（用户 2026-10-12）：
    - 样本数依次为 3、5、7、9、11，每轮给仍未判定的条件各加 2 个实例（同样预热后运行、同一冻结输入），每轮后判定。增加的实例算有效样本，保留全部实例，不按得分挑选。
    - 标准误按该次测量的实例分计算：`SE = sqrt(s1²/n1 + s2²/n2)`，d 为两条件均值差。离群实例计入计算，同时单列说明原因。
    - 分出高下（O'Brien–Fleming 边界）：|d| > c·SE，c 依样本数为 5.0 / 3.6 / 2.9 / 2.5 / 2.25（= 2.25·sqrt(5/轮次)）。前几轮门槛高，挡住小样本标准差估计不准带来的早期误判。已判定落后的条件退出。
    - 多候选（3–6 个，用户 2026-10-12；采样维为 3 个）：每轮把仍在采样的候选各与当前领先者（均值最高）比较。落后超过 c·SE 的出局；|d| + 2·SE < δ 的记为并列，不再加样本，最后与领先者一起按速度选；其余继续，领先者和它们下一轮各加 2 个实例（镜像排程 a b c c b a，逐轮反向）。c = c_final(k)·sqrt(5/轮次)，k 按开始时的候选数固定，不因出局放宽：c_final 为 2 个 2.25、3 个 2.6、4 个 3.0、5 个 3.3、6 个 3.4。理由：与"观测到的领先者"比较是挑最大值后的比较，Bonferroni 不够；上表按模拟标定，使全部候选真实相同时误淘汰任一候选的概率仍约 6%（`tools/tuning/staged_decision.py` 的 `simulate`）。
    - 3 候选模拟（组内标准差 0.04 / 0.06，各 3000 次）：全部相同时平均 27 / 32 个实例，误淘汰约 6%，判等效 52% / 4%，其余到 11 个未判定；一个高 0.10 时 18 / 25 个实例判出（100% / 84%）；一个高 0.06 时判出 73% / 29%。组内标准差是耗时和判定率的主因。
    - 等效停止：|d| + 2·SE < δ 时判定等效，停止增加，按引擎输出 tok/s 选择。δ = 0.05（分数为 0–1 刻度；用户 2026-10-12：分差小于 0.05 对实际使用无影响）。
    - 依据：模拟（组内标准差 0.04，真实差为 0 时误判约 6%、72% 提前判为等效，平均样本 8.4；真实差 0.06 时判出率约 88%）。
    - 到 11 个实例仍未判定：停下，分析原因（波动来源、离群、负载是否合适），交用户决定。
    - 报告写明每轮的样本数、d、SE、边界和判定。
  - 负载（用户 2026-10-12）：调参不使用 ARW 场景（评分不确定性高，Spec Readiness 组内标准差可达 0.12–0.16）。用答案可机械判定、单实例含多题以压低波动的专用负载；ARW 只用于 reviewer 能力验证和 benchmark。
    - 单实例时长（暂行，用户 2026-10-12）：普通调参场景每个 Strata 实例运行不超过 10 分钟（不含部署与加载）；需要压缩的场景（窗口负载）可适当放宽。若发现它让调参整体变慢，再放宽。为达到上限可减题或把难度减为 3 档。
    - 预热与连跑（用户 2026-10-12，取代"每个实例冷启动"）：每次加载模型后先用同一负载做一段不计分的预热（采样负载完整做一遍题），让前缀缓存和自适应参数进入稳态，使缓存均匀影响所有实例，也更接近常驻服务的真实工作点。分数类参数同一条件的实例排在一起连跑，实例之间只用全新会话隔开、不重新加载，换条件时部署、加载并预热；速度类参数见上文按块交替。报告检查同一条件内实例分和速度是否随运行顺序有趋势，并看引擎日志已缓存输入（reused）比例是否各实例一致；有趋势或缓存容量不足导致命中不均时，加长预热或调整后重跑受影响部分。
    - 分段清空上下文（用户 2026-10-12）：若"做几题后清空上下文再继续"能节省总时间，大多数调参场景都这样运行（每段一个全新会话，全部段合起来计一个实例分）；测长上下文和压缩本身的负载除外。
    - 硬时限（用户 2026-10-12）：做题负载都设硬时限，到时强制停止模型（杀掉会话的整个进程组，断开连接使 Strata 取消生成，并确认引擎空闲后才继续），按已写出的结果评分，未写入的题记 0 分；超时本身不使实例无效，报告写明超时会话数和已答题数。提示必须写明有硬时限、每题做完立即写入指定文件。采样负载按组设硬时限：组时限 = 组内各题档之和 × `group_seconds_per_tier`（暂定 30 秒，按试跑实测调整）；每组一个新会话，慢组不挤占其他组。窗口实例 1800 秒覆盖整段对话。Opus 标定同样按截止时刻的工作区快照评分。
    - 按组运行（用户 2026-10-12，试跑和正式实例都用，取代逐题门控）：同一方向内按档从低到高依次填满 `group_size` 题为一组，方向内剩余的题自成一组；组顺序固定为方向依次、方向内档由低到高，不随机。每组一个全新 Codex 会话，工作区只放本组题，模型可逐题做也可一起做——允许同类题批量解，因为调参只测参数效果，不测逐题解法能力，这样能快速跑完很多题。组耗时和组 token 精确（token 按组的引擎日志区间切分）；每题耗时只按结果文件写入间隔近似。会话发生压缩则该组无效，在新会话中重跑一次，仍压缩则实例效果检查失败。
    - 固定套题（用户 2026-10-12）：正式实例全部使用同一套固定题目和顺序，不随机抽题（随机抽题使实例间分数不可比）。选题由 `sampling_bank choose` 从试跑数据挑出（目标题数、试跑正确率区间、耗时），可以只剩约 20 题。
    - 隔离：每个会话一个临时工作目录，题面从原位置复制进去；工具命令只能读该目录（Codex 原生权限 profile，见 `tools.tuning.codex_workload.isolation`），提供方 key 不进命令环境。开跑前 `codex_workload check` 用本地模拟模型跑 `tools.tuning.sandbox_probe`，答案库、工程、CODEX_HOME、`/tmp`、`/mnt/c` 必须读不到；越界调用检查保留为兜底：被标记的调用不自动判实例无效，按结果在会话检查中逐条判定，只有确实看到工作区外内容（可能影响评分）才判无效，被沙箱拦下的只记录（用户 2026-10-12 环境查询按结果判定的同一口径）。
  - 工作时间（ARW 等场景）不确定性大，不作强选择依据（用户 2026-10-11）。

## 失败与重跑
- 先评估错误影响范围再决定重跑：影响该场景全部重复，修复后重跑全部；只影响当前一次，只重跑这一次；不影响结果，只修复不重跑。
- 保留原始失败、恢复过程和额外消耗。不按得分挑选重跑，重跑不算作额外有效样本。

## 存放
- `.tmp/`：运行副本、完整会话、请求响应、日志、逐项裁决、进行中的进展。
- `reports/`：只放**已结束**测量的摘要（`summary.md`）和可重算的完整精度数据（`summary.json`）。不放原始明细，测量未结束不发布。
- `benchmarks/`：场景、规则、冻结输入的源文件。
- 长期文档和报告不得依赖 `.tmp/` 才能理解或重算。删除明细后无法重放的部分，要写明边界。
- 展示格式：已有表格的单位和精度不批量修改；任何舍入都不能把非零值显示成零。
