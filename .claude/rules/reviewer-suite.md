# ARW Reviewer 测量规则

## 合同
- 直接使用冻结 ARW 的原场景、完整规则、准备 / 生成 / 评分入口和 Reviewer 运行层。不裁剪用例。确实需要改变合同时，先列出差异并取得同意。
- 评分按场景分两种口径，定义见[测量规则 · 评分口径](measurement.md#评分口径)（用户 2026-10-12）：调参取 ARW 扣罚前分，格式与报告诊断只记录；能力验证和 benchmark 完全按 ARW 原版罚分。两者都先由 `tools.reviewer.repair_reviewer_report` 在绑定原实例的独立副本中修复可机械修复的错误（数组外的单个整数 `lines`；markdown 首个条目前的前言；能唯一对应文件的简写证据引用；证据定位含义以 ARW 定义为准，顶层 `[a,b]` 是两行，不改写为区间），让报告能被评分；benchmark 另记录做过修复并照 ARW 规则 ×0.9。原报告不改，修复处数和类型标在分数旁。
- 计分只经 `tools/reviewer/arw_native.mjs` 或 `tools.reviewer.single_scenario_score`，不直接调用 ARW 的计分脚本：这两个入口会先给物化副本补上本工程的评分规则升级（证据 F2 与两类计分，`arw-patches/scoring-f2.patch`），并按答案键 sha 绑定 `judgment/` 下的 A 类标记。答案键没在 `judgment/registry.json` 登记就报错，新场景版本（含草稿）计分前先登记，未标定的登记为 `all-B`。
- 所有场景的能力判定都用相对口径：Q3 分数与同场景同版本的 Opus 参考分之比（Q3 / Opus），不设绝对分数通过线（如 0.75）；报告给出两者分数、比值和双方 0 命中的用例（用户 2026-10-13）。
- 重构场景时，在不影响质量的前提下尽量少用付费模型（总则「少用付费模型」，用户 2026-10-13）。例如：只改答案键或 placement 时，用已有回答重新评分，不重跑 Opus；裁决中能机械判定的部分（证据行是否落在 placement、文件是否存在、重复 finding）先由脚本处理，只把需要语义判断的候选交给付费模型；Opus 参考每个冻结版本只跑一次，改版前先用无模型检查和 Q3 运行排除夹具与评分机制问题。
- 盲裁只裁有变化的部分（用户 2026-10-13）：已裁过的候选，若所属用例的答案键、placement 和裁决 brief 都没变，沿用原裁决，不重复盲裁；只把新回答产生的候选和受改动影响的用例的候选送盲裁。若这样仍消耗较多，再考虑只派一个裁决者。增量盲裁池混入约 10–15 个已裁候选作锚点（对裁决者隐藏来源与原判，覆盖 matched/not-matched 和多个用例），报告锚点数与一致率；不一致时扩大复核。
- 补充或新增问题用例时，优先选审计或夹具本身能证明、非某一方模型独家发现的缺陷；若取自某个被测模型回答里的线索，报告给出含/不含该用例的两套分数与 Q3/Opus，并注明来源（用户 2026-10-13 同意）。
- 场景时长（设计规则，用户 2026-10-13）：Strata（rtx3080ti 当前默认部署）跑一个 reviewer 场景实例（含该实例全部子线程，如 Spec 的 RM+AP），工作时间每次不得超过 30 分钟，平均最好在 20 分钟以内。这是场景设计与验收的约束：设计新版本时控制 Input 规模和用例数，冻结后若 Q3 有实例超过 30 分钟或均值明显超过 20 分钟，先缩减场景再定版。不改 ARW 原版的时限提醒与中断，也不在运行中途强杀。加难度应靠推理深度（跨文件对照、隐含缺陷）。
- 阅读量维度（Code Spec、Code Standards 等代码题，用户 2026-10-14）：从大量代码中找出问题是 reviewer 的真实工作，大阅读量是正确的出题方式；真实审查可能面对约 300K 材料，审查中压缩不加限制。阅读量作为独立难度维度，与推理难度分开测，不在同一版本里同时改。目标阅读量 100K–150K，工作时长 20 分钟以内：到时限停止答题（用 ARW 原版的时限与中断实现，不强杀），只按截至时刻已写出的结果计分；时限和"每确认一个问题就追加写入结果文件"都写进 handoff 提示。时限公式（用户 2026-10-14）：T 秒 = B ×（1/P + k/G）/ β，B 为输入规则和代码总字节，β 为该模型在该输入上的字节/token（B ÷ 引擎报告的输入 token），P、G 为该机器加该模型的读入、生成速度（每批测量前用短探针测一次，不按单次运行取值），k 为每个输入 token 允许的生成 token；k 按"rtx3080ti 上 Q3 时限 = B/10K 分钟"反推（估计约 2），β 首次实测后校正一次再固定。Opus 用同一公式和它自己的 P、G、β。Opus 若在自己的时限内也找不到大部分缺陷，先调大 k，不把被时限压低的比值当结论。干草堆用真实相关的代码，缺陷不能靠 spec 关键词搜索直接定位（防搜索捷径），也不能有局部线索。Opus 参考窗口更大、压缩更少，接受这一差异（测整体后端表现），报告注明。
- 难度设计（用户 2026-10-13）：推理步骤数是智力难度的关键。加难度时提高每个缺陷从 spec 到判定所需的推理步数；调整按 AGENTS.md 的二分法：试跑显示太容易，平均步数至少 +2（上界未知时大步探界），发现太难就取与上一个"太容易"点的中点（用户 2026-10-14），不做 +1 以内的小步试探。步骤类型同样决定难度：推算具体值（单位、边界、时间点）或依赖语言语义（类型转换、展开覆盖顺序、引用共享、异步时序）的步骤，比对照 spec 逐行比对的步骤难得多；加难度时步数和步骤类型两边同时加（用户 2026-10-14）。步数指规则网络中的推理步数（从事实到判定违规需要经过的规则应用、优先级或覆盖判断、条件分支的个数），不是代码执行或引用追踪的步数：后者能被执行代码直接压平，一万步和一步没有区别；规则网络的推理要用代码复现就得先完成很强的数据建模，答题者真有这个能力，用代码做也可以（用户 2026-10-14）。步数按"有效步数"计：从 spec 到判定的最短推理路径，不是设计者写下的链长。不得留捷径，缺陷所在行和它附近不能有局部线索（可疑写法、命名、注释、与 spec 字面直接对照），否则答题者跳过中间步骤就能判定（用户 2026-10-14）。"局部线索"指缺陷附近能提示问题的东西；缺陷行本身写得自然、只有懂语言语义或把数据流追到最终结果才能判错的，不算捷径（例：先展开原对象再展开 `delete` 过字段的新对象，被删字段的原值保留）。一套题不能只有一种题型或一种难度：以这类长链、无线索的缺陷为主，同时保留一部分推理步数少但问题隐晦的缺陷（例：`save` 前少写 `await`），以及少量保底题（用户 2026-10-14）。design.md 为每个用例写明为什么每一步都不可跳过。能执行代码的答题者会用运行代码压平静态推理链（因素探针 2026-10-14：约 20 步的容易链与 4 步链检出相同），所以难度要放在执行代码绕不过去的推理上；首选做法是参考 Spec Readiness，把 spec 写成有优先级、覆盖、条件分支和例外的规则网络，判定违规需要在网络中正向或反向探索，优先级和覆盖关系必须在 spec 中写明以保证答案唯一（用户 2026-10-14）。因素探针（分开测量步数、步骤类型等难度因素的小组题）不是 ARW 场景，不受 ARW 用例数等合同限制，可按测量需要拆分；每组 Q3 跑多次。Opus 只在 Q3 结果还不能下结论的组上跑：Q3 在某组已经全部检出（该因素对 Q3 无效），这组就不需要 Opus（用户 2026-10-14）。答案键为每个问题用例写明推理链和步数，审计核对步数与唯一性。草稿难度用 Q3 单次试跑校准，不必跑满：第一次得分就很高说明难度一定不够，直接回到设计继续加难；试跑得分低不能直接定版（可能只是单次波动），只有试跑得分已明显下降，才进入审计、冻结和正式测量（正式测量仍按原定次数）。难度目标是 Opus 稳定找到大部分缺陷，同时 Q3 明显下滑；审计阶段的 Opus-high 盲答找不到的缺陷，先查歧义或过偏，不当作难度合适。
- 场景分工（用户 2026-10-14）：各场景的难度来源要不同，避免考察内容重合。Code Standards 中难度来自规则网络的题最多占一半，其余守住代码质量与设计标准（复用与归属、同形异质、`writing.md` 结构问题、语言语义）。发现重复或高度相似代码并合并是重点能力，这类题约占 1/3 或更多；负面例子（看起来相似、实际不应合并的代码，作 clean 孪生）与正面例子 1:1，每道重复题配一个，design.md 写明不该合并的理由（反例输入或归属、演化理由）。不出逐字或几乎逐字相同的重复：机械比对就能找到，检验不了智能；只出写法不同但行为等价、参数化后可合并、同一规则不同表达的重复，并用去空白、去标识符后的文本比对自检，能直接匹配的要改写。design.md 用配比表写明每题的难度来源。
- 权限沿用原生设置：`:read-only` 加显式写路径，审批走 on-request / auto_review；网络、搜索、MCP 保持原生。不额外收紧，不启用可选的严格隔离。
- 正式能力测量之前，先确认所需的安全证据（原生沙箱行为、auto_review 审批质量）。见 `docs/plan.md`。

## 执行
- 时限按累计工作时间计：初审 55 分钟提醒、60 分钟中断；同线程后续沟通 10 分钟提醒、15 分钟中断。提醒和中断使用原版 ARW 接口。
- 能力验证和 benchmark 中，早停接续使用 ARW 原版运行层的接续机制，本工程驱动不另发继续指示（用户 2026-10-11：最大限度还原 ARW，便于与 ARW 自己的结果直接对比）。到达原版 10 / 5 次早退暂停点时，停下交给用户决定。
- 能力验证和 benchmark 由 ARW 自己的 Strata provider 持有独占并启动模型（打了本工程接口补丁的 ARW，`selection.model_owner = "arw"`），引擎参数用安装目录的每机每量化默认值。每批开跑前 `arw_measure` 经租约停掉常驻模型，批从冷加载开始；实例之间不停模型，只允许 Strata 精确前缀缓存的复用，不复用上一个实例的上下文；token 按派发时刻切分的引擎日志段计算（用户 2026-10-11）。
- 测量交接末尾追加冻结的测量说明（不发送中途消息、不需要运行标识、禁止查询环境变量和平台身份），记录 SHA；只追加，不改原版交接和 Role。
- Reviewer 的命令环境用 Codex 原生 `shell_environment_policy.exclude` 去掉 `STRATA_API_KEY`（用户 2026-10-12；provider key 由 Codex 自己经 `env_key` 读取，命令不需要）。Codex 0.162.0 默认会把它传给命令，无模型探测已确认排除生效、`set` 的变量照常可见。
- Spec Readiness 的 runtime-migration 与 artifact-promotion 各用全新根线程，互不可见，与 ARW 准备规则一致（每个 instanceId 一个独立线程和一次审核）；两份报告分别绑定，按原版融合评分。原"合并实例"（同一线程先 RM 后 AP）已停用（用户 2026-10-13）：它偏离 ARW，且有 AP 照搬 RM finding、引用 RM 专有约定的污染证据（[审查报告](../../reports/v0.1.42/spec-rule-audit/summary.md)）；此前用合并实例得到的 Spec Readiness 结果只在合并实例之间可比。
- Spec Readiness 现行版本是 v4.1（修订号 44；重构已收尾，用户 2026-10-13 决定不再迭代）：冻结源 manifest 依次叠加 `arw-patches/spec-readiness-v2.patch`、`-v3.patch`、`-v4.patch`、`-v4.1.patch`；差异、原因和审查依据见 [v2](../../benchmarks/reviewer-suite-v1/spec-readiness-v2.md)、[v3](../../benchmarks/reviewer-suite-v1/spec-readiness-v3.md)、[v4/v4.1](../../benchmarks/reviewer-suite-v1/spec-readiness-v4.md) 变更说明。分数只在同一版本内比较（v4 回答按 v4.1 键重评分后与 v4.1 可比）；v4.1 用于能力验证和 benchmark，不用于调参（10 次 SD 0.073，[报告](../../reports/v0.1.42/spec-readiness-v4/summary.md)）。
- Code Spec 现行版本是 v5（正式场景，code-spec-reviewer 修订号 38；冻结源 manifest `manifest-code-spec-v5.json`，在 `code-spec-v3.patch` 之后叠加 `arw-patches/code-spec-v5.patch`）：150K 阅读量，20 个缺陷打散到各模块，以长链无线索缺陷为主，混合规则交互、短而隐晦和保底题，见 [v4](../../benchmarks/reviewer-suite-v1/code-spec-v4.md)、[rv](../../benchmarks/reviewer-suite-v1/code-spec-rv.md)、[v5](../../benchmarks/reviewer-suite-v1/code-spec-v5.md) 变更说明。分数只在同一版本内比较。

## 会话检查
- 按冻结 ARW 的 `docs/agents/reviewer-capability-session-inspection.md` 检查每个原生会话：准备项、线程身份、启动上下文、交接后的全部消息、每次工具调用及结果、读写范围、报告和终态，并排查隐藏答案、其他实例等禁止来源。
- 用 `tools.reviewer.inspect_session` 提取，Main 逐条审阅动作（用户 2026-10-11）：
  - 必读 `actions.md` 全文和 `flagged.md` 全文。后者含被标记调用（目标出根目录、`..` 越界、未赋值变量、环境与身份查询、网络、会话或凭据材料、拒绝报错、无结果）的完整命令和结果，以及交接后的非 assistant 消息。
  - 推理、元数据、压缩摘要和未标记调用的结果在安全检查中不作例行阅读。依据：Reviewer 只能经工具调用接触来源，调用目标限于场景根时，结果也只来自场景根。ARW 文档不要求检查推理。诊断早停、卡住等问题时按事件号调取原文。
- 解题过程分析：按测量规则「会话分析」执行。reviewer 场景还要判断场景设计是否达到目的：难度从哪里来、干草堆是否参与找针、有没有捷径。
  - 启动上下文按 `summary.json` 的归一化 SHA 在同批实例间比对，不一致时读原文。
  - 程序只做提取和标记，结论由 Main 根据逐条动作作出；标记项逐条写明判定。
- 环境变量与平台身份查询按结果判定（用户 2026-10-12），调参与 benchmark 相同：
  - 输出或其后续动作接触到隐藏答案、评分材料或其他实例结果，可能抬高得分：该实例无效，按「失败与重跑」处理。
  - 否则（只看到变量名、路径、运行标识、端点等，且后续动作未借此访问禁止来源）：样本保留，分数照常计入均值，在分数旁标"诊断分（环境查询 1 次）"并记录命令与输出范围；不乘 0.9，也不因此判批次失败。
  - 判定写明依据：命令、输出内容范围（是否含值）、之后的工具调用是否用到这些信息。
- 检查完成前不清理原始记录。
- A 类判断题正例与反例数量必须相等（用户 2026-10-15）：不平衡时补题凑齐，不靠计分算法平衡（某一侧为空时算法平衡失效）；已冻结场景补题即出新版本。
