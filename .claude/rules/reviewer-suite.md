# ARW Reviewer 测量规则

## 合同
- 直接使用冻结 ARW 的原场景、完整规则、准备 / 生成 / 评分入口和 Reviewer 运行层。不裁剪用例。确实需要改变合同时，先列出差异并取得同意。
- 评分按场景分两种口径（调参取扣罚前分；能力验证和 benchmark 再按本工程罚分升级扣罚），定义见下文「评分」（用户 2026-10-12）。两者都先由 `tools.reviewer.repair_reviewer_report` 在绑定原实例的独立副本中修复可机械修复的错误，让报告能被评分；benchmark 的修复处计入格式罚的 r（`tools.reviewer.format_penalty`）。原报告不改，修复处数和类型标在分数旁。
- 计分只经 `tools/reviewer/arw_native.mjs` 或 `tools.reviewer.single_scenario_score`，不直接调用 ARW 的计分脚本：这两个入口会先给物化副本补上本工程的评分规则升级（证据 F2 与 k 分档计分，`arw-patches/scoring-k.patch`），并按答案键 sha 绑定 `judgment/` 下的 k 标记。答案键没在 `judgment/registry.json` 登记就报错，新场景版本（含草稿）计分前先登记，未标定的登记为 `all-B`（全部按默认档 0.25）。
- 所有场景的能力判定都用相对口径：Q3 分数与同场景同版本的 Opus 参考分之比（Q3 / Opus），不设绝对分数通过线（如 0.75）；报告给出两者分数、比值和双方 0 命中的用例（用户 2026-10-13）。场景区分度判据是 Q3 / Opus < 0.8，参考模型维持 Opus（用户 2026-10-15；Opus 参考兼作场景正确性检查）。Haiku 完整计分作第二参考（Q3 位置、场景灵敏度），默认不盲裁、给机械区间，特殊情况补盲裁；Haiku-high ×5 另作格式罚基准。
- 重构场景时少用付费模型的做法（总则「少用付费模型」，用户 2026-10-13）：只改答案键或 placement 时，用已有回答重新评分，不重跑 Opus；裁决中能机械判定的部分（证据行是否落在 placement、文件是否存在、重复 finding）先由脚本处理，只把需要语义判断的候选交给付费模型；Opus 参考每个冻结版本只跑一次，改版前先用无模型检查和 Q3 运行排除夹具与评分机制问题。
- 盲裁只裁有变化的部分（用户 2026-10-13）：已裁过的候选，若所属用例的答案键、placement 和裁决 brief 都没变，沿用原裁决，不重复盲裁；只把新回答产生的候选和受改动影响的用例的候选送盲裁。若这样仍消耗较多，再考虑只派一个裁决者。增量盲裁池混入约 10–15 个已裁候选作锚点（对裁决者隐藏来源与原判，覆盖 matched/not-matched 和多个用例），报告锚点数与一致率；不一致时扩大复核。
- 出题原则（用户 2026-10-16/17）：同一道题只出一次，两个子场景之间、同一答案键内部都不得重复。意外的重复改题；有意保留的重复必须在答案键里显式声明为合并用例（`merge`），评分按声明合并：两份各判一次、取低分、只计一次，正反例都适用（评分 r8.2）；两侧期望证据须相同，场景的测量说明告诉 reviewer 重复要求只计一次分、可引用已审过的行并照抄结论和证据（用户 2026-10-17）。不靠计分端去重：计分端只按声明合并，不自行识别重复。冻结检查 `freeze_arw_source.check_repeats` 拒绝未声明的重复。
- 报告凡给得分处同时给耗时，附 token 数和工具调用数；耗时不进分数（用户 2026-10-17）。
- 补充或新增问题用例时，优先选审计或夹具本身能证明、非某一方模型独家发现的缺陷；若取自某个被测模型回答里的线索，报告给出含/不含该用例的两套分数与 Q3/Opus，并注明来源（用户 2026-10-13 同意）。
- 设计或改版场景前读 [scenario-design.md](../../benchmarks/reviewer-suite-v1/scenario-design.md)：场景时长、阅读量维度与时限公式、难度设计、场景分工。
- 权限、网络沿用原生设置：`:read-only` 加显式写路径，审批走 on-request / auto_review；网络与 Codex 默认一致（允许 web_search，不允许脚本访问网络），搜索、MCP 保持原生（用户 2026-10-11）。不额外收紧，不启用可选的严格隔离。多模型 benchmark 期间豁免搜索这一项：所有模型、两个 harness 都关闭搜索（Codex `web_search = "disabled"`，Claude Code 不提供并禁用 WebSearch/WebFetch），安全门和逐实例检查确认没有搜索工具（用户 2026-10-19，D5；[benchmark 计划](../../benchmarks/multi-model-v1/plan.md#3-固定条件)）。第二项豁免是凭据路径 deny-read（G7，2026-10-19 起，所有 Codex 臂含 Strata，不限 benchmark；Main 按硬约束 4 决定，待用户复核）：`:read-only` 能读用户登录和工程私有文件，API 臂会把读到的内容发往外部服务，所以 Reviewer 权限 profile 对 `~/.claude/.credentials.json`、`~/.codex` 整个目录（ChatGPT 登录按用户 2026-10-19 决定用默认的 `~/.codex`；selection 另写的 `auth_home` 同样拒读）、`project.private.toml` 一律设为 `none`（`providers.credential_deny_paths`，由 `arw_native_setup.mjs` 在每次 open 时加进 ARW 生成的 profile，不改 ARW）；安全门在合成 HOME 下用合成文件验证这些路径读不到（`deny_read_pass`），不通过即判失败。其余权限设置不变。
- 私有 scratch（用户 2026-10-20）：以后的 Codex Reviewer 测量默认在 prepare 时选用 ARW 补丁 `reviewer-private-scratch`（`harness_patches`）：每个 Reviewer 一个不在报告目录、不与其他实例共享的可写目录，也是命令的 TMPDIR，公共根对所有 Reviewer 拒读；实例结束后用 `python3 -m tools.reviewer.reviewer_scratch --remove <arw_measure 输出目录>` 删除。多模型 benchmark v1 例外：所有 Codex 臂都不选它，以免前后条件不一致。
- 正式能力测量之前先过「正式测量前的安全验收」。

## 评分
调参（参数维度、资源校准等条件对比）和 benchmark／reviewer 能力验证用不同的评分口径，按场景选择，不混用（用户 2026-10-12）。

评分、盲裁或有效性有争议时，先查[裁决先例](../../benchmarks/reviewer-suite-v1/rulings.md)，有先例就照先例处理；新的裁决定下后补进去（用户 2026-10-21）。

- **证据 F2（用户 2026-10-14）**：ARW 评分里 β 大于 2 的 F-beta 一律改为 F2，即证据定位分 `evidenceF3Score`（问题用例 placement 与 clean 用例证据）改为 F2。与下一条一起由独立的计分补丁实现，所有计分入口固定叠加，不改冻结场景补丁。下文"ARW 原版"均指升级后的规则。
- **按 k 分档计分（评分 r8，用户 2026-10-15/16，取代 F2 总分与 A/B 两类计分）**：每个用例有档位 k，即答错一个反例（clean 用例）相对漏报一个正例（问题用例）的代价。按两点定档：结论能否简单核实（对照选定 Input 的原文就能核实，不需要多步推理），以及判错与漏判哪个影响大。

| 能否简单核实 | 判错与漏判的影响 | k |
|---|---|---|
| 可简单核实 | 任意 | 0.25 |
| 难以核实 | 判错比漏判大 | 4 |
| 难以核实 | 相当 | 1 |
| 难以核实 | 判错比漏判小 | 0.25 |

  - k = 0.25 的含义：可简单核实的问题，漏报代价是误报的 4 倍（误报会被 main agent 核实排除，代价只是核实时间）。默认档是 0.25；k = 1 和 k = 4 的用例写在答案键（`k` 字段）或 `judgment/` 覆盖文件里，同一题型的正例和反例同档；选定时不看模型结果，经独立审查后生效。k = 4 档反例的误报须双裁（两名裁决者一致才算误报，一次误判就相当于 4 个正例漏报）；双裁流程实现之前，冻结检查拒绝 k = 4 标记（答案键和覆盖文件都报错）。
  - 令 N = Σ 正例得分 − Σ 失败反例的 k（含额外失败）。N ≥ 0 时分数 = N ÷ 正例数；N < 0 时分数 = N ÷ Σk，Σk 为答案键全部反例的 k 之和（合并用例计一次，noOther 按 0.25；Spec Readiness 两个子场景先求和再归一）。什么都不报得 0，全对得 1，正例全不报且反例全部失败得 −1；不设下限，额外失败只在分子里扣，可以低于 −1（评分 r8.4，用户 2026-10-21，取消 r8.3 以前截到 [0, 1] 的下限：截断让"全部行报空话"和"只在问题行报空话"同分）。模型失误（没有报告）按正例全部漏报、反例全部失败计，得 −1；取 −1 还是 0 待用户定（r8.4 暂按 −1）。正例：k = 0.25 档得 ARW 部分分 c（0.4 结果 + 0.4 证据 F2 + 0.2 原子性）；k ≥ 1 档与答案关联就得 1，否则 0，证据定位分不设门槛（评分 r7 起）。反例：被误报（经盲裁确认，R1、R3b）记 k；k = 0.25 档按 k ×（1 − 干净分）计，干净分含 Commit Audit 的证据观察分；k ≥ 1 档干净分大于 0 即算通过（Commit Audit 的部分证据观察分不扣），为 0 才记 k（目前没有 Commit Audit 的 k ≥ 1 用例，以后定档时再定是否改为线性扣分）。反例（含 noOther）只有所属检查存在时才算通过；现有场景中这条只对 Spec Readiness 缺检查的报告起作用（Commit Audit、Code Review 的检查总是存在）。noOther 和额外失败的反例（R3b 中排在 noOther 之后的无依据 finding、同一反例的重复误报、越过停止点、Commit Audit 范围外的行）一律按 0.25 计。Commit Audit 的 finding 落在答案键判为 satisfied 的要求行上时，按 `requirementSource` 直接提名该行反例，不看证据和 `findingTerms`；裁为无依据时也只让该反例失败，不再占 noOther，同一个判断错误只扣一次（评分 r8.1，用户 2026-10-17；前提是同一行上的同一个错误被两条计分途径重复计入，模型写出的每一条错误行各自计分，同源误读不合并，用户 2026-10-18）；发现候选裁决也只能把 finding 补关联到同一要求行的问题用例（评分 r8.3）。答案键声明的合并用例（`merge`，同名恰两例、不同范围、同种类与 k 和结果）按一个用例计：正例取两者较低的得分，反例取较高的失败权重，k 档计数和分母各计一次（评分 r8.2，用户 2026-10-17）。没有额外失败反例时，这等价于每例得分 s ∈ [−1, 1]（正例 2c − 1，反例过 +1、败 −1）按正例 1、反例 k 加权平均后，以"什么都不报"为零点分段线性重标：零点以上以满分为 1，零点以下以"正例全不报、反例全部失败"为 −1，两侧斜率不同（P 与 Σk 之比）；额外失败反例不进这个加权平均的分母，只在分子里各减 0.25。
  - 平衡（用户 2026-10-15/16）：每个 k ≥ 1 档内，正例数 = k × 反例数（k = 1 正反等数，k = 4 四比一），一律报或一律不报在该档都得 0，评分没有漏洞可钻；不平衡时补题，不靠计分算法平衡，已冻结场景补题即出新版本。k = 0.25 档不要求平衡：一律报得正分正是偏重召回的含义，每条发现都要给定位和理由，无依据的按 R3b 失败一个反例。各档权重由用例构成决定，不设上限；计分结果列出 k ≥ 1 各档的正反例份额（`kTiers`），各档权重占比由报告计算。
  - Spec Readiness 一次重复的 RM 与 AP 合并计算，先合并两个子场景的计数（含 Σk）再计算分数，单个子场景的分数只作诊断。两个子场景不出同一道题，与 k 无关（用户 2026-10-16/17）：每个子场景各自完整覆盖它的全部检查；RM 是短场景，只审 INPUTS、REQUIREMENTS 两项需求检查，这两项的正反例全部归 RM，AP 照常覆盖这两项但只保留 noOther；其余检查的用例按证据文件分边（正例已按 `FULL_REVIEW_SELECTED_SPECS` 分）。意外的重复改题（见「出题原则」）；拆分时若有 noOther 之外的用例同时进入两边，ARW 加载答案键即报错（v4.3 补丁）。不再有份额规则，0.5 份额代码已在评分 r8.2 删除。
  - 迁移：两类计分的 A 类标记（答案键 `judgment: true`、覆盖文件里没写 k 的用例）按 k = 1 读取，其余用例按 0.25。
  - 能力判据 Q3 / Opus < 0.8 沿用（用户 2026-10-16）；调参的 SD 阈值按新尺度跑出结果后再定（用户 2026-10-16），新阈值同时看分数和 `rawScore`（r8.4 起分数不再在 0 处截断；r8.3 以前截断会让弱条件的 SD 显得偏小）。

| | 调参（参数维度、资源校准等条件对比） | benchmark、reviewer 能力验证 |
|---|---|---|
| 目的 | 比较条件，分数只反映主要体现模型能力的因素 | 与 ARW 自己的结果直接对比 |
| 罚分 | 取扣罚前分（`scoreBeforePenalty`），ARW 的整体罚分一概不计 | 按罚分归属原则（见下）：格式错误按比例整体罚分，其余报告错误在所属用例内扣分；越过停止点见下 |
| 格式错误 | 不计入分数，只记录并标在分数旁 | 计入格式罚：f = 0.1×min(1, p/(2·p基准))，最终分 = 罚前分 − f ×|罚前分|（评分 r8.4；罚前分 ≥ 0 时即 ×(1 − f)，负分同样降低）；p = r/T，r 为全部格式错误数，T 为计分器读到的定位数（均按计分器口径），p基准见下 |
| 可机械修复的错误 | 修复成可评分副本，只为让报告能被评分 | 修复成可评分副本，修复处计入 r，修复后的证据有效 |
| 无法机械修复的错误 | 按 ARW 原版判定，只影响其本身的得分项 | 格式错误（不是条目的报告行、无效 JSON/UTF-8 行、无法归到需求的行）计入 r；起点在文件内、终点越过文件末尾的区间截到末尾，计入 r；其余（无效定位、缺失或无效的需求行、答案键外的需求行等）在所属用例内扣分 |

- 理由（用户 2026-10-11）：低频、随机的格式和报告诊断样本太少，不能说明能力差异，在调参中只是噪声；benchmark 需要保持 ARW 原版口径，罚分按下面的本工程升级。
- **罚分归属原则（用户 2026-10-15，评分升级 r7）**：按比例的整体罚分只用于无法或不适合归到单个用例的问题，例如格式错误（与所在用例无关，反映模型整体能力）。某个用例的证据有误，只要不是格式错误，就算这条证据无效，在该用例内扣分（影响关联与定位分）；整条发现因此无依据时按 R3b 记一个失败 clean，同一条错误只扣一次。可机械修复的格式问题计入格式罚的 p，修复后证据有效。
- **越过停止点（Spec Readiness `requirement-scope-continuation`，用户 2026-10-15）**：算停止规则这一道题答错，报告仍有效。在 RM 场景记 1 个失败反例，按 k = 0.25 计，不另加罚分；停止点之后的检查内容一律忽略（不计分、不扣分，其报告行的诊断不计入格式罚的 r，定位不计入 T）。按 0.25 计的理由：(1) 影响小，代价只是多花时间做不该做的检查，而时间代价在选模型时会自然体现，不在分数上重复罚；(2) main agent 能发现并忽略越界内容。
- **早退暂停（S2，用户 2026-10-20）**：ARW 到达早退暂停点时，harness 以用户身份答复继续（发普通消息，走原版继续入口），实例照常跑完。每次暂停都在 instance.json 的 `arw_pause_events` 里记一条违规；计分时有暂停的实例整体扣 0.1（按下条，罚前分 − 0.1 ×|罚前分|），不论暂停几次。ARW 原版评分看不到运行时的暂停，不会重复扣。
- **整体罚分只扣一次（用户 2026-10-20）**：一个实例的各项整体罚分不相乘，只扣一次，取其中最大的扣减。ARW 残余的 0.9 折减（本工程未处理的报告诊断）也是一项扣 0.1 的整体罚分，一起取最大。例如同时有早退暂停（扣 0.1）和格式罚 f 时，最终分 = 罚前分 − max(0.1, f) ×|罚前分|（评分 r8.4 起按分数绝对值扣，负分同样降低；罚前分 ≥ 0 时即 ×(1 − max(0.1, f))，与 r8.3 逐位相同）。
- **格式罚基准 p基准**：按冻结答案键（审查者 + `expected.json` sha256）登记在 `benchmarks/reviewer-suite-v1/format-baseline.json`，取 Haiku-high ×5 的合并 Σr/ΣT，下限每份报告 2 处（2/平均 T），同时登记 bootstrap 90% 区间；基准报告与修复记录按 sha256 存档在 `benchmarks/reviewer-suite-v1/format-baseline/`，可据此重算。未登记的答案键报错；Haiku 升级后重测。计算用 `python3 -m tools.reviewer.format_penalty`，每个实例都须声明修复记录（`--repair`）或无修复（`--no-repair`）。
- 证据定位的含义只有一个，以冻结 ARW 的定义为准，调参和 benchmark 相同，修复不得改变含义（用户 2026-10-12）：
  - Commit Audit（角色文档 `commit-audit-reviewer.md`）：`lines` 是数组，元素为正整数（单行）或 `[起,止]`（闭区间）。所以 `"lines":[12,20]` 表示第 12 行和第 20 行两行，`[[12,20]]` 才是区间。
  - Code Review markdown（`reviewer-capability-scenarios.md#locator-matching`）：`完整路径:行,起-止`；同一对反引号内仅含行号的片段归属最近的文件路径；新文件必须写出完整路径。
  - Spec Readiness（`spec-readiness-reviewer/findings.md`）：以 Input 完整 `filePath` 开头，后接行号或范围；同一文件的后续片段可以省略路径，换文件时写出完整路径。
- 可机械修复（在上述定义下有唯一含义、只是写法不合规）：`lines` 写成数组外的单个整数（补成 `[n]`）；markdown 报告第一个编号或 `- ` 条目之前的标题和说明段；正文中省略目录、能唯一对应冻结源中一个文件且行号在文件范围内的简写证据引用。证据引用的是 harness 落盘的工具输出文件（如 Claude Code 把大输出存成文件）而不是源文件，且能按落盘内容（如 diff 的 hunk 头）唯一换算回冻结源文件和行号的，换算后计入 r（用户 2026-10-20：能机械恢复的就算格式错误）；落盘文件缺失或换算不唯一的，按无效定位在用例内扣分。报告已写完、只是最终状态消息不恰为 ARW 要求的写法（如 `{"status":"ready"}` 前多了说明），且未经接续修正的实例，按已交付计分，每个实例计 1 处格式错误进 r（用户 2026-10-20，B 类）。只纠正写法，不改判断、finding 或证据指向；修复在绑定原实例的独立副本中进行，往返断言确认只改了这些位置，原报告不改。Commit Audit 要求行号整体错位（用户 2026-10-21，见[裁决先例](../../benchmarks/reviewer-suite-v1/rulings.md)）：某行引用的要求原文在请求的第 1 关要求行中唯一对应同一文件的另一行（要求原文里的反引号片段都在该行里，其余词至少 80% 在该行里；多于一行或没有都不修），且改挂后没有别的行也落在这一行，就把该行的 `source.line` 改到那一行，每个改挂的行计 1 处进 r；第 2 关（spec 行自由）不修。因原报告语法有效，ARW 的格式修正入口不收，修复副本直接作为被评分的报告（`bench_score.place_reports`）。改挂后新形成的候选需重新盲裁（决定库按指纹判旧决定作废）。符合 ARW 定义的写法（如顶层 `[a,b]`）按定义解释，不做修复，即使模型可能本意是区间。
- 无法机械修复：行号越界（单行或区间起点超出文件；起点在文件内、终点越界的区间由计分器截到末尾并计入 r）、证据写成非定位内容（如时间比较）、简写对应多个文件。
- 修复不改变样本数，每个实例无论得分高低都用同一套规则。
- 调参判定标准（用户 2026-10-13）：ARW 场景 10 次组内 SD ≤ 0.068（单侧 90% 上限 < 0.1），扣罚前和扣罚后两个口径都满足，才考虑用于调参；判定只看 10 次，不按 5 次提前下结论。这个阈值定于 r8 之前的分数尺度，r8 尺度下的阈值待新结果出来后由用户再定，新阈值同时看 `rawScore`（用户 2026-10-16；r8.4 起分数不再截断）。

## 场景流程
- 场景逐个进行，不并行。一个场景要等正式场景冻结并完成正式测量才算做完，才开始下一个；阅读量这类单变量维度测完不算场景做完。排顺序或提建议前，先核对当前场景的正式版本是否已冻结并测完（用户 2026-10-13/14）。
- 流程（每个场景）：0 整理规则、场景、答案键与评分 → 1 Opus（high）审计 + 盲答循环，至多 6 轮，直到无问题 → 2 Opus（medium）基准 ×3 → 3 IQ3_XXS ×5（空闲时加测到 10，见测量规则「空闲时加测」）→ 4 评估 Q3 回答（逐 finding 复核裁决、会话检查、对比 Opus、组内标准差）。完成 4 后，"一切正常"是否成立、能否冻结或转下一场景，按重要决策处理（独立 agent 给意见，Main 综合），结论写进报告，并在状态页 `know` 交用户复核，不停下等待；不成立时先修当前场景。盲答漏检不自动成为删题理由，只有审计确认"从 Input 推不出或有歧义"才改或删。
- "一切正常"判据（用户 2026-10-13）：Opus 基准明显高于 Q3；没有 Opus 与 Q3 都 0 命中且审计认为可疑的用例；Q3 5 次会话全部有效；评分可复现（独立复评一致）。
- 加难最多两版（新版 + 中点版）；仍达不到 Q3 / Opus < 0.8，就冻结末版、记为区分度不足、转下一个场景（用户 2026-10-15；Code Standards 起，适用于所有场景）。

## 执行
- 时限按累计工作时间计：初审 55 分钟提醒、60 分钟中断；同线程后续沟通 10 分钟提醒、15 分钟中断。提醒和中断使用原版 ARW 接口。
- 提醒和中断是高优先级消息，目的是让模型在超时之前确实收到：harness 为送达它而打断当前生成（如 Codex 放弃正在接收的流、带着消息重发）是预期行为，不是故障。relay、代理和有效性检查都要把这种主动打断和真实传输错误分开，不能因此判失败或作废（用户 2026-10-20）；benchmark 的机械判据见 [benchmark 计划 §14 M2](../../benchmarks/multi-model-v1/plan.md)。
- 能力验证和 benchmark 中，早停接续使用 ARW 原版运行层的接续机制（用户 2026-10-11：最大限度还原 ARW，便于与 ARW 自己的结果直接对比）。到达原版 10 / 5 次早退暂停点时按「早退暂停（S2）」处理：harness 以用户身份答复"继续"，实例照常跑完。Claude Code 路径没有 ARW 运行层，由 `tools.reviewer.claude_headless.execute_continued` 在 harness 里模拟：交付判定、三种接续指令原文、10 / +5 暂停点和截止规则都照冻结 ARW，在同一会话里 `--resume` 发出（用户 2026-10-20）。
