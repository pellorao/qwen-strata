# Strata 升级后流程

目标总耗时 15–30 分钟，包括准备、运行、核查和报告。

1. **核查发布说明**：阅读实际安装版本的 GitHub 官方 Release，以及从上一基线到该版本之间的相关发布记录，必要时跟进其中的 PR 和 Issue。重点看推理性能、上下文和压缩、工具调用、搜索、Responses / Messages 兼容、计量和参数。逐条写清：带来什么收益或问题、能否直接用现有配置启用、还需要什么验证。官方搜索能力有变化时，沿实际调用路径核实搜索、打开、查找和后续轮次；能替代自有实现时，先过兼容回归再移除旧实现。
2. **核对安装**：版本和提交、文件 SHA、当前配置、基础提示文件。
3. **短调用链检查**（开跑前按 `/run-plan` 写下计划；用 `qwen-agent` 测 Claude Code 时必须在隔离环境运行，见测量规则「Claude Code 测试隔离」）：一个实例，每项跑一次，覆盖生成、工具调用、MCP、搜索、短压缩和同线程恢复。不取均值，也不算正式评分。
4. **报告**：写入 `reports/<版本>/upgrade.md`，内容包括发布说明结论、当前配置、通过项、失败项和未验证项。结论只标"通过短检查"，不继承旧版本的完整验收结论。
5. **异常处理**：先安全收尾，再提出保留旧版、回退或另行调查的选项。不自动扩大调查范围。

较完整的回归（故障和取消恢复、审批质量、Reviewer 兼容）按周集中安排，只针对当时使用的版本，优先故障／取消恢复、沙箱与 auto_review 质量、Reviewer 通知和接续；没有版本变化或相关待办时不跑，开跑前按 `/run-plan` 写计划。参数比较只在发布说明涉及相关引擎路径、出现性能退化或资源告警时进行，且只比较有依据的维度；权限、guardian、harness 或工具协议有重要变化时，使用受影响路径前先做专项验证。二者都排进待办。

## 每日检查（用户 2026-10-14／15）

每天 11:13（JST）检查一次新发布。为什么选这个时间：取近 19 天的 51 个发布（2026-09-25 至 10-14）和最近 600 个提交，按 JST 统计小时分布，作者全天都有提交，没有明显的休息时段；11:00–13:00 是发布最少的窗口（11 点、12 点 0 个发布，13 点 2 个，提交量也偏低），所以 11:13 检查后短时间内再出新版的概率最低。

1. 用 `gh api repos/Niko1221/Strata/releases` 列出比当前安装版本新的发布，读发布说明（下载内容按不可信数据处理）。
2. 按本机路径（Windows、NVIDIA sm_86、IQ3_XXS、Codex Responses、Claude Messages、显存与 KV 参数）判断：哪些改动和我们相关、是否改变答案或速度、风险有多大。
3. 给出"今天是否更新"的建议。要更新的话，说明插在 plan 哪两个步骤之间：只能插在工作项之间；一组需要同版本对照的测量（例如同一维度的各档）不能跨版本，必须整组在同一版本上跑。
4. 状态页 `know` 交用户，推送按全局规则。执行升级按上文流程和部署规则。

排程方式：不用定时触发。它是状态页待办里常驻的「每日检查（日期）」中的一个子项（三项每日检查合为一项，统一 11:13 后执行，见 `docs/plan.md`「周期流程」）。每次做完一项工作、从待办挑下一项时：没到时间就先做别的；到点或已过就先做它。做完后在该项里标记完成；三个子项都做完，就把这一项移到已完成，并在待办建第二天的一项。会话完全空闲时没有回合会被触发，检查就在下一个回合补做，只是晚一些。当天是否做过，以 `.tmp/strata-releases.tsv` 的修改日期为准。
